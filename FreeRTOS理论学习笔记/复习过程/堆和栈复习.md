# 堆和栈

**栈（Stack）**和**堆（Heap）**是计算机内存管理中两个极其核心且功能截然不同的概念。在嵌入式系统（如 STM32 和 FreeRTOS）中，理清它们的区别对于防止系统崩溃和内存泄漏至关重要。

### 一、 栈 (Stack) —— 任务的私有工作台

栈是一块<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">由编译器或操作系统底层**自动管理**的内存区域</span>，它的核心使命是**为<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">函数调用</span>和<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">任务运行</span>提供<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">临时的存储空间</span>**。

- **存放的内容：** 栈主要用于存放**<span style="background:#00FF80; border:1px solid #FF00FF;">局部变量</span>**、**<span style="background:#00FF80; border:1px solid #FF00FF;">函数参数</span>**（<span style="color:#FF0000;">尤其是超过 4 个时的多余参数</span>）、以及<span style="background:#00FF80; border:1px solid #FF00FF;">函数调用时的**上下文现场**</span>（如 <span style="color:#FF0000;">CPU 的寄存器备份</span>和<span style="color:#FF0000;">函数返回地址 LR</span>）。
- **生长方向：** 在 ARM 架构中，栈采用的是**“倒生长”**机制，即**从高地址向低地址生长**。每次向栈内压入数据（`PUSH`），栈指针（SP）的值就会减小，相当于在内存中“向下挖坑”。
- 物理布局与分类：
  - **<span style="background:#00FF80;">系统栈 (MSP)</span>：** 位于<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;"> RAM 的最高地址处</span>，向下生长。它是系统公用的，主要供**<span style="color:#FF0000; background:#00FF80;">中断服务函数 (ISR) </span>和<span style="color:#FF0000; background:#00FF80;"> OS 内核</span>**使用。
  - **<span style="background:#00FF80;">任务栈 (PSP)</span>：** 在 FreeRTOS 等操作系统中，<span style="background:#00FF80;">**每个任务都有自己独立的、私有的栈空间**。</span>如果<span style="color:#FF0000;">任务是<span style="background:#00FF80;">动态创建</span>的</span>，这块<span style="color:#FF0000;">栈空间其实是<span style="background:#00FF80;">系统从“堆”中划拨出来</span>的一块内存</span>；如果是<span style="color:#FF0000; background:#00FF80;">静态创建</span>的，则是<span style="font-family:serif; background:#00FF80; border:1px solid #FF00FF;">位于<span style="color:#FF0000;">静态区（.bss 段）</span>的一个<span style="color:#FF0000;">全局数组</span></span>。
- **致命风险（栈溢出）：** 栈的空间通常是<span style="color:#FF0000; background:#00FF80;">有限且固定</span>的。如果函数嵌套调用太深，或者在函数内部定义了巨大的局部变量数组，栈指针就会越界，这被称为**栈溢出 (Stack Overflow)**。<span style="color:#FF0000; background:#00FF80;">溢出的栈会无情地破坏相邻的任务栈、全局变量或堆数据</span>，导致系统莫名其妙地卡死或崩溃。

### 二、 堆 (Heap) —— 全局的共享大仓库

堆是一块庞大的、供程序在运行时**动态“申请”和“释放”**的全局内存区域。

- **存放的内容：** 任何通过动态内存分配函数（如 C 语言的 `malloc`、FreeRTOS 的 `pvPortMalloc`）申请的内存，都出自于堆。在 FreeRTOS 中，如果你<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">使用动态方式（如 `xTaskCreate`）创建任务</span>，内核会自动<span style="color:#FF0000;">从<span style="background:#00FF80;">堆</span>中<span style="background:#00FF80;">申请两块内存</span></span>：一块用作<span style="color:#FF0000; background:#00FF80;">任务控制块（TCB）</span>，一块用作<span style="color:#FF0000; background:#00FF80;">任务的私有栈</span>。此外，<span style="color:#FF0000; background:#00FF80;">动态创建的队列</span>、<span style="color:#FF0000; background:#00FF80;">信号量</span>等<span style="color:#FF0000; background:#00FF80;">内核对象</span>也<span style="color:#FF0000; background:#00FF80;">都在堆中分配</span>。
- **生长方向：** 在 <span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">STM32 的内存映射</span>中，<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">堆</span>通常<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">紧挨着静态区（.bss 段）的末尾</span>，**从低地址向高地址生长**（向上生长）。如果堆不断向上长，栈不断向下长，两者在中间相撞，就会发生灾难性的硬件错误（HardFault）。
- **管理机制与碎片问题：** <span style="color:#FF0000;">堆的管理</span>依赖于<span style="color:#FF0000;">复杂的底层算法</span>。申请内存时，系统会在用户数据前隐藏一个“头部”（Header）记录这块内存的大小，然后切分一块空间给你；释放（`free`）时，系统通过这个头部读取大小边界，并将内存归还给**空闲链表 (Free List)**。频繁地申请和释放不同大小的内存，会导致大块内存被切割得支离破碎，形成**内存碎片 (Heap Fragmentation)**，最终可能导致系统有总空闲内存却无法分配大块连续空间的窘境。

### 三、 核心互动：指针的“口袋与储物柜”比喻

为了彻底弄明白<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">堆和栈</span>是如何配合工作的，我们可以将**<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">任务栈（Stack）</span>比作你衣服上的口袋**，将**<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">系统堆（Heap）</span>比作火车站的储物柜区**。

当你在一行代码中写下 `char *buf = pvPortMalloc(100);` 时，实际上发生了跨越堆和栈的三个动作：

1. **口袋里的纸条：** `char *buf` 作为一个<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">局部指针变量</span>，仅仅<span style="color:#FF0000;">占用 <span style="background:#00FF80;">**栈** </span>上的 4 个字节空间</span>（它是你口袋里的纸条）。
2. **租用储物柜：** `pvPortMalloc(100)` 跑去庞大的全局 <span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">**系统堆** </span>里，为你划出了<span style="background:#00FF80;">一块真正用于存数据的 100 字节实体空间</span>（你租用的储物柜）。
3. **记录编号：** 赋值操作 `=` 将堆里那 100 字节的首地址，抄写到了你栈上的 `buf` 变量里（在纸条上写下储物柜的编号）。

**最危险的内存泄漏陷阱：** 在 FreeRTOS 中，如果<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">一个任务被删除</span>（如调用 `vTaskDelete`），内核会<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">自动负责把这个任务的 TCB 和任务栈空间回收</span>（相当于把你整条裤子和口袋一起烧了）。 但是，内核**绝对不会**去检查你栈里面的指针指向了哪里。如果在此之前你没有手动执行 `free(buf)`，那么随着口袋被烧毁，你永远丢失了找回储物柜的“地址纸条”。此时，堆里的那 100 字节依然显示“已占用”并锁死，这就造成了极其严重的**内存泄漏 (Memory Leak)**。



# stm32 的内存映射

<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">stm32的内存映射是什么样的呢，我怎么记得好像不只有堆栈，还有.data，.bss，.rodata这些之类的好像。各个部分都是存放些什么内容呢。</span>

在STM32的CPU眼中，它看到的是一个<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">连续的4GB地址空间</span>（从 `0x0000 0000` 到 `0xFFFF FFFF`），这个巨大空间被硬件设计者划分成了不同的“街区”（也就是内存映射）。你记忆中的 `.data`、`.bss`、`.rodata` 等段（Sections）确实存在，<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">编译器和链接器会根据数据的性质</span>，将它们智能地分配到<span style="color:#FF0000; border:1px solid #FF00FF; background:#00FF80;">物理上的 **Flash（闪存）** </span>和 <span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">**SRAM（内存）** </span>这两块核心区域中。

具体的分布与存放内容如下：

**1. 存放在 Flash (通常<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">从 0x0800 0000 开始</span>)** Flash 的特性是掉电不丢失且运行时只读，它就像是“刻在石碑上的字”。

- **代码区 (`.text` 段)**：这是程序真正的“家”，专门存放**编译后的机器码指令**（比如你的 `main()` 函数和其他所有的业务逻辑代码）。STM32 支持“就地执行”（XIP），CPU 上电后直接从这里读取指令运行。
- **只读数据区 (`.rodata` 段)**：存放着**全局的 `const` 常量**（如 `const int MAX_USERS = 100;`）以及**字符串字面量**（如 `"Hello!"`）。将常量存放在 Flash 中不仅能极大地节省宝贵的 SRAM 空间，还能通过硬件特性防止程序里的野指针意外篡改这些关键数据，提升安全性。
- **`.data` 段的初始值**：虽然<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">已初始化的全局变量在运行时是放在 RAM</span> 里的，但它们断电前配置好的“初始值”必须保存在掉电不丢失的 Flash 中，等待系统启动时被搬运。

**2. 存放在 SRAM (通常从 0x2000 0000 开始)** SRAM 的特性是读写速度极快但掉电即丢数据，它是程序运行时的“工作草稿纸”。

- **数据区 (`.data` 段)**：存放**<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">已初始化的全局变量和静态变量</span>**（如 `int global_counter = 10;`）。在芯片上电启动的瞬间，隐藏的启动代码（Startup file）会负责把 Flash 中存放的初始值完整“拷贝”到这个 SRAM 区域中。
- **静态区 (`.bss` 段)**：存放**<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">未初始化的全局变量和静态变量</span>**（如 `int sensor_reading;`）。启动代码会自动将这块 SRAM 区域**全部清零**（这也是为什么未初始化的全局变量默认值为0的原因）。在 FreeRTOS 中，如果我们使用静态分配的方式创建任务（例如定义 `StackType_t myTaskStack;`），这个任务的专属栈空间也是在编译时就被划拨在 `.bss` 段，拥有绝对安全的“永久产权”。
- **堆区 (Heap)**：存放**程序运行时动态申请的内存**（例如调用 C 语言的 `malloc`，或者 FreeRTOS 中使用 `xTaskCreate` 动态分配任务 TCB 和栈空间时切走的内存）。在内存布局上，堆通常紧挨着 `.bss` 段的末尾，**从低地址向高地址（向上）生长**。
- **栈区 (Stack)**：存放**局部变量**、**函数参数**以及发生函数调用或硬件中断时的**CPU上下文现场（如返回地址 LR、各个寄存器的备份）**。系统主栈通常位于 RAM 的最高地址处，**从高地址向低地址（向下）生长**。

**补充：堆与栈的“相撞危机”** 在<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">整个 RAM 的空间规划中，底部的 `.data` 和 `.bss` 区域大小在代码编译链接完毕的那一刻就固定死了。剩下的整片空白 RAM 空间，全部留给堆（向上长）和栈（向下长）去共同瓜分。</span>在堆和栈之间会有一块空闲的缓冲无人区，只要程序中函数嵌套不深（栈不越界）、动态申请不过度（堆不溢出），两者没有在中间发生相撞，系统就是稳定安全的。



# 系统栈 与 任务栈（不占用实际栈空间）

<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">系统栈的作用是什么呢，你能够给我举个例子吗解释下吗，还有系统栈的内存布局是什么样的呢，这里任务栈无论是动态创建（在堆上分配任务栈）还是静态创建（在全局数据区.bss 上分分配任务栈）都是不占用内存中实际的栈空间的好像。</span>

你的理解非常精准！你已经完全看透了底层内存布局的本质。<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">任务栈（无论是动态创建还是静态创建）确实**不占用内存映射中那个位于顶部的、专属的“系统栈（System Stack）”空间**。</span>它们本质上只是 RAM 里的一块普通内存（缓冲区）。

为了让你彻底融会贯通，我将为你详细拆解系统栈的作用、运作实例，以及它在内存中的物理布局。

### 1. 系统栈的作用是什么？

在 STM32（Cortex-M 架构）结合 FreeRTOS 的系统中，<span style="background:#00FF80; color:#FF0000;">硬件提供了“双堆栈机制”：</span>

- **任务栈 (PSP - 进程栈指针)：** 每个任务私有，用于<span style="color:#FF0000; background:#00FF80;">保存任务自己的局部变量和函数调用。</span>
- **系统栈 (MSP - 主栈指针)：** 它是系统公用的，主要供**<span style="background:#00FF80;">中断服务函数 (ISR) 和操作系统内核代码</span>**使用。

你可以把系统栈比作医院里唯一的**“公共急救室”**，而任务栈是医生各自的**“私人工位”**。不管哪个医生（任务）在工位上干活，<span style="background:#00FF80; color:#FF0000;">一旦发生突发急诊（硬件中断），所有人都要放下手里的活，使用这唯一的急救室（系统栈）来处理紧急情况。</span>

**为什么必须这样区分？（核心作用）** 主要是为了**极大地节省内存**。<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">如果不区分（单栈模型），任何一个中断随时可能打断任务并在当前任务的栈里压入大量数据，这意味着**每一个**任务栈都必须预留出足够应对“最坏中断嵌套”的巨大空间。区分后，所有中断共用一个系统栈，任务栈只需要管自己的业务逻辑即可，极大减少了 RAM 消耗，也防止了任务栈溢出破坏中断系统。</span>

### 2. 结合实例：系统栈是如何运作的？

假设你的系统中有一个正在运行的“任务 A”，并且发生了一个“串口接收中断”。

1. **任务 A 正常运行：** 此时 CPU 使用的是 PSP（任务栈指针）。任务 A 内部定义的局部变量都存放在<span style="color:#FF0000; background:#00FF80;">任务 A 的专属栈（位于堆或 `.bss` 段）</span>中。
2. **中断突发瞬间（硬件自动切栈）：** 串口中断信号到来。CPU 硬件会自动暂停任务 A，并**瞬间切换到使用 MSP（系统栈指针）**。<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">此时，CPU 会把任务 A 打断瞬间的部分核心寄存器（如 R0-R3, R12, LR, PC, xPSR）自动压入**系统栈**中保存现场。</span>
3. **执行中断服务函数 (ISR)：** CPU 开始执行你写的 `USART_IRQHandler` 中断代码。<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">如果你在中断函数里定义了一个局部变量（例如 `char buf`），这 100 个字节的占用会全部分配在**系统栈**上，完全不会消耗任务 A 的栈空间。</span>
4. **中断返回：** <span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">ISR 执行完毕后，CPU 从系统栈弹出刚才保存的寄存器，恢复任务 A 的现场，然后硬件自动切换回 PSP。任务 A 像什么事都没发生过一样继续在自己的任务栈上运行。</span>

### 3. 系统栈的内存布局是什么样的？

在 STM32 的内存映射中，<span style="color:#FF0000; border:1px solid #FF00FF;">RAM 的布局</span>通常呈现一种<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">“三明治”</span>或<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">“对向生长”</span>的结构。

<span style="color:#FF0000; background:#00FF80;">系统栈</span>位于整个 **<span style="color:#FF0000; background:#00FF80;">RAM 的最高地址处，并且是从高地址向低地址（向下）生长的</span>**。 <span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">具体的内存分布从低地址到高地址</span>依次为：

- **`.data` 和 `.bss` 段（底部）：** 存放<span style="color:#FF0000; border:1px solid #FF00FF;">已初始化和未初始化</span>的<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">全局变量</span>、<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">静态变量</span>。**<span style="background:#00FF80;">静态创建的任务栈（一个全局数组）就固定存放在 `.bss` 段里</span>**。
- **堆区 / Heap（中间，向上生长）：** 用于 `malloc` 动态分配。**<span style="background:#00FF80;">动态创建的任务 TCB 和任务栈就是在这里挖出的一块块内存</span>**。
- **空闲缓冲区（缓冲无人区）：** <span style="color:#FF0000; border:1px solid #FF00FF; background:#00FF80;">堆的顶点和系统栈的栈底之间的空白地带</span>。
- **系统栈 / MSP（顶部，向下生长）：** 这是<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">供 `main` 函数启动前以及中断 (ISR) 使用的专属栈空间</span>。

**总结验证你的理解：** 你的理解完全正确！任务栈无论静态还是动态，都只是占用底部的 `.bss` 段或中间的堆区空间，CPU 只是临时把 PSP 寄存器指向这些区域的末尾当做栈来用。<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">真正物理意义上位于 RAM 顶部的那个“栈”，是专门留给中断和内核使用的系统栈。</span>只要中间的空闲区域没有被耗尽，底下的堆（包括动态任务栈）就不会和顶部的系统栈发生相撞（HardFault）。



# freeRtos 各种组件存放位置

<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">动态创建的任务栈的私有空间和TCB都是在堆上的，那么静态创建的任务栈的TCB是存放在哪里呢，也是.bss段吗？还有freeRtos中的各种组件，如信号量，互斥量，事件组，各种队列（就绪阻塞延时挂起）等这些都是在哪里存放的呢，应该不是在系统栈吧。</span>

你的理解非常准确！静态创建的任务相关的结构，以及 FreeRTOS 的各种核心组件和系统列表，**绝对不会存放在系统栈（MSP）中**。<span style="color:#FF0000; background:#00FF80;">系统栈</span>是专门留给<span style="color:#FF0000; background:#00FF80;">中断服务函数（ISR）</span>和<span style="color:#FF0000; background:#00FF80;">操作系统内核处理突发硬件中断时临时保存现场和局部变量</span>用的，里面的数据用完即焚，随时会被新的中断覆盖。

关于它们的具体存放位置，我们可以分为以下三个层面来详细拆解：

**1. 静态创建的任务 TCB 存放在哪里？** 答案是：**存放在 `.bss` 段（静态区）**。 <span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">当你</span>使用 `xTaskCreateStatic` <span style="color:#FF0000; background:#00FF80;">静态创建任务</span>时，你<span style="color:#FF0000; background:#00FF80;">必须在代码中手动提前定义两个变量</span>：一个是 <span style="background:#00FF80; border:1px solid #FF00FF;">`StackType_t` 类型的数组作为任务栈</span>，另一个是 <span style="background:#00FF80; border:1px solid #FF00FF;">`StaticTask_t` 类型的结构体作为 TCB</span>。 因为这些变量必须拥有跨越函数生命周期的“永久产权”，我们通常会将它们定义为全局变量或静态变量（`static`）。根据 C 语言的内存映射规则，这些未赋初始值的全局/静态变量，在编译时就会被统一分配到 RAM 的 **`.bss` 段**中，并在系统启动时被自动清零。

**2. FreeRTOS <span style="color:#FF0000; background:#00FF80;">通信组件</span>（队列、信号量、互斥量、事件组）存放在哪里？** 这些组件本质上都是系统内部维护的“内核对象”（例如队列、互斥量、信号量底层都复用了 `QueueDefinition` 结构体）。它们的<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">存放位置完全取决于你的创建方式</span>：

- **动态创建（最常用）：** 如果你调用 `xQueueCreate`、`xSemaphoreCreateMutex` 等动态 API，FreeRTOS 内核会自动调用内部的 `pvPortMalloc` 函数，从 FreeRTOS 统一管理的 **系统堆（Heap）** 中为这些结构体（以及它们的数据缓冲区）切出一块内存。
- **静态创建：** FreeRTOS <span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">也为所有组件提供了静态创建的 API</span>（如 `xQueueCreateStatic`）。如果你使用这种方式，同样<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">需要你提供全局的结构体和数组变量，那么它们自然也就存放在 **`.bss` 段**。</span>

**3. 系统的各种状态列表（就绪、阻塞延时、挂起）存放在哪里？** 这需要区分<span style="color:#FF0000; background:#00FF80;">“列表容器”</span>和<span style="color:#FF0000; background:#00FF80;">“列表里的节点”</span>：

- **全局列表容器（挂钩子的墙）：** 像就绪列表（`pxReadyTasksLists`）、延时列表（`pxDelayedTaskList`）、挂起列表（`xSuspendedTaskList`）等，它们<span style="background:#00FF80;">是在 FreeRTOS 的内核代码（`tasks.c`）中定义的**全局静态变量**。因此，这些列表容器本身固定存放在内存的 **`.bss` 或 `.data` 段**。</span>
- **列表里的节点（钩子）：** <span style="background:#00FF80;">任务并不是把整个 TCB 塞进列表里，而是将 TCB 内部自带的两个节点成员（`xStateListItem` 和 `xEventListItem`）链接到上述全局列表中</span>。既然<span style="background:#00FF80;">这两个节点是 TCB 结构体的一部分，那么它们的物理位置就**跟着 TCB 走**——TCB 在堆上，它们就在堆上；TCB 在 `.bss` 段，它们就在 `.bss` 段。</span>

**总结来说：** 系统运行的<span style="color:#FF0000; background:#00FF80;">全局骨架（各类状态列表头）死死扎根在静态区（`.bss` / `.data`）；而业务用的各种实体组件（TCB、任务栈、队列、互斥量等），则根据你调用的创建接口，要么买下了“永久房产”（静态创建在 `.bss` 段），要么租用了“临时公寓”（动态创建在 堆区 Heap），但它们绝不会占用医院的“公共急救室”（系统栈 MSP）。</span>



# 空闲堆内存管理

<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">这份笔记里面有一个堆内存的管理，有个global_heap，还有个nextfree好像，这里我有点没有看懂是怎么实现的。</span>

这是一个非常核心且精妙的底层内存管理机制！你提到的 `global_heap`（在笔记源码中实际命名为 `g_heap`）和 `next_free`，正是构建**<span style="color:#FF0000; background:#00FF80;">“空闲链表（Free List）”</span>**的核心元素。

为了让你彻底弄懂它的实现原理，我们可以把堆内存（Heap）想象成一块**“巨大的空地”**，而程序需要在这块空地上不断地划出小块地皮（`malloc`）并回收地皮（`free`）。

我们可以通过以下四个步骤来详细拆解它的运作机制：

### 1. 核心角色：物理空地与管理“账本”

首先，内存的物理载体只是一个巨大的连续数组，比如 `char heap_buf;`。 为了管理这 1024 字节，系统引入了两个非常重要的管理工具：

- 管理头部 (`struct head`)：

   系统规定，<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">无论是分出去的内存还是空闲的内存，在它的最开头都必须隐藏一个“头部”。</span>这个头部包含两个信息：

  - `size`：记录这块地有多大。
  - `next_free`：这是<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">一个指针，专门用来指向**“下一块空闲的内存”**在哪里。</span>

- **全局哨兵 (`g_heap`)：** 也就是你提到的类似 `global_heap` 的东西。它是一个全局的特殊头部（哨兵节点），它本身不代表任何实际的内存块（它的 `size = 0`），但它的 `next_free` 指针永远指向**内存中第一块可用的空闲地皮**。

### 2. 初始状态：一整块大蛋糕

在系统刚启动时，整个 `heap_buf` 是完整的一块空闲内存。 此时，系统会在 `heap_buf` 的最开头放一个头部，标明 `size` 为 1024 减去头部自身的大小，<span style="color:#FF0000; background:#00FF80;">它的 `next_free` 设为 `NULL`（因为后面没有别的空闲块了）</span>。 同时，<span style="background:#00FF80;">全局哨兵 `g_heap.next_free` 就会指向这块唯一的巨大空闲块。 **此时的链表形态：`[g_heap]` -> `[巨大的空闲块]` -> `NULL`**。</span>

### 3. 分配内存 (`malloc`)：切蛋糕与“分裂”

假设你现在需要申请 100 字节的内存（`my_malloc(100)`）。

- **顺藤摸瓜：** 系统会去找 `g_heap.next_free`，发现第一块空闲地皮有 1000 多字节，足够大。

- 分裂 (Split)：

   系统不会把整块地都给你，而是把它切成两半：

  - **块 A（给你用的）：** 包含一个新头部（记录 `size = 100`）和 100 字节的数据区。
  - **块 B（剩下的空闲地）：**<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;"> 包含一个新头部（记录剩下的 `size`），并且它的 `next_free` 指向原本块 A 后面的空闲块（在这个例子中是 `NULL`）。</span>

- **更新账本：** 最关键的一步，系统会将全局哨兵 `g_heap.next_free` 更新为指向**新切出来的块 B**。块 A 就这样从空闲链表中被“摘除”了，然后系统把块 A 的数据区地址返回给你使用。

### 4. 释放内存 (`free`)：还钥匙与“插队”

这是 `next_free` 发挥巨大作用的时刻。假设你用完了那 100 字节，调用 `my_free(buf)`。

- **找回账本：** `free` 函数拿到你给的地址后，会向后退几个字节，找到隐藏在前面的那个管理头部，从而读取到 `size = 100`，知道了这块地的大小。
- **挂回链表：** <span style="color:#FF0000; background:#00FF80;">这 100 字节现在变成空闲的了，必须让全局哨兵 `g_heap` 重新管理它。系统会将这块刚刚归还的内存的 `next_free` 指针，指向当前全局链表里的第一块空闲地（即原来的 `g_heap.next_free`）。</span>
- **<span style="color:#FF0000; border:1px solid #FF00FF; background:#00FF80;">更新哨兵</span>：** 最后，让 `g_heap.next_free` 指向这块刚刚归还的 100 字节内存。

**总结来说：** `g_heap` 和 `next_free` 的组合，本质上就是在物理内存数组之上，虚构出了一根**“只把空闲块串联起来的绳子（空闲链表，Free List）”**。

- 每次 `malloc`，就是从绳子上解下一个大环，切下一部分拿走，把剩下的做成小环重新挂回绳子上。
- 每次 `free`，就是把你用完的环，重新挂到这根绳子的最前面去。 正是由于这种设计，系统才能在不断申请和释放造成的“内存空洞（碎片）”中，准确地找到每一块可用的内存。



# 利用链表来管理堆中隔离开的空闲区域

当堆内存经历多次分配和释放操作后，物理内存中会产生不连续的“空洞”（即内存碎片）。为了<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">高效管理这些隔离开的空闲区域</span>，<span style="background:#00FF80; color:#FF0000;">系统底层引入了**“空闲链表”（Free List）**机制。</span>

<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">利用链表管理堆中空闲区域</span>的完整机制可以分为以下几个核心环节：

**1. 核心基石：隐藏的内存头部（Header）与哨兵节点** <span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">要将散落的空闲区域串联起来，就必须借助数据结构。</span>

- **内存头部：** 系统规定，<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">每一块内存（不论是空闲的还是分配出去的）最开头都隐藏着一个 `struct head` 结构体。</span>它包含<span style="background:#00FF80; color:#FF0000; border:1px solid #FF00FF;">两个关键信息</span>：`size`（记录这块内存的大小）和 `next_free`（专门指向“下一个”空闲块头部的指针）。
- **全局哨兵（g_heap）：** 系统还会维护<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">一个全局的链表头节点（如 `g_heap`）</span>。它<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">本身大小为 0，不代表具体内存</span>，但<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">它的 `next_free` 指针永远指向堆中**第一个可用的空闲块**。</span>

**2. 分配内存（malloc）：链表遍历与“分裂”** 当程序申请一段内存时，系统会通过空闲链表来寻找合适的区域：

- **遍历：** 从<span style="color:#FF0000; background:#00FF80;">哨兵节点 `g_heap.next_free` 开始</span>，顺着<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">链表依次检查每个空闲块的 `size`，直到找到一块足够大的空闲区域（首次适配策略，First Fit）。</span>

- 分裂（Split）：

   为了不浪费空间，系统通常会将找到的大空闲块“切”成两半：

  - 第一部分作为**分配块**，更新其头部的 `size`，并将其从空闲链表中“摘除”，把数据区的地址返回给用户。
  - 第二部分作为**新的空闲块**，<span style="color:#FF0000; background:#00FF80;">重新计算它剩余的 `size`</span>，并<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">更新它的 `next_free` 指针，让全局哨兵或其他节点指向它，使它继续挂在空闲链表上。</span>

**3. 释放内存（free）：找回边界与“插入”链表** 当隔离开的区域被释放时，它必须重新回归系统的管理：

- **找回元数据：** `free` 函数<span style="color:#FF0000; background:#00FF80;">接收到用户的地址</span>后，会向低地址方向偏移（减去头部结构体的大小），精准找到隐藏的内存头部，读取出 `size`，从而知道这块“废弃地”到底有多大。
- **重新挂载：** 接着，系统<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">会将这块刚刚释放的内存块重新插入到空闲链表中</span>（例如<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">将其 `next_free` 指向链表原本的第一个空闲块，然后让哨兵 `g_heap.next_free` 指向自己</span>）。

**4. 消除隔离的高阶优化：内存合并（Coalescing）** 如果仅仅是把释放的块挂回链表，堆中依然会充满隔离开的小空洞。 为了彻底解决碎片问题，优秀的堆管理算法（例如 FreeRTOS 中的 `heap_4.c`）在执行释放（free）并将其重新加入链表时，还会增加一步极具智慧的操作：<span style="color:#FF0000; background:#00FF80;">**检查相邻邻居**。 它会查看这块刚刚释放的内存的物理“前邻居”和“后邻居”是否也碰巧在空闲链表中。</span>如果是，系统就会<span style="color:#FF0000; background:#00FF80;">打破它们之间的边界，将它们的 `size` 累加，**合并（Coalescing）成一个超大的连续空闲块**。</span>

通过这种**“自带指针的隐藏头部 + 动态分裂与插入 + 相邻合并”**的链表设计，系统就能在不断产生隔离空洞的堆内存中，始终保持对所有可用空间的高效追踪与管理。





# 这里分配出去的这块内存的开头中的next_free是不是没有用啊，只有空闲块头部的next_free才有用

你的理解完全正确！在这个内存管理机制中，**分配出去的内存块头部的 `next_free` 指针确实在分配期间是“没有用”的（处于闲置状态），<span style="background:#00FF80;">只有空闲块头部的 `next_free` 才参与实际的链表管理</span>**。

我们可以从分配和释放的生命周期来详细印证这一点：

**1. 分配期间（处于闲置状态）** 当调用 `my_malloc` 找到合适的空闲块并将其切割分配给用户时，这块内存（分配块）就会被从全局空闲链表中“摘除”。此时，系统只需要更新它的 `size` 字段来记录这块地有多大，而**不需要设置或关心它的 `next_free` 指针，因为它已经不在空闲链表中了**。因此，在被用户占用的这段时间里，这个 `next_free` 指针确实是毫无用处的。

**2. 空闲期间（发挥核心作用）** 只有那些<span style="color:#FF0000; background:#00FF80;">没有被使用的、留在堆里的空闲内存块，才需要依靠头部的 `next_free` 指针互相串联起来，形成一个“空闲链表”（Free List）。</span>全局哨兵（如 `g_heap`）和后续的空闲块正是通过这个指针来维持联系，以便下一次分配时能顺藤摸瓜找到可用的内存。

**3. 闲置的指针何时再次“复活”？** 那个<span style="background:#00FF80;">分配出去的闲置 `next_free` 指针，只有在用户调用 `free()` 归还内存的那一刻才会重新被激活。在释放时，系统会向低地址偏移找到这个隐藏的头部，读取 `size` 后，会**重新给这个处于闲置状态的 `next_free` 赋值**（例如让它指向原本空闲链表中的第一个块），并让全局哨兵重新指向它，从而将这块内存重新挂载回空闲链表中。</span>

**总结：** 因为系统规定了无论是分配块还是空闲块，在物理上都必须统一使用 `struct head` 这个固定格式的头部（包含 `size` 和 `next_free`），所以它物理上占据了空间。但在逻辑层面上，你的直觉非常精准：**被分配出去的块只用得到 `size`，只有处于空闲状态的块才会真正使用 `next_free` 来维持链表结构**。

# PUSH压栈的寄存器中可以改变与不可以改变

<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">我有个问题，就是函数调用的时候一开头的push操作保存在栈里面的寄存器，这些保存的空间之后在函数内部有些是可以改变有些是不能够改变的吧。还有在push之后是通过sub操作来为栈中的局部变量分配空间的吧 ？</span>

你的理解非常精准，已经完全抓住了 ARM 汇编中函数栈帧（Stack Frame）构建的核心逻辑！

关于你的两个问题，我们可以结合底层机制详细拆解如下：

### 1. `PUSH` 保存在栈里的寄存器空间，能改变吗？

物理上，这些数据被压入了 RAM（内存）中，所以**绝对是可以被修改的**。但是从**软件运行逻辑和系统安全性**的角度来看，它们分为“绝对不能碰”和“可以随意改”两类：

- 绝对不能改变的空间（保护现场的私有寄存器 & 返回地址）：

  如果 

  ```
  PUSH
  ```

   压入的是 

  ```
  R4~R11
  ```

  （被调用者保存寄存器）或者 

  ```
  LR
  ```

  （链接寄存器，存着返回地址），这段栈空间是神圣不可侵犯的。

  - 如果函数在内部（比如因为数组越界）不小心修改了保存 `LR` 的那块内存，那么当函数执行完毕调用 `POP {..., PC}` 准备返回时，CPU 就会弹出一个错误的垃圾地址并跳转，直接导致程序跑飞或触发 HardFault 硬件死机。
  - 同样，篡改了 `R4~R11` 的备份，也会在 `POP` 恢复现场时破坏掉调用者（上级函数）的私人数据。

- <span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">可以改变的空间（强制分配到内存的参数/局部变量副本）：</span>

  在某些特定情况下，编译器会把 R0~R3（用来传参的公共寄存器）也 

  PUSH 进栈里。比如资料中演示的带有 volatile 关键字的参数，<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">编译器为了强制给参数分配一个真实的物理内存地址，会在函数一开头就 </span>PUSH {r0, r1}。

  - <span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">此时，这块存着 `R0`、`R1` 初始值的栈空间，本质上就变成了该函数内部的普通**局部变量空间**。</span>
  - 因为按照 AAPCS 规则，调用者本来就不指望函数会保留 `R0~R3` 的旧值，所以函数在内部完全可以根据业务逻辑，随意覆盖、修改这块特定的栈内存。

### 2. `PUSH` 之后是通过 `SUB` 操作分配局部变量空间吗？

**完全正确！**

在函数序言（Prologue）中，<span style="color:#FF0000; background:#00FF80; border:1px solid #FF00FF;">执行完 `PUSH` 保存完必要的寄存器后，紧接着的动作通常就是使用 `SUB` 指令来为局部变量圈地盘。</span>

- **底层原理：** 因为 ARM 架构的堆栈是“向下生长”（从高地址向低地址延展）的，所以用减法指令（如 `SUB sp, sp, #4`）让栈指针 `sp` 继续向下移动，就相当于在栈内存里强行挖出了一块新的空地。
- **代码实例印证：** 在资料展示的 `add` 函数汇编代码中，紧跟在 `PUSH {r0, r1, lr}` 之后的指令就是 `SUB sp, sp, #4`。这条指令的作用正是为函数内部的局部变量 `sum` 分配 4 个字节的专属存储空间。
- **后续使用：** 空间分配好后，编译器就会利用相对于 `sp` 的偏移量去访问这块空间。例如执行计算后，利用 `STR r0, [sp, #0]` 将运算结果存入刚才用 `SUB` 挖出来的这 4 个字节的局部变量内存中。如果在后续的逻辑中不再需要这块空间了，函数会在结束时使用 `ADD sp, sp, #4` 将指针移回去，从而实现空间的释放。
