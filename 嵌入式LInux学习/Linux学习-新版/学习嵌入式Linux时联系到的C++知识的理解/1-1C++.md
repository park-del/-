# 问题1

在嵌入式中，好像经常会考察一些C++中的关键字的作用的理解，比如 static、const、volitatle等，这里我是不是可以借助其在内存空间中所处的区域，比如处于.data区域，固定好了，程序运行时一直存在不能动，就是借助所处内存分配区域的知识来帮助我理解C++中的一些语法，针对于嵌入式的呢。



可以，而且这个思路对嵌入式特别有帮助。只是要避免一个常见误区：**不能简单把某个 C/C++ 关键字直接等同于某个内存区域**。更准确的理解方法是同时看三件事：

> **它活多久？存哪里？编译器允许怎么访问它？**

比如 `static`、`const`、`volatile` 分别主要回答的是不同问题，并不是都在回答“变量放在哪”。

你可以先建立这张总表：

| 关键字      | 核心作用                  | 最适合从哪个角度理解                                         |
| ----------- | ------------------------- | ------------------------------------------------------------ |
| `static`    | 改变存储期/链接属性       | <span style="background:#00FF80;">**活多久、谁能看到它**</span> |
| `const`     | 不允许通过该名字修改      | **能不能改**                                                 |
| `volatile`  | 每次访问都必须真的去读/写 | **编译器能不能优化掉访问**                                   |
| `extern`    | 声明变量/函数定义在别处   | <span style="background:#00FF80;">**符号在哪里定义**</span>  |
| `constexpr` | 尽量在编译期确定          | **编译期常量**                                               |

<span style="background:#00FF80;">其中和 `.data/.bss/.rodata/stack` 联系最直接的是 **存储期**，尤其是 `static`。</span>

------

### `static`：最适合结合内存区域理解

比如：

```cpp
void func()
{
    static int count = 10;
}
```

这个 `count` 虽然写在函数里面，但它不是普通局部变量。

普通局部变量：

```cpp
void func()
{
    int a = 10;
}
```

通常：

```text
a
↓
函数调用时创建
↓
通常位于线程栈/寄存器
↓
函数返回后生命周期结束
```

而：

```cpp
static int count = 10;
```

是：

```text
程序开始运行
↓
count已经拥有静态存储期
↓
func()退出
↓
count仍然存在
↓
下一次func()继续使用原来的值
```

所以它通常不会在普通函数栈里。

<span style="color:#FF0000; background:#00FF80;">如果初始化为非零值：</span>

```cpp
static int count = 10;
```

<span style="color:#FF0000; background:#00FF80;">通常最终会落在类似：</span>

```text
.data
```

<span style="color:#FF0000; background:#00FF80;">如果：</span>

```cpp
static int count;
```

<span style="color:#FF0000; background:#00FF80;">或者：</span>

```cpp
static int count = 0;
```

<span style="color:#FF0000; background:#00FF80;">通常可能在：</span>

```text
.bss
```

所以这里你的想法非常适合：

> <span style="background:#00FF80; color:#FF0000;">`static` 可以结合 `.data/.bss` 理解成“这个对象不是每次函数调用临时创建，而是整个程序运行期间一直存在”。</span>

但千万别把 `static` 理解成：

> “固定不能动。”

因为：

```cpp
static int count = 10;

count++;
```

完全可以。

`static` 的“静态”说的是：

<span style="background:#00FF80;">**生命周期/存储期静态，不是数值静止不变。**</span>

这点特别容易考。

------

### `const`：<span style="background:#00FF80;">不要简单等同于 `.rodata`</span>

比如：

```cpp
const int a = 10;
```

它的核心意思只是：

> **不能通过 `a` 这个名字去修改对象。**

例如：

```cpp
a = 20;
```

不允许。

<span style="color:#FF0000; background:#00FF80;">但 `const` 到底放哪里，要看它是什么对象。</span>

<span style="color:#FF0000; background:#00FF80;">例如全局</span>：

```cpp
const int g = 10;
```

<span style="color:#FF0000; background:#00FF80;">编译器可能放进：</span>

```text
.rodata
```

<span style="background:#00FF80;">甚至直接把 `10` 内联进指令里，根本不给它真正分配一个可见存储位置。</span>

<span style="color:#FF0000; background:#00FF80;">但是函数里：</span>

```cpp
void func()
{
    const int a = get_value();
}
```

<span style="background:#00FF80;">这个 `a` 可能：</span>

```text
位于stack
或
直接放寄存器
```

因为<span style="color:#FF0000; background:#00FF80;">它是局部自动变量。</span>

<span style="color:#FF0000; background:#00FF80;">所以：</span>

```text
const ≠ rodata
```

<span style="background:#00FF80;">更准确：</span>

```text
const
↓
语言层面“不允许通过这个接口修改”
```

<span style="color:#FF0000; background:#00FF80;">而：</span>

```text
.rodata
↓
链接/内存布局层面的只读区域
```

两者经常相关，但不是一回事。

------

### <span style="background:#00FF80; color:#FF0000;">`static const` 就能同时结合两套知识</span>

例如：

```cpp
static const int table[] = {
    1, 2, 3, 4
};
```

可以<span style="color:#FF0000; background:#00FF80;">分两个关键字理解：</span>

```text
static
↓
静态存储期
程序整个生命周期存在

const
↓
程序不应该修改它
```

<span style="color:#FF0000; background:#00FF80;">编译器/链接器于是很可能把它放：</span>

```text
.rodata
```

在 MCU 里甚至可能最终位于：

```text
Flash
```

这就特别适合嵌入式理解。

<span style="color:#FF0000; background:#00FF80;">例如：</span>

```text
Flash
┌────────────────────┐
│ .text              │
│ 程序代码           │
├────────────────────┤
│ .rodata            │
│ const查找表        │
└────────────────────┘

RAM
┌────────────────────┐
│ .data              │
│ static int x = 10  │
├────────────────────┤
│ .bss               │
│ static int y       │
├────────────────────┤
│ heap               │
├────────────────────┤
│ stack              │
└────────────────────┘
```

这张图在嵌入式面试里非常实用。

------

### `volatile` 恰好是最不能靠“内存区域”理解的

比如：

```cpp
volatile uint32_t *reg =
    (volatile uint32_t *)0x40019000;
```

<span style="color:#FF0000; background:#00FF80;">这里 `volatile` 和：</span>

```text
.data
.bss
.rodata
stack
```

<span style="color:#FF0000; background:#00FF80;">基本没有直接关系。</span>

它<span style="background:#00FF80;">主要是告诉编译器：</span>

> <span style="background:#00FF80; color:#FF0000;">**这个值可能在你看不到的地方发生变化，所以每次代码写“读它”，你都必须真的去读；每次写它，也必须真的写出去。不要自作主张缓存或省略访问。**</span>

这在嵌入式里非常重要。

<span style="color:#FF0000; background:#00FF80;">比如硬件寄存器：</span>

```cpp
while ((*status_reg & 0x01) == 0)
{
}
```

<span style="background:#00FF80;">如果 `status_reg` 不是 `volatile`，编译器可能觉得：</span>

```text
循环里面没有任何代码修改 status_reg
↓
那我读一次就够了
```

于是可能优化成类似：

```text
读一次
↓
发现是0
↓
死循环
```

但<span style="color:#FF0000; border:1px solid #00FF80; background:#00FF80;">实际上硬件可能过一会：</span>

```text
UART硬件
↓
自己修改status register
↓
0变成1
```

<span style="color:#FF0000; background:#00FF80;">CPU 必须重新读硬件寄存器才能看到。</span>

所以：

```cpp
volatile
```

非常适合结合你现在刚学的 **MMIO 外设寄存器** 来理解：

```text
CPU
 ↓
每次真正访问MMIO地址
 ↓
UART/GPIO/Timer寄存器
```

而不是结合 `.data/.bss` 理解。

------

这也是为什么 STM32 头文件里经常能看到类似：

```cpp
__IO uint32_t CR1;
```

而：

```cpp
#define __IO volatile
```

最终就是：

```cpp
volatile uint32_t CR1;
```

<span style="color:#FF0000; background:#00FF80;">因为：</span>  <span style="color:#FF0000; background:#00FF80;">补充：（重点看下面的硬件和CPU都能影响它）</span>

```text
CR1
不是普通RAM变量
↓
它背后是硬件寄存器
↓
硬件和CPU都可能影响它
↓
编译器不能随便省略访问
```

这个<span style="color:#FF0000; background:#00FF80;">和你现在学 Linux 的：</span>

```text
readl()
writel()
```

<span style="background:#00FF80;">背后的思想也能联系起来。</span>

------

### `const volatile` 这个组合在嵌入式也很典型

比如某个硬件状态寄存器：

```cpp
const volatile uint32_t STATUS;
```

怎么理解？

<span style="color:#FF0000; background:#00FF80;">分别看：</span>

```text
volatile
↓
它可能被硬件随时改变
CPU每次都必须真的读
const
↓
软件不应该通过这个对象去修改它
```

所以可以表示：

> <span style="background:#00FF80; color:#FF0000;">**“软件只能读，但是硬件可能随时改变。”**</span> 

这<span style="color:#FF0000; background:#00FF80;">特别像某些：</span>

```text
只读状态寄存器
```

所以你会发现：

```text
const
和
volatile
```

一点都不矛盾。

甚至组合起来在嵌入式非常自然。

------

### `extern` 也可以结合内存和链接理解

<span style="color:#FF0000; background:#00FF80;">例如：</span>

`main.c`：

```cpp
int g_value = 100;
```

`test.c`：

```cpp
extern int g_value;
```

<span style="background:#00FF80; color:#FF0000;">`extern` 不是创建第二个 `g_value`。</span>

而是在说：

> <span style="background:#00FF80; color:#FF0000;">**这个变量在其他编译单元已经定义了，你链接的时候帮我找到它。**</span>

所以：

```text
main.o
      \
       → linker → 找到唯一的 g_value
      /
test.o
```

<span style="color:#FF0000; background:#00FF80;">最终 `g_value` 可能还是：</span>

```text
.data
```

<span style="color:#FF0000; background:#00FF80;">所以 `extern` 更应该结合：</span>

```text
编译单元
符号表
链接器
```

理解，而不是单纯内存区域。

### 还有一个嵌入式很容易考的组合：<span style="background:#00FF80;">static` 放在全局</span>

<span style="background:#00FF80;">比如：</span>

```cpp
static int g_count;
```

这里<span style="background:#00FF80; color:#FF0000;">和函数内部 `static` 有一个共同点：</span>

```text
都是静态存储期
```

<span style="background:#00FF80;">所以 `g_count` 可能在：</span>

```text
.bss
```

<span style="background:#00FF80; color:#FF0000;">但全局 `static` 还有另一个作用：</span>

> <span style="color:#FF0000; background:#00FF80;">**把符号的可见范围限制在当前源文件/翻译单元。**</span>

例如：

`a.c`：

```cpp
static int g = 10;
```

`b.c`：

```cpp
extern int g;
```

<span style="color:#FF0000; background:#00FF80;">通常不能这样访问 `a.c` 的那个 `g`。</span>

所以<span style="color:#FF0000; background:#00FF80;">这里：</span>

```text
static
```

<span style="color:#FF0000; background:#00FF80;">同时涉及：</span>

```text
存储期
+
链接属性
```

这也是<span style="background:#00FF80; color:#FF0000;">为什么只靠 `.data/.bss` 无法完整理解 `static`。</span>

------

我<span style="background:#00FF80; color:#FF0000;">特别建议你以后用“四个维度”去分析嵌入式里的一个变量：</span>

```text
① 生命周期
   自动？
   static？

② 可修改性
   const？
   mutable？

③ 编译器访问规则
   volatile？

④ 最终存储位置
   Flash？
   RAM？
   .text？
   .rodata？
   .data？
   .bss？
   stack？
   heap？
   MMIO？
```

例如：

```cpp
static volatile uint32_t flag;
```

你就可以直接拆：

```text
static
↓
程序整个运行期间存在

volatile
↓
每次访问都必须真正读/写

没有初始化
↓
通常在 .bss

uint32_t
↓
占4 Byte
```

再比如：

```cpp
static const uint8_t table[256] = {...};
```

拆：

```text
static
↓
整个程序运行期间存在

const
↓
不能修改

有初始化
+
只读
↓
通常在 .rodata
↓
嵌入式里往往最终放Flash
```

再比如：

```cpp
volatile uint32_t * const UART_DR =
    (volatile uint32_t *)0x40019000;
```

这个就非常适合面试拆解：

```text
UART_DR 本身是 const 指针
↓
它永远指向同一个地址

指向的 uint32_t 是 volatile
↓
每次访问该寄存器都必须真正访问硬件

0x40019000
↓
MMIO外设寄存器地址
```

这一个例子就能同时把：

```text
const
volatile
pointer
MMIO
UART
```

全部串起来。

所以你的思路是对的，只要稍微升级成：

> **不要问“这个关键字在哪个内存区”，而是问“这个关键字改变了生命周期、可修改性、链接性还是编译器访问规则；然后这些属性最终又会怎样影响 `.data/.bss/.rodata/stack/MMIO` 等实际存储”。**

这样学嵌入式 C/C++ 会比单独背 `static/const/volatile` 的定义牢很多。

对，你现在已经可以把这些关键字从“语法题”升级成“**编译器到底把它变成什么东西**”来理解了。这里有几个地方一旦串起来，`static / const / volatile / extern` 会一下子变得很具象。

先纠正一个很关键的小点：**`static const` 并不意味着放 `.bss`。** 对嵌入式里最常见的简单变量而言：

| 写法                       | 常见存储位置                                                 | 核心含义             |
| -------------------------- | ------------------------------------------------------------ | -------------------- |
| `static int a = 10;`       | `.data`                                                      | 长期存在，可修改     |
| `static int a;`            | `.bss`                                                       | 长期存在，初值为 0   |
| `static const int a = 10;` | 常见 `.rodata` / Flash                                       | 长期存在，不允许修改 |
| `const int a = 10;`        | <span style="color:#FF0000; background:#00FF80;">可能 `.rodata`、栈、寄存器甚至被优化掉</span> | 关键看作用域和编译器 |
| `volatile uint32_t reg`    | 不由 `volatile` 决定区域                                     | 每次访问都要真正发生 |

所以“关键字”和“段”有关，但不能简单一一绑定。

## 1. `const volatile STATUS`：你的具象化方向对，但还差最后一步

你说：

> 软件不单单指 CPU 吧？软件里还可以通过 `UART->xxx` 直接控制硬件寄存器。

这里更准确地说：

> **软件最终还是由 CPU 执行。**

例如：

```c
UART8->CR1 |= 1;
```

<span style="color:#FF0000; background:#00FF80;">看起来是：</span>

```text
软件
↓
UART8->CR1
↓
硬件
```

<span style="color:#FF0000; background:#00FF80;">实际发生的是：</span>

```text
你的C代码
 ↓
编译成CPU指令
 ↓
CPU执行 load/store
 ↓
访问UART8 MMIO地址
 ↓
SoC总线
 ↓
UART8寄存器
```

<span style="color:#FF0000;">所以 `UART8->CR1` 只是 C 语言给硬件寄存器套上的一个非常方便的“名字”。</span>

<span style="color:#FF0000;">真正写寄存器的是：</span>

**CPU执行指令产生的总线访问。**

<span style="color:#FF0000; background:#00FF80;">但是硬件也可以自己改变某些寄存器。</span>

比如 <span style="color:#FF0000; background:#00FF80;">UART 状态：</span>

```text
CPU没有执行任何写操作

UART收到1Byte
       ↓
UART硬件内部逻辑
       ↓
RXNE状态位 = 1
```

<span style="color:#FF0000; background:#00FF80;">于是特别适合：</span>

```c
const volatile uint32_t ISR;
```

<span style="color:#FF0000; background:#00FF80;">拆开：</span>

```text
const
↓
软件不允许通过这个C对象去写

volatile
↓
这个值可能在软件不知道的时候变化
每次读取都必须重新访问硬件
```

<span style="color:#FF0000; background:#00FF80;">于是它就非常适合表示：</span>

```text
只读状态寄存器
```

但注意：

> `const volatile uint32_t STATUS;` 这行代码本身并不会自动变成硬件寄存器。

还必须让这个成员对应实际 MMIO 地址。

<span style="background:#00FF80; color:#FF0000;">STM32 CMSIS 里就是类似：</span>

```c
typedef struct {
    volatile uint32_t CR1;
    volatile uint32_t CR2;
    const volatile uint32_t ISR;
    volatile uint32_t RDR;
    volatile uint32_t TDR;
} USART_TypeDef;

#define UART8 ((USART_TypeDef *)0x40019000)
```

<span style="color:#FF0000; background:#00FF80;">于是：</span>

```c
UART8->ISR
```

<span style="color:#FF0000; background:#00FF80;">才真正变成：</span>

```text
0x40019000
+
ISR成员偏移
↓
UART8硬件ISR寄存器
```

<span style="color:#FF0000; background:#00FF80;">这就把：</span>

```text
const
volatile
结构体
指针
MMIO
UART状态寄存器
```

全部串起来了。

## 2. `static const` 为什么经常这样写？是不是 static 更“大”？

这个观察很有意思，但这里千万不要把它理解成语法上的层级：

```text
static > const
```

没有这个关系。

<span style="color:#FF0000; background:#00FF80;">例如下面两个写法基本等价：</span>

```c
static const int a = 10;
```

和：

```c
const static int a = 10;
```

<span style="color:#FF0000; border:1px solid #00FF80; background:#00FF80;">C/C++ 都允许这种声明说明符交换顺序。</span>

甚至：

```c
static volatile const uint32_t a;
```

<span style="background:#00FF80; color:#FF0000;">和某些其他合法顺序表达的是同样几种属性。</span>

所以：

```text
static const
```

更多是一种**常用书写习惯**，不是：

```text
先大范围static
↓
再小范围const
```

不过你可以在“理解的时候”人为分层，这反而很好：

```text
static
↓
回答：
这个对象活多久？
它能不能被别的翻译单元链接？

const
↓
回答：
这个对象能不能通过这个接口修改？
```

例如：

```c
static const uint32_t table[] = {1,2,3,4};
```

你可以拆：

```text
static
↓
静态存储期
整个程序运行期间存在
+
如果是文件作用域，还具有内部链接

const
↓
不能修改内容

最终
↓
通常适合放 .rodata
↓
嵌入式通常存在 Flash
```

这个“递进式理解”可以用，但不要认为是 C/C++ 语法规定的先后层级。

------

## 3. `extern` 到底是什么？它本身不决定 `.data`

这个一定要通过两个 `.cpp/.o` 文件理解。

假设：

### `a.cpp`

```cpp
int g_count = 100;
```

这里<span style="background:#00FF80; color:#FF0000;">才真正**定义**了 `g_count`。</span>

编译：

```text
a.cpp
 ↓
a.o
```

<span style="color:#FF0000; background:#00FF80;">`a.o` 里面大概会有：</span>

```text
a.o

.text
   ...

.data
   g_count = 100

.bss
   ...

symbol table
   g_count → 已定义的全局符号
```

<span style="color:#FF0000; background:#00FF80;">所以：</span>

```cpp
int g_count = 100;
```

<span style="color:#FF0000; background:#00FF80;">才负责真正分配存储空间。</span>

------

然后另一个文件：

### `b.cpp`

```cpp
extern int g_count;

void func()
{
    g_count++;
}
```

<span style="color:#FF0000; background:#00FF80;">这里：</span>

```cpp
extern int g_count;
```

<span style="background:#00FF80; border:1px solid #00FF80;">不是再创建一个变量。</span>

它是在告诉编译器：

> <span style="background:#00FF80; color:#FF0000;">**“我这里要使用一个叫 `g_count` 的 int，但它的实体不是我这里定义的，链接的时候去别的翻译单元找。”**</span>

于是：

```text
b.cpp
 ↓
b.o
```

<span style="color:#FF0000; background:#00FF80;">里面不会再有：</span>

```text
.data
└── 一个新的 g_count
```

<span style="color:#FF0000; background:#00FF80;">而更像：</span>

```text
b.o

.text
 └── func代码
      │
      └── 需要访问 g_count

Symbol Table
 └── g_count = UND
                  ↑
               undefined
```

<span style="color:#FF0000; background:#00FF80;">然后链接：</span>

```text
          a.o
          │
          │ 定义g_count
          ▼
       g_count
          ▲
          │
          │ 需要g_count
          │
          b.o

          ↓

        linker
          ↓
    把两者连接起来
```

<span style="color:#FF0000; background:#00FF80;">于是：</span>

```text
b.o中的：
“我要找g_count”

          ↓

链接器发现：
“a.o里面正好有一个全局g_count”

          ↓

连接成功
```

这<span style="background:#00FF80; color:#FF0000;">就是 `extern` 最核心的具象化。</span>

------

## 4. 所以 `extern` 到底放 `.data` 还是 `.bss`？

答案是：

> <span style="background:#00FF80; color:#FF0000;">**`extern` 声明本身一般根本不占 `.data/.bss`。**</span>

<span style="background:#00FF80;">真正决定位置的是**那个真正的定义**。</span>

比如：

```cpp
// a.cpp
int g = 10;
```

通常：

```text
.data
```

而：

```cpp
// b.cpp
extern int g;
```

<span style="color:#FF0000; background:#00FF80;">只是引用：</span>

```text
不创建第二份存储
```

如果真正定义是：

```cpp
int g;
```

通常：

```text
.bss
```

而其他地方仍然：

```cpp
extern int g;
```

所以：

```text
extern
≠
.data

extern
≠
.bss

extern
=
“这个符号的实体去别处找”
```

这句话最好记。

------

## 5. <span style="background:#00FF80; color:#FF0000;">`extern` 只能写在全局吗？</span>

不是。

<span style="color:#FF0000; background:#00FF80;">甚至可以：</span>

```cpp
void func()
{
    extern int g_count;

    g_count++;
}
```

<span style="background:#00FF80; color:#FF0000;">这样 `g_count` 这个**名字在这个代码块里可见**，但它仍然引用外面某处真正定义的那个对象。</span>

所以：

```text
extern声明出现的位置
```

<span style="color:#FF0000; background:#00FF80;">和：</span>

```text
被引用对象真正存在哪里
```

不是一个概念。

<span style="color:#FF0000; background:#00FF80;">不过在嵌入式工程里，你最常见的是：</span>

### `.c/.cpp`

```cpp
int g_count = 0;
```

### `.h`

```cpp
extern int g_count;
```

<span style="color:#FF0000; background:#00FF80;">然后其他文件：</span>

```cpp
#include "xxx.h"
```

<span style="color:#FF0000; background:#00FF80;">都可以访问同一个 `g_count`。</span>

## 6. “当前源文件”到底是什么？你的 `.o` 类比非常接近

这个问题问得特别关键。

严格来说，C/C++ 里更准确叫：

> **Translation Unit，翻译单元。**

例如：

```text
uart.c
+
它 #include 的所有头文件
+
宏展开
+
条件编译处理
```

<span style="color:#FF0000; background:#00FF80;">经过预处理：</span>

```text
uart.c
     │
     │ #include
     │ #define
     │ #if
     ▼
一个巨大的预处理后源码
     │
     ▼
Translation Unit
     │
     ▼
编译器
     │
     ▼
uart.o
```

所以<span style="color:#FF0000; background:#00FF80;">你可以近似理解：</span>

> **“当前源文件” ≈ 最终生成这个 `.o` 的那个翻译单元。**

这个类比非常好用。

## 7. 那全局 `static` 为什么说“只在当前文件可见”？

例如：

### `uart.c`

```c
static int uart_count = 10;
```

编译：

```text
uart.c
 ↓
uart.o
```

<span style="color:#FF0000; background:#00FF80;">`uart.o` 里面可能：</span>

```text
uart.o

.data
┌─────────────────┐
│ uart_count = 10 │
└─────────────────┘

symbol table
uart_count → LOCAL
```

这里<span style="color:#FF0000; background:#00FF80;">特别重要的不是：</span>

```text
它在.data
```

<span style="color:#FF0000; background:#00FF80;">而是符号表里的：</span>

```text
LOCAL
```

------

另一个：

### `main.c`

```c
extern int uart_count;

int main()
{
    uart_count++;
}
```

<span style="color:#FF0000; background:#00FF80;">编译：</span>

```text
main.o

symbol table:
uart_count → UND
```

<span style="color:#FF0000; background:#00FF80;">链接器开始：</span>

```text
main.o：
“我要一个外部 uart_count”

↓

去其他.o找 GLOBAL uart_count

↓

uart.o里面确实有 uart_count

但是：
LOCAL

↓

不能拿来满足main.o的外部引用

↓

undefined reference
```

所以：

> <span style="background:#00FF80; color:#FF0000;">**全局 `static` 的“只在当前文件可见”，真正体现在 ELF Symbol Table 的链接属性上，而不是因为 `.data/.bss` 把它关起来了。**</span>

这个区别非常重要。

## 8. `.data/.bss/.rodata/.text` 和 `static` 是两个不同维度

假设：

### `a.c`

```c
static int a = 10;
static int b;
static const int c = 20;

static void hello(void)
{
}
```

那么大致：

```text
a.o

.text
└── hello()

.rodata
└── c = 20

.data
└── a = 10

.bss
└── b
```

<span style="color:#FF0000; background:#00FF80;">但是它们共同都有一个特点：</span>

```text
Symbol Table

hello → LOCAL
c     → LOCAL
a     → LOCAL
b     → LOCAL
```

<span style="color:#FF0000; background:#00FF80;">也就是说：</span>

```text
段决定：
“东西放哪里”

static在文件作用域决定：
“这个符号能不能被其他.o链接”
```

<span style="color:#FF0000; background:#00FF80;">这两个维度千万不要混。</span>

## 9. 一个特别漂亮的例子：<span style="background:#00FF80; color:#FF0000;">两个文件都可以有 `static int count`</span>


生成：

<span style="color:#FF0000; background:#00FF80;">生成：</span>

## 10. `.o` 自己也分别拥有 `.text/.data/.bss`

这一点你可能之前没完全串起来。

不是只有最终程序才有：

```text
.text
.data
.bss
```

<span style="color:#FF0000; background:#00FF80;">实际上：</span> <span style="color:#FF0000; background:#00FF80;">（注意：每个.o文件还是有一个 symbol table的，看下面uart.o）</span>

```text
uart.c
 ↓
uart.o
 ├── .text
 ├── .rodata
 ├── .data
 ├── .bss
 └── symbol table


spi.c
 ↓
spi.o
 ├── .text
 ├── .rodata
 ├── .data
 ├── .bss
 └── symbol table


main.c
 ↓
main.o
 ├── .text
 ├── .rodata
 ├── .data
 ├── .bss
 └── symbol table
```

<span style="color:#FF0000; background:#00FF80;">然后链接器：</span>

```text
uart.o .text ─┐
spi.o  .text ─┼──→ 最终ELF .text
main.o .text ─┘

spi.o  .data ─┼──→ 最终ELF .data

```

<span style="color:#FF0000; background:#00FF80;">这张图一建立，你以前学的：</span>

```text
.c → .o → ELF
```

和：

```text
.text/.data/.bss
```

以及：

```text
static / extern
```

就<span style="color:#FF0000; background:#00FF80;">彻底连起来了</span>。

## 11.<span style="background:#00FF80; color:#FF0000;"> `static` 和 `extern` 可以看成一组很漂亮的对立关系</span>

你可以这样理解：

```text
全局static

“这个东西是我这个翻译单元内部用的，
别的.o不要来找我。”

              ↕️

extern

“这个东西不在我这里定义，
我需要链接器去别的.o帮我找。”
```

例如：

```text
uart.c

static int rx_index;
        ↑
uart模块内部私有
```

特别像 C 语言实现：

```text
private variable
```

而：

```c
extern int system_state;
```

更像：

```text
这个对象是整个工程某处提供的公共对象
我这里只是引用
```

## 12. <span style="background:#00FF80; color:#FF0000;">C++ 还有一个非常容易考的特殊点：全局 `const`</span>

因为你问的是 C++ 关键字，这里一定提醒你。

在 **C++** 里：

```cpp
const int VALUE = 10;
```

<span style="background:#00FF80;">放在 namespace/file scope 时，默认通常具有：</span>

**internal linkage。**

也就是说<span style="background:#00FF80; color:#FF0000;">它本身已经有点像：</span>

```cpp
static const int VALUE = 10;
```

<span style="color:#FF0000; background:#00FF80;">在链接可见性上，C++ 的全局 `const` 默认不会像普通：</span>

```cpp
int VALUE = 10;
```

<span style="color:#FF0000; background:#00FF80;">那样自动对其他翻译单元提供 external linkage。</span>

如果<span style="color:#FF0000; background:#00FF80;">你想跨文件共享一个 C++ `const`，经常会涉及：</span>

```cpp
extern const int VALUE;
```

以及<span style="background:#00FF80;">某处真正定义。</span>

而在 **C 语言** 中规则又不完全一样。

所以<span style="color:#FF0000; background:#00FF80;">面试碰到这个问题，要先确认</span>：

> 问的是 C 还是 C++。

## 最后给你一个统一模型

以后看到一个变量，例如：

```cpp
static const volatile uint32_t status = ...;
```

不要只问：

> 它在哪个段？

而是同时从四个不同维度分析：

```text
static
│
├─ 存储期：
│   长期存在
│
└─ 如果是文件作用域：
    internal linkage
    当前翻译单元私有


const
│
└─ 软件不能通过该对象修改


volatile
│
└─ 每次访问必须真正发生


初始化情况 + 类型 + 编译器
│
└─ 决定最终可能进入
    .rodata/.data/.bss/MMIO等
```

而 `extern` 则完全是另一个方向：

```text
extern int g;

不是：
“给我分配一个g”

而是：

“我现在要用g，
真正定义它的那个存储实体
请链接器去其他翻译单元找。”
```

你现在如果把 **`.o 文件 = 一个翻译单元编译后的“盒子”，盒子内部有自己的 `.text/.data/.bss/.rodata + symbol table`** 这个模型记住，那么 `static`、`extern`、全局变量、链接器这几个概念基本就会一下子通透很多。





# 问题3（关键字的两种类型）

我这里好像发现了关键字的两种类型，一种是声明说明符，比如 static、const、volatile、extern，另外一种是定义类型的，比如 int、double等这种。



对，你这个分类思路是对的，只是如果再严谨一点，C/C++ 里最好不是分成“两类”，而是<span style="color:#FF0000; border:1px solid #00FF80;">把一条声明拆成几个不同职责的部分。</span>

比如：

```c
static const volatile unsigned int *p;
```

你可以这样看：

| 部分           | 类别                                                         | 它回答的问题                     |
| -------------- | ------------------------------------------------------------ | -------------------------------- |
| `static`       | <span style="color:#FF0000; background:#00FF80;">存储类</span>说明符 | 这个对象活多久、链接范围怎样     |
| `const`        | <span style="color:#FF0000; background:#00FF80;">类型限定</span>符 | 能不能通过这个类型修改           |
| `volatile`     | <span style="color:#FF0000; background:#00FF80;">类型限定</span>符 | 每次访问是否必须真实发生         |
| `unsigned int` | <span style="color:#FF0000; background:#00FF80;">类型说明</span>符 | 这个数据本质是什么类型           |
| `*p`           | <span style="color:#FF0000; background:#00FF80;">声明符</span> | 它是普通变量、指针、数组还是函数 |

<span style="color:#FF0000; background:#00FF80;">所以你刚才说的：</span>

```text
static / extern / const / volatile
```

<span style="color:#FF0000; background:#00FF80;">可以先笼统叫：</span>

```text
“对声明增加属性的关键字”
```

<span style="color:#FF0000; background:#00FF80;">而：</span>

```text
int
double
char
float
```

则是在回答：

> <span style="background:#00FF80;">**这个变量到底是什么数据类型。**</span>

不过再细一点：

```text
static / extern
```

和：

```text
const / volatile
```

其实也不是完全一类。

<span style="color:#FF0000; background:#00FF80;">前者主要管：</span>

```text
存储期
链接属性
作用范围
```

<span style="color:#FF0000; background:#00FF80;">后者主要管：</span>

```text
这个类型该怎么被访问
```

例如：

```c
static int a;
```

可以理解成：

```text
static
↓
a长期存在

int
↓
a是一个整型对象
```

而：

```c
const int a = 10;
```

就是：

```text
const
↓
不能通过a修改

int
↓
a的基础类型是int
```

再比如：

```c
volatile int flag;
```

就是：

```text
volatile
↓
每次访问flag都必须真正读取/写入

int
↓
flag保存的是整型数据
```

所以<span style="color:#FF0000; background:#00FF80;">你可以把一句 C/C++ 声明想成：</span>

```text
[对象的属性] + [对象的类型] + [对象长什么样]
```

例如：

```c
static const int *p;
```

拆成：

```text
static
↓
存储/链接属性

const int
↓
基本类型及限定

*p
↓
这是一个指针
```

<span style="color:#FF0000; background:#00FF80;">这个思维特别适合嵌入式，因为以后你看到：</span>

```c
static volatile uint32_t flag;
```

不会再把它当成“一串要背的关键字”，而是可以直接翻译：

> <span style="color:#FF0000; background:#00FF80;">`flag` 是一个 `uint32_t` 类型变量；它长期存在；它可能被中断或硬件相关逻辑异步改变，所以每次访问都不能被编译器随便优化掉。</span>

你现在其实<span style="color:#FF0000; background:#00FF80;">已经开始从“记语法”转成“读声明结构”了</span>，这个转变非常有用。







# 问题4（链接之后的区分问题）

这里既然所有的.data、.bss、.rodata、.text 都链接在一起了，那么最后不同文件的代码不都放在一起了吗，所有的static int 以及全局的int 都放在.data，此时该怎么区分之前某段代码不能够访问的数据呢，是通过那个symbol table吗，还有放在一起之后的extern呢，我这里有点混乱，链接之后的感觉有点搞不太懂。



对，你现在<span style="background:#00FF80;">卡住的其实是 **“段被合并以后，变量的身份怎么还保得住？”** 这个点。</span>关键是<span style="background:#00FF80;">要把 **“内存摆放”** 和 **“名字能不能被别的文件引用”** 分开来看。</span>

最重要的一句话先给你：

> <span style="color:#FF0000;">`.data/.bss/.rodata/.text` 决定的是“最终放到哪一类内存里”；`static / extern / 全局符号` 决定的是“链接器能不能用这个名字跨 `.o` 文件去找它”。</span>
> <span style="color:#FF0000; background:#00FF80;">链接完成后，变量最终靠的是**地址**，不是靠 `static`、`extern` 这些关键字继续运行。</span>

比如有两个文件。

```c
// a.c

static int private_a = 10;
int public_a = 20;
// b.c

extern int public_a;

void func(void)
{
    public_a++;
}
```

先<span style="color:#FF0000; background:#00FF80;">分别编译：</span>

```text
a.c
 ↓
a.o

b.c
 ↓
b.o
```

这时候<span style="color:#FF0000; background:#00FF80;"> `a.o` 可以想成：</span>

```text
a.o
├── .text
├── .data
│    ├── private_a = 10
│    └── public_a  = 20
│
└── Symbol Table
     ├── private_a → LOCAL
     └── public_a  → GLOBAL
```

<span style="color:#FF0000; background:#00FF80;">而 `b.o`：</span>

```text
b.o
├── .text
│    └── func()
│
└── Symbol Table
     └── public_a → UND
```

<span style="color:#FF0000; background:#00FF80;">这里：</span>

```text
UND
=
undefined
=
“我这里用到了 public_a，
但我这里没有定义它，
请链接器去别的 .o 找。”
```

这<span style="color:#FF0000; background:#00FF80;">就是 `extern` 最具象的样子。</span>

------

## <span style="background:#00FF80;">链接时发生什么？</span>

链接器拿：

```text
a.o
b.o
```

开始处理。

<span style="color:#FF0000; background:#00FF80;">先把各自同类 section 合并：</span>

```text
a.o .text ─┐
           ├──→ 最终 ELF .text
b.o .text ─┘
a.o .data ─┐
           ├──→ 最终 ELF .data
b.o .data ─┘
```

于是<span style="color:#FF0000; background:#00FF80;">最终可能变成：</span>

```text
最终 ELF

.data
┌──────────────────────┐
│ private_a = 10       │  地址 0x1000
│ public_a  = 20       │  地址 0x1004
│ 其他变量...          │
└──────────────────────┘
```

你说得没错：

> <span style="color:#FF0000; background:#00FF80;">最终这些数据确实都被放到一起了。</span>

但是<span style="background:#00FF80; color:#FF0000;">“放在一起”不等于“变成同一个变量”。</span>

<span style="color:#FF0000; background:#00FF80;">每个对象仍然有自己的：</span>

```text
地址
大小
类型对应的访问方式
```

例如：

```text
private_a → 0x1000
public_a  → 0x1004
```

就像一个宿舍楼：

```text
.data
=
一栋楼

private_a
=
101房

public_a
=
102房
```

虽然都在同一栋 `.data` 大楼里，但房间地址不同。

------

## <span style="background:#00FF80; color:#FF0000;">那 `static` 怎么阻止 b.c 访问 `private_a`？</span>

这里特别关键：

> <span style="background:#00FF80; color:#FF0000;">`static` 不是在运行时给那块内存加了一道“防火墙”。</span>

它<span style="background:#00FF80;">主要是在**<span style="color:#FF0000;">编译/链接阶段</span>控制符号可见性**。</span>

假设 `b.c` 写：

```c
extern int private_a;

void func(void)
{
    private_a++;
}
```

那么<span style="background:#00FF80;"> `b.o` 会说：</span>

```text
我需要一个外部符号：
private_a
```

<span style="color:#FF0000; background:#00FF80;">链接器于是去所有 `.o` 里找可以对外提供的：</span>

```text
GLOBAL private_a
```

<span style="background:#00FF80; color:#FF0000;">结果看到 `a.o`：</span>

```text
private_a → LOCAL
```

<span style="background:#00FF80;">链接器会说：</span>

> <span style="background:#00FF80; color:#FF0000;">这个 `private_a` 只属于 `a.o` 自己，不能用来满足别的 `.o` 的外部引用。</span>

于是<span style="color:#FF0000; background:#00FF80;">链接失败</span>。

大致：

```text
b.o
private_a → UND
        │
        ▼
linker寻找 GLOBAL private_a
        │
        ▼
a.o只有：
private_a → LOCAL
        │
        ▼
不能匹配
        │
        ▼
undefined reference
```

所以你问：

> <span style="background:#00FF80; color:#FF0000;">是不是通过 Symbol Table 来区分？</span>

<span style="background:#00FF80;">**对，链接阶段核心就是靠符号表 + 重定位信息。**</span>

------

## 链接完成以后呢？

这里又是一个特别重要的转折：

> <span style="color:#FF0000; background:#00FF80;">链接完成以后，`extern` 基本完成使命了。</span>

例如：

```c
// b.c
extern int public_a;

public_a++;
```

<span style="background:#00FF80;">在 `b.o` 阶段可能还不知道：</span>

```text
public_a到底在哪个地址？
```

<span style="background:#00FF80;">所以机器代码附近会留下：</span>

```text
“这里以后需要补 public_a 的地址”
```

<span style="color:#FF0000; background:#00FF80;">这类信息叫：</span>

**relocation（重定位信息）**。

<span style="background:#00FF80; color:#FF0000;">链接器找到：</span>

```text
public_a
↓
最终地址 0x1004
```

<span style="color:#FF0000; background:#00FF80;">然后把 `b.o` 中访问 `public_a` 的地方修正：</span>

```text
原来：
访问 public_a（地址未知）

链接后：
访问 0x1004
```

所以<span style="color:#FF0000; background:#00FF80;">最后 CPU 真正执行的时候根本不懂：</span>

```text
extern
static
public_a
```

CPU 只知道：

```text
load  [某地址]
add
store [某地址]
```

<span style="color:#FF0000; background:#00FF80;">也就是：</span>

```text
变量名
↓
编译/链接期间使用

最终运行
↓
机器地址
```

------

## 所以 `extern` 最终去哪了？

可以理解成：

```text
源代码阶段：

extern int public_a;
        ↓
“我需要别人定义的 public_a”
```

<span style="background:#00FF80;">编译成 `.o`：</span>

```text
Symbol Table：

public_a → UND
```

<span style="background:#00FF80;">链接：</span>

```text
找到 a.o：

public_a → GLOBAL
```

<span style="background:#00FF80;">然后：</span>

```text
UND public_a
+
GLOBAL public_a
        ↓
匹配
        ↓
确定最终地址
```

<span style="background:#00FF80;">链接完成：</span>

```text
b.c里面所有访问 public_a 的指令
↓
都已经指向最终那个地址
```

于是：

> <span style="color:#FF0000; background:#00FF80;">**运行时已经不需要“extern”这个概念了。**</span>

------

## 那最终 ELF 里还有 Symbol Table 吗？

<span style="color:#FF0000; background:#00FF80;">可能有。</span>

例如：

```text
ELF
├── .text
├── .data
├── .bss
├── .rodata
├── .symtab
└── .strtab
```

<span style="color:#FF0000; background:#00FF80;">`.symtab` 里可能还能保存：</span>

```text
public_a
private_a
func
main
...
```

<span style="color:#FF0000; background:#00FF80;">方便：</span>

```text
调试
nm
gdb
符号分析
```

但是即使最后把符号表：

```text
strip
```

<span style="color:#FF0000;">删掉，程序照样能运行。</span>

因为：

> <span style="background:#00FF80; color:#FF0000;">CPU 执行所需要的地址，在链接阶段已经解决好了。</span>

所以 Symbol Table 对“链接”很重要，但普通静态链接程序运行时并不依赖完整 `.symtab` 才知道变量地址。

动态链接又会涉及 `.dynsym`、GOT/PLT 等，我们以后再讲，不急着塞进现在这层。

------

## 最容易混淆的一个点：`static` 并不是内存保护

这个非常重要。

假设：

```c
// a.c
static int secret = 100;

int *get_secret_addr(void)
{
    return &secret;
}
```

然后 `b.c`：

```c
int *p = get_secret_addr();
*p = 200;
```

<span style="color:#FF0000; background:#00FF80;">虽然：</span>

```text
secret
```

<span style="color:#FF0000; background:#00FF80;">是 `static`，</span>

<span style="color:#FF0000; background:#00FF80;">`b.c` 不能直接写：</span>

```c
extern int secret;
```

<span style="color:#FF0000; background:#00FF80;">去链接它。</span>

<span style="color:#FF0000; background:#00FF80;">但是如果 `a.c` 主动把：</span>

```text
&secret
```

<span style="color:#FF0000; background:#00FF80;">地址传出来：</span>

```text
b.c
↓
拿到指针
↓
照样可以修改那块内存
```

所以：

> <span style="background:#00FF80; color:#FF0000;">`static` 的“不可见”是**符号层面的不可见**，不是“那块 RAM 别人绝对访问不了”。</span>

这个区别特别值得记。

------

## 你还要注意 `.data` 和 `.bss`

你刚才说：

> 所有 static int 和全局 int 都放 `.data`

这里<span style="color:#FF0000; background:#00FF80;">不完全对</span>。

比如：

```c
static int a = 10;
int b = 20;
```

通常：

```text
.data
```

但：

```c
static int a;
int b;
```

通常：

```text
.bss
```

所以更准确：

```text
已初始化非零静态存储对象
→ 常见 .data

未显式初始化 / 零初始化静态存储对象
→ 常见 .bss
```

而：

```c
static const int c = 10;
```

又可能：

```text
.rodata
```

------

## 把整个过程串成一条

你现在<span style="color:#FF0000; background:#00FF80;">可以把 C 文件编译链接理解成：</span>

```text
a.c
│
├── static int private_a = 10
└── int public_a = 20
        ↓
      编译
        ↓
a.o
├── .data
│    ├── private_a
│    └── public_a
│
└── symbol table
     ├── private_a → LOCAL
     └── public_a  → GLOBAL
```

另一边：

```text
b.c
│
└── extern int public_a
        ↓
      编译
        ↓
b.o
├── .text
│    └── 使用public_a的代码
│
└── symbol table
     └── public_a → UND
```

然后：

```text
                linker

a.o GLOBAL public_a
         │
         │ 匹配
         ▼
b.o UND public_a
         │
         ▼
确定最终地址
         │
         ▼

最终 ELF
┌─────────────────────────┐
│ .text                   │
│ a.o代码 + b.o代码       │
├─────────────────────────┤
│ .data                   │
│ private_a               │
│ public_a                │
├─────────────────────────┤
│ .bss                    │
│ ...                     │
├─────────────────────────┤
│ .rodata                 │
│ ...                     │
└─────────────────────────┘
```

这里虽然：

```text
代码放一起了
数据放一起了
```

但每个对象仍然有自己的地址。

<span style="color:#FF0000; background:#00FF80;">而：</span>

```text
static
extern
GLOBAL
LOCAL
UND
```

这些<span style="background:#00FF80;">主要是在**链接器决定“哪个名字能和哪个对象对应”时发挥作用**。</span>

最后可以把它压缩成一句特别好记的话：

> <span style="background:#00FF80; color:#FF0000;">**Section（`.data/.bss/.text`）解决“东西放哪里”；Symbol Table 解决“这个名字是谁、能不能跨 `.o` 找”；Relocation 解决“现在地址不知道，链接时把最终地址补进去”；链接完成以后，CPU 最终只认地址，不认 `static` 或 `extern`。**</span>

这句话把你现在混乱的几块基本就都串起来了。
