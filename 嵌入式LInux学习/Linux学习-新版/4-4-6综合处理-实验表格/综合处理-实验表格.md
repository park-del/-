## 5. 整个程序被拆成了三个功能

视频实际上逐渐形成了这种结构：

```c
int main(...)
{
    // 打开文件

    while (1)
    {
        read_line(...);

        process_data(...);

        write(...);
    }

    // 关闭文件
}
```

也就是：

```text
① read_line()
   ↓
负责：怎么读


② process_data()
   ↓
负责：怎么处理


③ write()
   ↓
负责：怎么输出
```

<span style="color:#FF0000; background:#00FF80;">这种“**输入 → 处理 → 输出**”的拆法非常重要，以后写嵌入式程序也经常这么干。</span>

## 6. `main()` 为什么需要两个 fd？

程序大概以这种方式运行：

```bash
./process_excel score.csv result.csv
```

所以：

```text
argv[0] = "./process_excel"
argv[1] = "score.csv"
argv[2] = "result.csv"
```

于是需要两个文件描述符：

```text
fd_data
↓
输入文件 score.csv

fd_result
↓
输出文件 result.csv
```

概念上：

```text
score.csv
    │
    │ fd_data
    ▼
  read()
    │
    ▼
处理程序
    │
    │ fd_result
    ▼
  write()
    │
    ▼
result.csv
```

这就是你前面学过的：

```text
当前进程
│
├── fd 3 → score.csv对应struct file
│
└── fd 4 → result.csv对应struct file
```

视频测试时也能看到类似：

```text
data file fd = 3
resultfile fd = 4
```

## 7. 为什么输入文件通常 `O_RDONLY`，输出文件使用 `O_CREAT | O_TRUNC`？

最终的逻辑应该是：

输入：

```c
open(argv[1], O_RDONLY);
```

因为：

> 只需要读 `score.csv`。

输出：

```c
open(argv[2],
     O_RDWR | O_CREAT | O_TRUNC,
     0644);
```

因为：

```text
O_RDWR
→ 要写/可读写

O_CREAT
→ result.csv不存在就创建

O_TRUNC
→ result.csv已经存在就清空旧内容
```

这也把上一节刚学的几个宏真正用起来了。

## 8. `read_line()` 是整节课第一个难点

<span style="color:#FF0000; background:#00FF80;">`read()` 没有“读取一行”这个概念。</span>

它只有：

```c
read(fd, buf, count);
```

<span style="color:#FF0000; background:#00FF80;">所以老师自己实现：</span>

```c
read_line(fd, buf);
```

<span style="color:#FF0000; background:#00FF80;">思路特别朴素：</span>

```text
循环：

read(fd, &c, 1)

↓
每次只读1个字节

不是换行？
↓
buf[i] = c
i++

是换行？
↓
这一行结束
break
```

代码大致：

```c
while (1)
{
    len = read(fd, &c, 1);

    if (len <= 0)
    {
        break;
    }

    if (c != '\n' && c != '\r')
    {
        buf[i] = c;
        i++;
    }
    else
    {
        break;
    }
}

buf[i] = '\0';
```

## 9. 为什么每调用一次 `read(fd, &c, 1)`，都能继续读下一个字符？

这正好和你前几天一直问的：

```text
struct file
↓
f_pos
```

联系起来。

第一次：

```c
read(fd, &c, 1);
```

比如读取：

```text
张
```

实际 UTF-8 会涉及多个字节，这里暂时按“读取一个字节”理解。

成功读 1 字节后：

```text
f_pos += 1
```

下一次：

```c
read(fd, &c, 1);
```

自然接着读下一个字节。

所以：

```text
read
↓
使用当前 f_pos
↓
读取1字节
↓
f_pos + 1

read
↓
再从新的f_pos继续
```

`read_line()` 根本不需要自己调用 `lseek()`。

## 10. 为什么要检查 `'\r'` 和 `'\n'` 两种？

因为这个 CSV 是在 Windows/Excel 环境生成的。

<span style="color:#FF0000; background:#00FF80;">Windows 文本行经常：</span>

```text
\r\n
```

对应十六进制：

```text
0D 0A
```

其中：

```text
\r
= Carriage Return
= 回车
= 0x0D

\n
= Line Feed
= 换行
= 0x0A
```

<span style="color:#FF0000; background:#00FF80;">所以视频后面 `hexdump` 会看到：</span>

```text
... 0d 0a ...
```

<span style="color:#FF0000; background:#00FF80;">代表：</span>

> 一行结束。

------

## 11. 这里其实存在一个很有意思的细节

程序的 `read_line()`：

```c
if (c != '\n' && c != '\r')
```

<span style="color:#FF0000; background:#00FF80;">碰到 `\r` 就结束本次调用。</span>

但是 Windows 一行实际上：

```text
......\r\n
       ↑ ↑
       │ └ 下一字节还是\n
       └ 第一次碰到这里就退出
```

那么下一次 `read_line()`：

```text
一开始
↓
读到 \n
↓
马上结束
↓
返回一个长度0的空行
```

所以后面的主循环里能看到类似：

```c
if (len != 0)
{
    process_data(...);
    write(...);
}
```

也就是说：

> 它把因为 CRLF 导致的“额外空行”跳过去了。

<span style="color:#FF0000;">这是一个教学上能工作、但并不特别漂亮的实现。</span>

<span style="color:#FF0000; background:#00FF80;">更成熟的做法通常是：</span>

```text
读到 '\n' 才认定一行结束
↓
如果前面有 '\r'
↓
把 '\r' 去掉
```

## 12.`read_line()` 返回值怎么设计？

视频里逐渐设计成：

```text
返回 -1
→ 已经到文件结尾，并且一个字节都没读到

返回 0
→ 读到一个空行

返回 >0
→ 这一行实际有多少字节
```

例如：

```c
if (err && i == 0)
{
    return -1;
}
else
{
    return i;
}
```

这样主循环：

```c
len = read_line(fd_data, data_buf);

if (len == -1)
{
    break;
}
```

就知道：

> 文件真正处理完了。

## 13. 为什么最后必须：

```c
buf[i] = '\0';
```

因为 `read()` 只是在读**原始字节**。

例如得到：

```text
张三,90,91,92,,
```

<span style="color:#FF0000; background:#00FF80;">它不会自己帮你加 C 字符串结尾：</span>

```text
\0
```

<span style="color:#FF0000; background:#00FF80;">而之后要使用：</span>

```c
printf
strcpy
sscanf
sprintf
```

<span style="color:#FF0000; background:#00FF80;">这些字符串函数。</span>

<span style="color:#FF0000; background:#00FF80;">所以必须构造成：</span>

```text
张 三 , 9 0 , ... , , \0
                       ↑
                 C字符串结束
```

这和上一节 `read()` 里：

```c
buf[len] = '\0';
```

<span style="color:#FF0000; background:#00FF80;">完全是一个知识点。</span>

## 15. `sscanf()` 在这里特别值得理解

你之前可能熟悉：

```c
scanf(...)
```

<span style="background:#00FF80; color:#FF0000;">它从标准输入解析。</span>

而：

```c
sscanf(...)
```

<span style="color:#FF0000; background:#00FF80;">第一个 `s` 可以理解成：</span>

> <span style="background:#00FF80;">从 **string** 里面扫描。</span>

比如：

```c
char *str = "张三,90,91,92";

sscanf(str,
       "%[^,],%d,%d,%d",
       name,
       &scores[0],
       &scores[1],
       &scores[2]);
```

可以理解成：

```text
字符串：

张三,90,91,92
│    │  │  │
│    │  │  └─ %d
│    │  └──── %d
│    └─────── %d
└──────────── %[^,]
```

------

## 16. `%[^,]` 是什么意思？

这个格式挺重要。

```text
[^,]
```

意思：

> <span style="color:#FF0000; background:#00FF80;">不断读取“不是逗号”的字符。</span>

因此：

```text
张三,90,91,92
↑↑
```

遇到：

```text
,
```

停止。

于是：

```text
name = "张三"
```

然后格式串中的：

```text
,
```

再匹配掉实际 CSV 中的逗号。

随后：

```text
%d
```

读取：

```text
90
```

所以整个：

```c
"%[^,],%d,%d,%d,"
```

实际上就是：

```text
姓名
,
成绩1
,
成绩2
,
成绩3
,
```

## 19.`sprintf()` 又在干什么？

前面的：

```c
sscanf()
```

<span style="color:#FF0000; background:#00FF80;">是：</span>

```text
字符串
↓
拆成变量
```

后面的：

```c
sprintf()
```

<span style="color:#FF0000; background:#00FF80;">正好反过来：</span>

```text
变量
↓
拼成字符串
```

所以这是很好的一对：

```text
sscanf

sprintf
Variables → String
```


得到：

```text
result_buf
↓
"张三,90,91,92,273,A+"
```

然后：

```c
write(fd_result,
      result_buf,
      strlen(result_buf));
```

写入结果文件。

## 21. 为什么后来第一行处理出问题？

这里是后半段非常重要的知识。

老师本来看到第一行：

```text
,语文,数学,英语,总分,评价
```

可能会觉得：

```c
data_buf[0] == ','
```

就可以判断：

> 这是表头。

但是程序发现并不是。

于是：

```bash
hexdump -C score.csv
```

一看开头：

```text
ef bb bf 2c e8 af ad ...
↑ ↑ ↑
```

注意：

```text
2c
```

才是：

```text
','
```

前面居然还有：

```text
EF BB BF
```

------

## 22. `EF BB BF` 是什么？

它是：

> **UTF-8 BOM**

完整名称：

```text
Byte Order Mark
```

字节：

```text
EF BB BF
```

所以文件实际上不是：

```text
2C ...
,
```

开头。

而是：

```text
EF BB BF 2C ...
```

因此：

```c
data_buf[0]
```

实际是：

```text
0xEF
```

不是逗号。

这就是程序之前判断表头失败的原因。

------

## 23. BOM 是“3个字符”吗？

更准确应该说：

> **UTF-8 BOM 是 3 个字节。**

即：

```text
Byte 0 = EF
Byte 1 = BB
Byte 2 = BF
```

它们共同表示一个 BOM 标记。

不要理解成：

```text
三个正常可见字符
```

------

## 24. 为什么 Excel 保存出来会有 BOM？

<span style="color:#FF0000; background:#00FF80;">Windows 上的一些编辑器和 Excel 导出的：</span>

```text
UTF-8 CSV
```

<span style="color:#FF0000; background:#00FF80;">可能在文件最前面加：</span>

```text
EF BB BF
```

<span style="color:#FF0000; background:#00FF80;">主要用于帮助某些软件识别：</span>

> 这是 UTF-8 编码文本。

所以同样都是“UTF-8”，可能有：

```text
UTF-8 with BOM
```

也可能：

```text
UTF-8 without BOM
```

这两个文件开头不一样。

## 26. 不过这个写法是教学版，不是很通用

这一点建议你提前知道。

判断：

```c
data_buf[0] == 0xef
```

然后认为：

> 一定是表头。

只适用于这个实验文件。

因为：

```text
UTF-8无BOM
```

就没有 `EF BB BF`。

而且某个正常数据文件也不应该靠：

```text
第一个字节是不是EF
```

判断是不是 header。

更健壮的做法是：

```text
文件开头有BOM
↓
先统一跳过/删除BOM

然后再正常解析CSV
```

比如：

```text
EF BB BF , 语 文 ...
         ↑
删除BOM后从这里开始
```

这样业务处理就不需要知道 BOM 的存在。

## 28. 一个 CSV 文件从人眼和 CPU 眼里完全不同

你看到：

```text
张三,90,91,92,,
```

CPU/程序看到的其实是一串字节。

比如 ASCII 部分：

```text
',' = 0x2C

'9' = 0x39
'0' = 0x30

'\r' = 0x0D
'\n' = 0x0A
```

<span style="color:#FF0000; background:#00FF80;">中文“张三”采用 UTF-8 后，每个汉字通常又是多个字节。</span>

所以：

```text
人眼：
张三,90

CPU：
```

## 29. 这个程序跟你刚才问的 Page Cache 怎么连起来？

特别巧，你上一轮刚好问了这个。

程序：

```c
read(fd_data, &c, 1);
```

逻辑上：

```text
score.csv
↓
Linux文件系统 / Page Cache
↓
read()
↓
用户空间变量 c
```

而：

```c
write(fd_result, result_buf, ...);
```

则：

```text
用户空间 result_buf
↓
write()
↓
Linux Page Cache
↓
以后writeback
↓
eMMC / SSD / 硬盘
```

所以<span style="color:#FF0000; background:#00FF80;">整个实验从内存空间角度是：</span>

```text
       存储设备
           │
           ▼
      Page Cache
           │
       read()
           │
           ▼
┌──────────────────────┐
│   用户进程空间        │
│                      │
│ data_buf             │
│ ↓                    │
│ process_data         │
│ ↓                    │
│ result_buf           │
└──────────┬───────────┘
           │
        write()
           ▼
      Page Cache
           │
       writeback
           ▼
       存储设备
```

## 30. 还有一个性能问题：为什么现实中不会这样一字节一字节 `read()`？

视频：

```c
read(fd, &c, 1);
```

非常适合教学。

因为容易理解：

```text
一个字符
一个字符
一个字符
↓
遇到换行
```

但是性能上很差。

假设文件：

```text
1 MB
```

每次：

```text
read 1 byte
```

意味着可能进行极大量系统调用。

即使数据都在 Page Cache：

```text
用户态
↓
read syscall
↓
内核态
↓
返回用户态
```

<span style="color:#FF0000; background:#00FF80;">这个切换本身也有开销。</span>

<span style="color:#FF0000; background:#00FF80;">所以现实程序更常见：</span>

```c
read(fd, buf, 4096);
```

<span style="color:#FF0000; background:#00FF80;">或者直接：</span>

```c
fgets()
getline()
```

<span style="color:#FF0000; background:#00FF80;">一次读比较大的一块，然后在用户空间里找换行。</span>

这也正好解释了我们之前说：

> <span style="background:#00FF80; color:#FF0000;">`fread/fgets` 的用户空间 Buffer 为什么能提高性能。</span>

## 31. `read_line()` 还有一个潜在问题：没有长度限制

视频接口：

```c
read_line(int fd, unsigned char *buf);
```

只传了：

```text
buf指针
```

却没告诉函数：

```text
buf最多多大
```

假设：

```c
unsigned char data_buf[1000];
```

但 CSV 某行：

```text
2000字节
```

那么：

```c
buf[i] = c;
i++;
```

会写出：

```text
data_buf[999]
```

之后继续越界。

更安全的接口应该像：

```c
read_line(int fd,
          unsigned char *buf,
          size_t buf_size);
```

然后：

```c
if (i >= buf_size - 1)
{
    // 防止越界
}
```

# 问题1

回车和换行不是一个东西吗，我们平时在键盘上按enter的时候不就是回车换行了吗，还有这里一些C语言或者C++里面的字符串函数如果要使用的话是不是必须这个字符串要以\0结尾呢，为什么呢，如果不是以\0结尾难道不行吗，这些字符串的函数的作用都是什么呢，对这些字符串函数的处理是在这个线程对应的用户空间还是内核空间呢。



对，这几个问题其实是连在一起的，而且你现在正好到了一个很关键的交界点：**“文件里的字节” → “C 字符串” → “用户空间函数处理”**。

先说第一个：**回车 `\r` 和换行 `\n` 不是同一个东西，<span style="background:#00FF80;">只是我们平时按 Enter 时，经常由系统把它们组合成一次“换到下一行”的效果。</span>**

### 1. `\r` 和 `\n` 到底有什么区别？

它们来自早期打字机的两个独立动作：

```text
\r  = Carriage Return
    = 回车
    = 0x0D

\n  = Line Feed
    = 换行
    = 0x0A
```

想象一台老式打字机：

```text
Hello World█
```

<span style="color:#FF0000; background:#00FF80;">执行 `\r`：</span>

```text
█Hello World
```

<span style="background:#00FF80;">只是把“打印头”移回这一行最左边，**没有下移一行**。</span>

<span style="color:#FF0000; background:#00FF80;">执行 `\n`：</span>

```text
Hello World
            ↓
            █
```

<span style="background:#00FF80;">只是往下一行走，理论上横向位置不一定回到最左边。</span>

所以要得到我们今天理解的：

```text
Hello World
█
```

早期需要两个动作：

```text
\r + \n
```

也就是：

```text
CRLF
```

------

### 2. 那为什么我键盘只按一个 Enter？

因为键盘上的 Enter 是一个**逻辑按键**。

你按：

```text
Enter
```

以后，究竟转换成：

```text
\r
```

还是：

```text
\n
```

还是：

```text
\r\n
```

由操作系统、终端、程序或通信协议决定。

最典型的是：

```text
Windows 文本文件：
\r\n
0D 0A

Linux / Unix 文本文件：
\n
0A
```

所以同样在编辑器里你看到：

```text
第一行
第二行
```

底层可能是：

Windows：

```text
第一行 \r \n 第二行
```

Linux：

```text
第一行 \n 第二行
```

所以你说“按 Enter 不就是回车换行吗”，**从用户体验来说可以这么理解**；但从底层字节来说，`CR` 和 `LF` 是两个不同字符。

## 3. C 语言为什么这么依赖 `'\0'`？

这是因为 C 语言对“字符串”的定义本身就是：

> **一串字符 + 最后一个 `'\0'` 结束标记。**

例如：

```c
char str[] = "hello";
```

内存实际上是：

```text
地址      内容

1000      'h'
1001      'e'
1002      'l'
1003      'l'
1004      'o'
1005      '\0'
```

所以 `"hello"` 看起来 5 个字符，但实际上数组至少占：

```text
6 bytes
```

最后：

```text
\0
```

就是：

```text
0x00
```

它的作用不是“显示一个字符”，而是：

> **告诉字符串函数：到这里结束了。**

------

## 4. 为什么非得要 `\0`？不能顺便记一个长度吗？

可以。

<span style="color:#FF0000; background:#00FF80;">但传统 C 字符串选择的设计方式就是：</span>

```text
不单独存长度
↓
靠 '\0' 判断结束
```

比如：

```c
strlen(str);
```

它内部概念上就是：

```c
int len = 0;

while (str[len] != '\0')
{
    len++;
}
```

所以：

```text
h e l l o \0
          ↑
        停止
```

得到：

```text
strlen = 5
```

如果没有 `\0`，它根本不知道：

> “字符串到底在哪里结束？”

------

## 5. 如果没有 `\0` 会怎么样？

例如：

```c
char buf[5];

buf[0] = 'h';
buf[1] = 'e';
buf[2] = 'l';
buf[3] = 'l';
buf[4] = 'o';
```

内存：

```text
h e l l o ? ? ? ? ? ? ? 0
```

然后：

```c
printf("%s", buf);
```

`printf("%s")` 会想：

```text
h → 不是0
e → 不是0
l → 不是0
l → 不是0
o → 不是0
继续读
↓
???
继续
↓
???
继续
↓
直到碰巧遇到0
```

<span style="color:#FF0000; background:#00FF80;">于是可能输出：</span>

```text
hello乱码乱码乱码
```

也可能越界访问，引发程序异常。

在 C/C++ 语言规则里，这属于：

> **未定义行为 Undefined Behavior**

所以不是简单的：

> “没有 `\0` 就少打印一点。”

而是：

> **字符串函数不知道停止位置，会继续访问不属于这个字符串的内存。**

------

## 6. 这正好解释上一节为什么 `read()` 后要手工补 `\0`

例如：

```c
char buf[100];

len = read(fd, buf, 99);
```

假设读到了：

```text
hello
```

`read()` 只负责字节：

```text
buf:

h e l l o
```

它不会自动帮你变成：

```text
h e l l o \0
```

所以如果接下来：

```c
printf("%s", buf);
```

必须：

```c
buf[len] = '\0';
```

于是：

```text
read()
↓
得到原始字节

h e l l o

↓ 手动补

h e l l o \0

↓
现在才是C字符串
```

------

## 7.<span style="background:#00FF80;"> 是不是“所有函数”都要求 `\0`？</span>

不是，这里一定要区分。

### C 字符串函数

通常依赖 `\0`：

```c
strlen()
strcpy()
strcat()
strcmp()
strchr()
strstr()
printf("%s")
```

它们处理的是：

> **C-style string**

所以需要知道字符串结束位置。

------

### <span style="background:#00FF80; color:#FF0000;">按“长度”操作的函数</span>

不一定需要 `\0`。

例如：

```c
write(fd, buf, len);
```

这里你已经明确告诉：

```text
就处理 len 个字节
```

所以：

```text
buf有没有 '\0'
```

对 `write()` 根本没关系。

例如：

```c
char buf[5] = {'h','e','l','l','o'};

write(fd, buf, 5);
```

完全合法。

因为：

```text
write：
从buf开始
明确处理5字节
```

不需要寻找结束符。

同样：

```c
memcpy(dst, src, 100);
memcmp(a, b, 100);
memset(buf, 0, 100);
```

这些都是：

> **按明确字节数处理**

所以不需要 `'\0'`。

------

## 8.<span style="background:#00FF80; color:#FF0000;"> 可以把函数分成两类理解</span>

这个特别值得记：

```text
第一类：字符串型

strlen(str)
strcpy(dst, src)
strcmp(a, b)
printf("%s", str)

↓

不知道字符串长度
↓

靠 '\0' 找终点
```

而：

```text
第二类：内存/字节型

read(fd, buf, 100)
write(fd, buf, 100)
memcpy(dst, src, 100)

↓

你明确告诉它长度

↓

不需要 '\0'
```

## 9. 那常见字符串函数到底都干什么？

你现在先掌握这些就够了：

| 函数        | 英文来源           | 作用                   |
| ----------- | ------------------ | ---------------------- |
| `strlen()`  | string length      | 求字符串长度           |
| `strcpy()`  | string copy        | 复制字符串             |
| `strcat()`  | string concatenate | 拼接字符串             |

## 1. 为什么 `.text/.data/heap` 是线程共享的？

因为多个线程本质上使用的是同一个进程的：

```text
mm_struct
```

也就是同一套用户虚拟地址空间。

比如：

```c
int global = 100;
```

<span style="background:#00FF80; color:#FF0000;">位于：</span>

```text
.data
```

<span style="color:#FF0000; background:#00FF80;">Thread A：</span>

```c
global = 200;
```

<span style="color:#FF0000; background:#00FF80;">Thread B 马上就能看到：</span>

```text
global == 200
```

<span style="color:#FF0000; border:1px solid #330000; background:#00FF80;">因为：</span>

```text
Thread A
      \
       → 同一个 .data
      /
Thread B
```

<span style="color:#FF0000; background:#00FF80;">它们不是各有一份 `.data`。</span>

同理：

```c
malloc(100);
```

<span style="color:#FF0000; background:#00FF80;">申请的是这个进程 heap 中的内存。</span>

Thread A 和 Thread B，只要拿到了指针，都能访问。

## 2. 那为什么每个线程必须有自己的栈？

<span style="color:#FF0000; background:#00FF80;">因为线程的函数调用过程必须互不干扰。</span>

例如：

```c
void threadA()
{
    int a = 10;
    funcA();
}

void threadB()
{
    int b = 20;
    funcB();
}
```

<span style="color:#FF0000; background:#00FF80;">假设两个线程共用一个 stack：</span>

```text
Thread A:
a
返回地址
funcA调用现场

Thread B:
b
返回地址
funcB调用现场
```

<span style="color:#FF0000; background:#00FF80;">两边就会把对方的调用现场踩坏。</span>

所以必须：

```text
Thread A User Stack
独立

Thread B User Stack
独立
```

但这里有一个很重要的细节：

> <span style="background:#00FF80;">**这些线程栈依然位于同一个进程的用户虚拟地址空间里。**</span>

不是：

```text
Thread A有自己的地址空间
Thread B有自己的地址空间
```

而是：

```text
整个Process A虚拟地址空间

┌────────────────────┐
│ .text              │
│ .data/.bss         │
│ heap               │
│ mmap               │
│                    │
│ Thread A Stack     │
│                    │
│ Thread B Stack     │
│                    │
│ Thread C Stack     │
└────────────────────┘
```

所以<span style="color:#FF0000; background:#00FF80;">“独立栈”的意思是：</span>

> <span style="background:#00FF80; color:#FF0000;">给每个线程划一块不同的虚拟内存区域使用。</span>

<span style="color:#FF0000; background:#00FF80;">不是独立地址空间。</span>

```text
User Stack
Kernel Stack
线程控制信息
TLS
调度相关数据
```

所以线程绝对不是：

> “完全不拥有任何资源。”

只是课本说：

> 进程是资源分配基本单位

主要想强调：

> **大量重要资源是以“进程”为共享边界的。**

比如：

```text

文件描述符表
heap
代码
全局变量
```

而不是每创建一个线程就全部复制一份。

## 4. CPU 是不是“分配给线程的资源”？

这里最好换一个说法。

不太准确：

> “线程被分配到 CPU 这个资源。”

更准确：

> **调度器选择一个可运行线程，让它在某个 CPU 核心上执行一段时间。**

CPU 不像：

```text
malloc一块内存
open一个文件
```

那样被某个线程长期“拥有”。

比如单核 CPU：

```text
10:00:00.000
Thread A运行

10:00:00.005
Thread B运行

10:00:00.010
Thread C运行

10:00:00.015
又切回A
```

所以：

```text
CPU
不是永久分给Thread A

而是：

Scheduler
↓
选择Thread A
↓
让A运行一会
↓
切换Thread B
```

这叫：

> **dispatch / scheduling**

所以线程更准确是：

> **CPU 调度和执行的基本实体。**

## 5. 为什么 CPU 调度的是线程，不是进程？

假设一个进程有三个线程：

```text
Process A

Thread 1
Thread 2
Thread 3
```

系统完全可能在 4 核 CPU 上：

```text
CPU0 → Thread 1

CPU1 → Thread 2

CPU2 → Thread 3
```

三个线程同时执行。

如果调度单位只是进程，就很难表达：

> 一个进程内部的多个执行流可以同时运行。

因此现代 OS 一般调度：

```text
thread / task
```

而不是整个进程作为一个不可分割整体。

## 6. 在 Linux 里这个概念更加明显

Linux 内核实际上把线程视为：

```text
task
```

每个线程都有自己的：

```c
struct task_struct
```

里面保存很多：

```text
线程状态
调度优先级
CPU上下文
TID
kernel stack相关
信号状态
...
```

同一进程的多个线程：

```text
task_struct A
task_struct B
task_struct C
```

但是它们可以共享：

```text

fs_struct
sighand_struct
...
```

所以可以想成：

```text
              同一进程

        ┌──────── mm_struct ───────┐
        │ .text/.data/heap/mmap   │
        └───────────┬──────────────┘
                    │共享
        ┌───────────┼───────────┐
        │           │           │
 task_struct A  task_struct B  task_struct C
     Thread A       Thread B       Thread C
```

这已经非常接近 Linux 内核真实模型。

可以把资源分成两类。

### 进程级共享资源

例如：

```text

打开文件
共享库映射

```

线程通常共享。

### 线程级私有状态/资源

例如：

```text

PC
SP
线程ID
调度状态
调度优先级
TLS
部分信号状态
```

线程自己有一份。

所以真实情况其实是：

```text

          ┌──────────┴───────────┐
          │                      │

          │                      │

```

不是“所有资源一刀切”。

## 8. 那能不能说“线程也是某些资源分配的基本单位”？

从直觉上，你可以说：

> **有些资源确实是按线程分配的。**

比如：

```text
thread stack
kernel stack
TLS
调度实体
CPU上下文
```

但是在操作系统术语里，**不建议因此把线程重新称作“资源分配基本单位”**。

因为经典定义是为了突出两件事：

```text
Process
→ resource ownership / resource container

Thread
→ scheduling / execution
```

所以更准确的表达是：

> **线程是 CPU 调度的基本单位，同时线程也拥有一部分私有的执行资源和状态。**

这句话最好。

------

## 9. 再看你说的“CPU也是资源”这个问题

CPU当然可以广义上看作一种计算资源。

但是它的分配方式和内存不一样。

内存：

```text
malloc 1 MB
↓
这1MB可能长期属于这个进程
```

CPU：

```text
调度Thread A
↓
运行2ms

切走

调度Thread B
↓
运行3ms
```

所以可以区分：

```text
空间型资源
↓
Memory / file / address space
↓
更多以进程为共享边界


时间型计算资源
↓
CPU execution time
↓
更多以线程为调度单位
```

这个角度非常好理解。

## 13. 最后把你的理解调整成最准确版本

你原来的想法可以升级成：

> **进程主要是资源拥有和共享的边界，例如虚拟地址空间、代码、数据、heap、文件等；线程是进程内部独立的执行流，是 CPU 调度的基本单位。线程虽然共享所属进程的大部分资源，但为了能够独立运行和独立调度，每个线程仍然拥有自己的用户栈、内核栈、CPU 寄存器上下文、线程 ID、TLS 和调度状态等。CPU 本身不是像内存那样长期分配给线程，而是调度器在运行时不断把 CPU 执行时间分配给不同线程。**

你可以直接记这一张：

```text
Process
│
│ 共享：
│ .text
│ .data/.bss
│ heap
│ mmap
│ files
│
├── Thread A
│   ├ User Stack
│   ├ Kernel Stack
│   ├ Registers
│   ├ PC/SP
│   └ Scheduling state
│
├── Thread B
│   ├ User Stack
│   ├ Kernel Stack
│   ├ Registers
│   ├ PC/SP
│   └ Scheduling state
│
└── Thread C
    ├ User Stack
    ├ Kernel Stack
    ├ Registers
    ├ PC/SP
    └ Scheduling state
```

然后最值得记的两句话就是：

> **进程回答的是：“这些资源属于谁、谁和谁共享？”**

> **线程回答的是：“现在 CPU 到底在执行哪条执行流？”**

把这两个问题分开，你以后再看 Linux 的 `task_struct / mm_struct / files_struct / scheduler` 就会顺很多。

在内核空间的布局中，比如.data、.bss、.rodata、.heap、.stack、.txt，这些中是如何管理进程和线程的呢，对应的PCB和TCB是放在哪个位置中的，还有关于进程线程管理的一些队列，内核栈都是位于哪里的呢。还有一些内存管理的用到的公共数据结构又是位于哪里的呢，以及一些文件管理的数据结构又是位于内核空间的布局中的哪里的呢，我有点混乱，你能够给我弄清楚吗。

另外你写的 `.txt` 应该是：

```text
.text
```

```text
.data
.bss
.heap
.stack
```

而是<span style="color:#FF0000; background:#00FF80;">先分成：</span>

```text
Linux 内核空间

├── ① 内核镜像的静态区域
│      .text
│      .rodata
│      .data
│      .bss

│      ...

       ...
```

这一步特别重要。

## 二、<span style="color:#FF0000; background:#00FF80;">内核自己的 `.text/.rodata/.data/.bss` 是干什么的？</span>

<span style="background:#00FF80; color:#FF0000;">Linux kernel 本身就是一个很大的 C 程序</span>。

所以和普通程序一样：

```text
Kernel Image

.text
.rodata
.data
.bss
```

------

## `.text`

里面主要是：

> <span style="color:#FF0000; background:#00FF80;">Linux 内核函数的机器指令。</span>

例如<span style="color:#FF0000; background:#00FF80;">概念上</span>：

```text
调度代码
进程创建代码
文件系统代码
内存管理代码
系统调用代码
驱动程序代码
```

它们<span style="color:#FF0000; background:#00FF80;">编译以后都属于：</span>

```text
kernel .text
```

所以当你调用：

```c
fork();
```

<span style="color:#FF0000; background:#00FF80;">进入内核后，CPU 真正执行的是：</span>

```text
kernel .text
```

<span style="color:#FF0000; background:#00FF80;">中的相关函数代码。</span>

例如：

```text
用户程序
↓
fork / clone
↓
系统调用
↓
CPU进入内核态
↓
执行 kernel .text 中的进程创建代码
```

## 三、`.rodata`

这里放：

> <span style="background:#00FF80;">内核里只读的静态数据。</span>

例如：

```c
static const char name[] = "Linux";
```

或者某些：

```text
只读表
常量字符串
只读配置数据
```

可能进入：

```text
.rodata
```

------

## 四、`.data`

这里主要放：

> **已经初始化的内核全局变量 / static 变量。**

例如内核代码里：

```c
static int debug_enable = 1;
```

可能进入：

```text
kernel .data
```

------

## 五、`.bss`

这里主要放：

> 零初始化或未显式初始化的内核全局/static变量。

例如：

```c
static int count;

static struct xxx global_obj;
```

如果没有显式非零初始化，可能进入：

```text
kernel .bss
```

## 六、但是 <span style="color:#FF0000; background:#00FF80;">`task_struct` 一般不在 `.data/.bss`</span>

这里就来到你的核心问题了。

<span style="color:#FF0000; background:#00FF80;">Linux 中和你 RTOS 的 TCB 最接近的结构是：</span>

```c
struct task_struct
```

<span style="color:#FF0000; background:#00FF80;">每创建一个线程/task，通常都需要一份：</span>

```text
task_struct
```

假设<span style="color:#FF0000;">系统里运行：</span>

```text
Thread A
Thread B
Thread C
```

那么<span style="color:#FF0000;">可能有：</span>

```text
task_struct A
task_struct B
task_struct C
```

这些<span style="color:#FF0000;">数量是运行过程中变化的。</span>（<span style="color:#FF0000; background:#00FF80;">这也就是静态和动态的含义，.bss、.data、.text、.rodata是属于静态区，在程序装入之后是不会发生变化的，即运行的时候是不会变化的</span>）

所以<span style="color:#FF0000;">显然不适合：</span>

```text
链接时就全部塞进 .bss
```

<span style="color:#FF0000; background:#00FF80;">否则 Linux 怎么知道以后会创建多少进程？</span>

因此通常是：

```text
内核运行
↓
创建新task
↓
从内核动态内存分配器申请
↓
得到 task_struct
```

也就是：

> <span style="background:#00FF80; color:#FF0000;">**`task_struct` 通常是动态分配的内核对象。**</span>

------

## 七、<span style="background:#00FF80; color:#FF0000;">Linux 的 PCB 和 TCB 到底在哪里？</span>

先纠正一下名词。

<span style="color:#FF0000; background:#00FF80;">很多操作系统教材会说：</span>

```text
PCB = Process Control Block
TCB = Thread Control Block
```

但 <span style="background:#00FF80;">Linux 内核中并不是：</span>

```c
struct PCB
struct TCB
```

这样两个很明确的结构。

Linux 的核心是：

```c
struct task_struct
```

<span style="color:#FF0000;">Linux 把：</span>

> <span style="background:#00FF80;">进程和线程都看成 task。</span>

所以：

```text
一个Linux线程
↓
一个 task_struct
```

<span style="color:#FF0000; background:#00FF80;">同一个进程的多个线程：</span>

```text
Process A

Thread 1 → task_struct 1
Thread 2 → task_struct 2
Thread 3 → task_struct 3
```

然后它们通过共享一些对象表现为“属于同一个进程”。

## 八、`task_struct` 从哪里分配？

通常来自：

> **内核 slab/SLUB 对象分配系统。**

你现在可以先把 SLUB 理解成：

> <span style="color:#FF0000; background:#00FF80;">Linux 内核专门用来高效分配“小型内核对象”的内存管理器。</span>

例如：

```text
task_struct
inode
dentry
struct file
mm_struct
files_struct
...
```

很多这类对象都通过：

```text
kmalloc
kmem_cache
slab / SLUB
```

一类机制获得。

所以可以画成：

```text
物理RAM
  ↓
Buddy / Page Allocator
  ↓
提供物理页
  ↓
SLUB
  ↓
切成适合某类对象的小块
  ↓
task_struct
inode
dentry
file
...
```

------

## 九、所以<span style="background:#00FF80; color:#FF0000;"> Linux kernel 并没有一个简单的 `.heap` 区</span>

这是一个特别重要的修正。

<span style="color:#FF0000; background:#00FF80;">普通程序里我们喜欢画：</span>

```text
.text
.data
.bss
heap
...
stack
```

<span style="color:#FF0000; background:#00FF80;">但是内核里不能简单画成：</span>

```text
kernel .text
kernel .data
kernel .bss
kernel heap
kernel stack
```

<span style="color:#FF0000; background:#00FF80;">然后认为所有动态数据都从一块连续的“kernel heap”里 malloc。</span>

<span style="background:#00FF80;">Linux 内核的动态内存管理复杂很多：</span>

```text
Kernel Memory Allocators

Page Allocator
│
├── 分配一页/多页
│
├── 给SLUB提供底层页面
│
└── 给其他子系统提供页

SLUB / slab
│
├── task_struct
├── inode
├── dentry
├── file
└── 各种小对象

kmalloc
│
└── 一般内核动态对象

vmalloc
│
└── 虚拟地址连续、物理页可不连续
```

所以更准确说：

> <span style="color:#FF0000; background:#00FF80;">Linux 有“内核动态内存”，但没有必要把它想成一个单一固定的 `.heap` ELF section。</span>

------

## 十、那内核栈放在哪里？

Linux 中：

> <span style="background:#00FF80; color:#FF0000;">**每个 task/thread 都有自己的 kernel stack。**</span>

例如：

```text
Thread A
├── task_struct A
└── kernel stack A

Thread B
├── task_struct B
└── kernel stack B
```

内核栈<span style="color:#FF0000; background:#00FF80;">也不是：</span>

```text
kernel .stack
```

<span style="color:#FF0000; background:#00FF80;">里面大家共用一块。</span>

而是：

> <span style="background:#00FF80; color:#FF0000;">每创建一个线程，就为它准备自己的内核栈。</span>

概念：

```text
Kernel Dynamic Memory

task_struct A

kernel stack A


task_struct B

kernel stack B


task_struct C

kernel stack C
```

------

## 十一、为什么每个线程都必须有 kernel stack？

<span style="color:#FF0000; background:#00FF80;">因为线程进入内核执行时，需要保存：</span>

```text
内核函数局部变量
函数返回地址
寄存器现场
系统调用执行现场
异常处理现场
```

比如：

```c
read(fd, buf, 100);
```

发生：

```text
Thread A用户态
↓
read系统调用
↓
进入Linux内核
↓
使用 Thread A 的 kernel stack
↓
VFS
↓
文件系统
↓
返回
```

而 Thread B 同时也可能：

```text
Thread B
↓
write系统调用
↓
使用自己的 kernel stack
```

所以两个线程不能共用一个内核栈。

------

## 十二、注意：kernel stack 不是长期数据仓库

这一点和你之前理解 RTOS Task Stack 类似。

<span style="color:#FF0000;">内核栈主要保存：</span>

> <span style="color:#FF0000; background:#00FF80;">当前执行过程中的临时调用现场。</span>

不是：

```text
把 task_struct
files_struct
mm_struct
inode
dentry
都放kernel stack里
```

<span style="color:#FF0000; background:#00FF80;">这些长期数据结构通常在动态内核内存中。</span>

所以：

```text
Kernel Stack
=
“内核函数运行时工作台”
```

而：

```text
task_struct / mm_struct / files_struct
=
长期存在的内核对象
```

------

## 十三、进程相关的数据结构到底在哪里？

我们可以把一个 Linux 进程拆成这样：

```text
Process A
│
├── Thread 1
│    ├── task_struct 1
│    └── kernel stack 1
│
├── Thread 2
│    ├── task_struct 2
│    └── kernel stack 2
│
└── Thread 3
     ├── task_struct 3
     └── kernel stack 3
```

这些线程还共享：

```text

files_struct
fs_struct
sighand_struct
signal_struct
...
```

大致：

```text
            mm_struct
               ▲
      ┌────────┼────────┐
      │        │        │
 task A     task B     task C


           files_struct
               ▲
      ┌────────┼────────┐
      │        │        │
 task A     task B     task C
```

其中这些结构通常都属于：

> <span style="background:#00FF80; color:#FF0000;">**内核动态管理的数据对象。**</span>

## 十四、`mm_struct` 是干什么的？

它是一个非常重要的：

> <span style="color:#FF0000; background:#00FF80;">**进程用户虚拟地址空间描述结构。**</span>

例如：

```text
Process A用户空间

.text
.data
.bss
heap
mmap
stack
```

Linux 内核要记住：

```text
这些虚拟地址区域有哪些？
权限是什么？
页表在哪里？
heap在哪里？
mmap有哪些？
```

这些信息的重要入口之一就是：

```c
struct mm_struct
```

所以：

```text
task_struct
    │
    └── mm
         │
         ▼
      mm_struct
         │
         ├── 地址空间信息
         ├── 页表相关
         └── VMAs等
```

`mm_struct` 通常也是内核动态对象。

------

## 十五、那 VMA 这些结构在哪里？

Linux 中一个进程可能有：

```text
.text VMA
.data VMA
heap VMA
shared library VMA
stack VMA
```

内核会用相应的虚拟内存区域管理结构描述它们。

这些也是：

> **内核中的动态数据结构**

而不是放在用户空间。

所以：

```text
用户空间看到：
.text
heap
stack

内核空间保存：
“这些区域怎么映射”的管理结构
```

------

## 十六、页表在哪里？

页表也属于：

> **内核管理的数据。**

比如：

```text
VA
↓
Page Table
↓
PA
```

页表本身占用物理 RAM。

这些页通常由：

```text
page allocator
```

之类的内核机制分配。

所以：

```text
Page Tables
```

<span style="color:#FF0000; background:#00FF80;">不是：</span>

```text
kernel .data
```

<span style="color:#FF0000; background:#00FF80;">提前全部写好的。</span>

因为：

> <span style="color:#FF0000; background:#00FF80;">进程运行过程中页表不断创建、扩展、释放。</span>

------

## 十七、内存管理的公共数据结构放哪里？

你问这个特别好。

<span style="background:#00FF80; color:#FF0000;">Linux 内存管理自己也需要大量“管理内存的数据”。</span>

比如概念上会有：

```text
物理页描述信息
内存节点信息
zone信息
free lists
slab信息
page allocator状态
vmalloc管理结构
```

这些<span style="background:#00FF80;">根据具体结构不同：</span>

- 有些是**<span style="background:#00FF80;">静态全局数据</span>**，可能在 `.data/.bss`
- 有些是 **<span style="background:#00FF80;">per-CPU 数据</span>**
- 很多是**<span style="background:#00FF80;">启动时或运行时动态分配</span>**
- 有些<span style="background:#00FF80;">直接对应一大片预留 RAM 管理元数据</span>

例如每个物理页通常都需要有一个描述对象，Linux 中典型就是：

```c
struct page
```

概念：

```text
物理Page Frame
      ↕
struct page
```

这样内核才能知道：

```text
这个页是否空闲？
被谁引用？
是不是Page Cache？
是不是匿名页？
引用计数多少？
```

这些描述结构属于：

> 内核自己的管理数据。

------

## 十八、文件管理结构又在哪里？

你之前已经学过：

```text
fd
↓
fdtable
↓
struct file
↓
dentry
↓
inode
```

现在可以把它们放进内核空间：

```text
用户空间

fd = 3
read(3,...)


════════ syscall ════════


内核空间

task_struct
   │
   ▼
files_struct
   │
   ▼
fdtable
   │
   ▼
fd[3]
   │
   ▼
struct file
   │
   ├── f_pos
   ├── flags
   └── path
        │
        ▼
```

## 十九、它们具体是不是在 `.data/.bss`？

绝大多数运行时对象：


```text

dentry
```

```text
CPU1一份
CPU2一份
CPU3一份
```

```text
per-CPU data
```

## 最后给你一个特别好用的判断口诀

## 2. Page Table 为什么是动态的？

比如刚启动时系统里只有：

```text
Process A
Process B
```

后来你运行：

```bash
./hello
```

Linux 创建一个新进程。

这个新进程需要自己的：

```text
虚拟地址空间
↓
页表
↓
VA → PA 映射
```

于是<span style="color:#FF0000; background:#00FF80;"> Linux 就需要动态申请页表所占用的物理页。</span>

例如：

```text
创建 Process C
      ↓
创建 mm_struct
      ↓
建立页表
      ↓
从物理页分配器申请页面
      ↓
用于 Page Table
```

进程退出：

```text
Process C exit
      ↓
页表不再需要
      ↓
释放相关物理页
```

所以：

> <span style="background:#00FF80; color:#FF0000;">**Page Table 的数量和大小都会随着进程、映射、缺页等运行状态发生变化。**</span>

它显然<span style="background:#00FF80; color:#FF0000;">属于运行时动态资源。</span>

------

## 3. Page Cache 也是动态的吗？

也是。

比如：

```c
read(fd, buf, 4096);
```

<span style="color:#FF0000; background:#00FF80;">如果文件对应的数据目前不在 Page Cache：</span>

```text
read()
↓
Page Cache miss
↓
从 eMMC / SSD 读取
↓
Linux 找物理页面
↓
把文件内容缓存进这个页面
```

于是：

```text
Page Cache
+ 1 page
```

以后内存压力大：

```text
RAM不够
↓
某些Page Cache已经很久没用
↓
Linux回收这些page
```

于是：

```text
Page Cache
- 若干page
```

所以它一直在动态变化：

```text
运行程序
↓
Page Cache 增加

访问其他文件
↓
又增加

内存紧张
↓
回收
```

------

## 4. <span style="background:#00FF80; color:#FF0000;">Page Cache 本身不是“一块固定的 Page Cache 区”</span>

<span style="color:#FF0000; background:#00FF80;">这个尤其重要。</span>

不要想象：

```text
物理RAM

前100MB = Page Cache
后100MB = 程序
```

Linux 通常不是这么死切。

<span style="color:#FF0000; background:#00FF80;">更接近：</span>

```text
物理RAM页面

Page 1  → 用户进程匿名页
Page 2  → Page Cache
Page 3  → 页表
Page 4  → slab
Page 5  → Page Cache
Page 6  → kernel stack
Page 7  → 用户进程
...
```

今天某个 page：

```text
可能用作 Page Cache
```

以后释放之后：

```text
可能重新分给别的用途
```

所以：

> <span style="color:#FF0000; background:#00FF80;">**Page Cache 是“物理页当前承担的一种用途”，不是一块永久固定的硬件区域。**</span>

这和 MCU：

```text
这里永远是 .data
那里永远是 stack
```

的直觉很不一样。

------

## 5. Buffer Pages 也类似

你看到：

```text

```

这里还牵涉一点 Linux 历史。

早期 Linux：


概念相对分得更明显。

<span style="color:#FF0000; background:#00FF80;">现代 Linux 中很多块设备缓存已经和 Page Cache 体系紧密结合，文件系统还可能使用：</span>

```c

```

之类的结构描述块缓冲。

所以你学习阶段可以先理解：

```text

→ 缓存文件内容

Buffer相关结构
→ 帮助描述/管理文件系统块I/O
```

它们涉及的页面和对象同样大量是：

> **运行时动态创建、回收的。**

```text
          │                │                │
          ▼                ▼                ▼
       Page Table       Page Cache         SLUB
                                             │
                               ┌─────────────┼───────────┐
                               ▼             ▼           ▼
                         task_struct      inode       dentry
```

这个图比简单上下分区更准确。

------

## 7. Page Allocator 到底是什么？

它<span style="color:#FF0000; background:#00FF80;">不是“一块数据区”。</span>

它是：

> <span style="background:#00FF80; color:#FF0000;">**Linux 内核管理物理页的一套机制。**</span>

可以简单理解：

```text
整个可管理物理RAM
↓
切成一个一个page
↓
Linux记录：
哪些空闲？
哪些正在使用？
↓
Page Allocator
```

例如一页可能是：

```text
4 KB
```

具体依体系结构和配置而定。

<span style="color:#FF0000; background:#00FF80;">内核需要：</span>

```text
4 pages
```

<span style="color:#FF0000; background:#00FF80;">就问 Page Allocator：</span>

```text
“给我一些页。”
```

<span style="color:#FF0000; background:#00FF80;">以后不用：</span>

```text
“还给你。”
```

------

## 8. <span style="background:#00FF80;">SLUB 又和 Page Allocator 什么关系？</span>

这是非常关键的一层。

如果你只想创建：

```c
struct task_struct
```

显然没必要每次都：

```text
直接给它整个4KB page
```

可能很浪费。

<span style="color:#FF0000; background:#00FF80;">于是：</span>

```text
Page Allocator
↓
先给SLUB若干page

SLUB
↓
把page进一步切成很多小对象

例如：
┌───────────────┐
│ task_struct   │
├───────────────┤
│ task_struct   │
├───────────────┤
│ task_struct   │
└───────────────┘
```

所以关系：

```text
物理RAM
↓
Page Allocator
↓
SLUB
↓
task_struct / inode / dentry / ...
```

------

## 9. 那 `kmalloc()` 是什么？

<span style="background:#00FF80; color:#FF0000;">`kmalloc()` 是 Linux 内核非常常见的动态内存申请接口：</span>

```c
p = kmalloc(size, flags);
```

你<span style="color:#FF0000; background:#00FF80;">可以暂时把它类比：</span>

```text
用户空间：
malloc()

内核空间：
kmalloc()
```

但<span style="color:#FF0000;">底层实现和约束不同，不能认为完全一样。</span>

最重要的特点：

> <span style="background:#00FF80;">`kmalloc()` 返回的内核虚拟地址是连续的，并且它背后的物理内存通常也是连续的。</span>

例如：

```c
p = kmalloc(8192, GFP_KERNEL);
```

概念上可能：

```text
虚拟地址：

VA 0xC1000000
VA 0xC1001000

连续
```

<span style="background:#00FF80; color:#FF0000;">对应：</span>

```text
物理地址：

PA 0x81000000
PA 0x81001000

也连续
```

<span style="background:#00FF80; color:#FF0000;">简化为：</span>

```text
kmalloc

Virtual:
AAAA BBBB CCCC

Physical:
1111 2222 3333

两边都连续
```

------

## 10. 那 `vmalloc()` 呢？

`vmalloc()`：

```c
p = vmalloc(size);
```

它最重要的特点是：

> <span style="background:#00FF80; color:#FF0000;">**虚拟地址连续，但背后的物理页面可以不连续。**</span>

<span style="background:#00FF80; color:#FF0000;">例如：</span>

```text
程序/内核看到：

VA:
0xF0000000
0xF0001000
0xF0002000
0xF0003000

看起来连续
```

<span style="background:#00FF80; color:#FF0000;">但 MMU 页表实际映射：</span>

```text
0xF0000000 → PA 0x81000000
0xF0001000 → PA 0x93045000
0xF0002000 → PA 0x84512000
0xF0003000 → PA 0xA1007000
```

真实物理 RAM：

```text
东一块
西一块
南一块
北一块
```

但是通过：

```text
MMU + Page Table
```

拼成：

```text
一个连续的内核虚拟地址区域
```

这正好就是你前面问过：

> **“虚拟地址连续，物理地址可以不连续”**

的实际应用。

------

## 11. `kmalloc` 和 `vmalloc` 最核心区别

可以直接记这个：

```text
kmalloc：

虚拟地址连续
+
物理地址通常也连续


vmalloc：

虚拟地址连续
+
物理地址不要求连续
```

比如想申请：

```text
8 MB
```

如果要求物理连续：

```text
RAM里必须找到8MB连续空闲空间
```

系统运行时间久了以后可能很难。

但 `vmalloc()` 可以：

```text
这里找到4KB
那里找到4KB
那里再找4KB
...
```

然后 MMU：

```text
把所有散开的物理页
↓
映射成连续虚拟空间
```

所以更容易申请比较大的虚拟连续区域。

------

## 12. 为什么不全部使用 `vmalloc()`？

<span style="color:#FF0000; background:#00FF80;">因为它有成本。</span>

<span style="background:#00FF80;">`vmalloc()` 需要：</span>

```text
建立额外页表映射
```

访问还必须通过对应映射。

并且：

```text
物理不连续
```

某些底层硬件需求不适合。

相较而言 `kmalloc()`：

```text
通常使用内核直接映射区域
```

路径更直接。

所以：

```text
小型普通内核对象
→ 常用 kmalloc / slab

较大、只要求虚拟连续
→ 可以考虑 vmalloc
```

不过涉及设备 DMA 时，实际驱动应使用 Linux DMA API，而不能简单凭“物理连续”就直接拿 `kmalloc` 当通用 DMA 方案。

------

## 13. 什么叫 Direct-mapped Physical RAM？

你图最下面还有：

```text
Direct-mapped physical RAM
```

这个也非常容易误解。

Linux 内核经常把一部分物理 RAM：

```text
Physical RAM
```

直接建立一个固定偏移的内核虚拟地址映射。

概念：

```text
Physical:
0x80000000

      ↓ 固定关系

Kernel Virtual:
0xC0000000
```

比如：

```text
PA 0x80001000
↓
VA 0xC0001000
```

这样内核访问普通物理 RAM 很方便：

```text
物理页
↓
内核直接映射地址
```

所以：

```text
Direct Mapping
```

不是一种“动态分配器”。

它是一种：

> **虚拟地址映射方式。**

特别在 32 位 ARM Linux 上，具体 direct-map 范围还受架构和内核配置影响，所以不要把某一组固定地址死记成所有 Linux 都一样。

------

## 14. <span style="background:#00FF80;">回到 `per-CPU static data`</span>

你问：

> “per-CPU static data 在运行时不会动态变化又该怎么理解？”

这里<span style="color:#FF0000; background:#00FF80;">一定要区分：</span>

```text
这个变量是否存在、占多大空间
```

和：

```text
变量里面的值是否变化
```

<span style="color:#FF0000; background:#00FF80;">两个完全不同的问题。</span>

------

## 15. <span style="background:#00FF80; color:#FF0000;">`static per-CPU data` 的“static”不是说值不能改</span>

例如假设内核定义：

```c
DEFINE_PER_CPU(int, counter);
```

假设有：

```text
4个CPU
```

<span style="color:#FF0000; background:#00FF80;">那么内核会给每个 CPU 一份：</span>

```text
CPU0:
counter0

CPU1:
counter1

CPU2:
counter2

CPU3:
counter3
```

<span style="color:#FF0000; background:#00FF80;">这些变量的：</span>

```text
类型
数量
每CPU需要多少空间
```

<span style="color:#FF0000; background:#00FF80;">在编译/启动阶段基本就确定。</span>

所以称：

> **static per-CPU data**

但是运行时：

```text
CPU0 counter:
0 → 1 → 2 → 10000

CPU1 counter:
0 → 20 → 45
```

值当然一直可以变化。

所以：

```text
static
≠
const
```

------

## 16. `static` 和 `const` 一定不要混

`static` 更多表示：

> <span style="background:#00FF80;">生命周期/<span style="color:#FF0000;">存储形式/链接属性</span>等方面是<span style="color:#FF0000;">静态存在</span>的。</span>

`const` 才是：

> <span style="background:#00FF80; color:#FF0000;">不允许通过该对象修改其值。</span>

所以：

```c
static int count = 0;
```

完全可以：

```c
count++;
```

只是：

```text
这个count对象
从程序开始到结束一直存在
```

而不是说：

```text
count永远等于0
```

------

## 17. static per-CPU 可以想成<span style="color:#FF0000; background:#00FF80;">“固定工位上的计数器”</span>

比如有 4 个 CPU：

```text
CPU0 工位：
counter

CPU1 工位：
counter

CPU2 工位：
counter

CPU3 工位：
counter
```

<span style="color:#FF0000; background:#00FF80;">工位数量和计数器的位置：</span>

```text
系统启动后基本安排好了
```

但计数器里的数字：

```text
一直变
```

所以：

> <span style="color:#FF0000; background:#00FF80;">**静态的是“存储槽位/对象布局”，动态的是“里面的数据值”。**</span>

------

## 18. Linux 还有动态 per-CPU 内存

这个也很值得补充。

Linux 不只有：

```text
static per-CPU
```

也可以运行时：

```text
alloc_percpu(...)
```

动态申请每 CPU 一份的数据。

所以：

```text
per-CPU data
│
├── static per-CPU
│    编译/启动时布局
│
└── dynamic per-CPU
     运行时申请
```

因此之前图里的：

```text
per-CPU static data
```

只是专门指第一种。

------

## 20. 所以“Kernel Dynamic Memory”其实不是一个具体区域名

这也非常重要。

并不是 Linux 链接脚本里面真的存在：

```text
.kernel_dynamic_memory
```

这样一个 section。

真实世界里：

```text
task_struct
Page Cache
```

它们都可能是运行时动态占 RAM，

```text
来源
```

## 最后把你的三个问题压成一句一句

### Page Table、Page Cache 是动态的吗？

**是。**

```text
Page Table
→ 随进程/虚拟映射动态创建释放

Page Cache
→ 随文件访问和内存压力动态增加回收
```

之前单独画出来只是为了强调用途，不代表它们不是动态内存。

### `kmalloc` 和 `vmalloc`？

记：

```text
kmalloc
→ 虚拟连续
→ 物理通常也连续

vmalloc
→ 虚拟连续
→ 物理可以完全不连续
→ MMU用页表把它们拼起来
```

这正好是你前面学习“虚拟地址和物理地址分离”的一个真实例子。

### `per-CPU static data` 运行时不变吗？

不是。

> **对象的存储布局相对固定，但里面的值完全可以不停变化。**

比如：

```text
CPU0 counter：100 → 101 → 102
CPU1 counter：500 → 501
```

`static` 不是 `const`。

你现在可以把 Linux 内核 RAM 最终理解成两类：

```text
相对静态：
Kernel .text/.rodata/.data/.bss
static per-CPU layout

动态：
task_struct
inode/dentry
Page Tables
Page Cache
Kernel Stacks
vmalloc backing pages
各种kmalloc/slab对象
```

而动态这部分**不是一个整齐连续的“内核 heap 区”**，而是 Linux 用 Page Allocator、SLUB、kmalloc、vmalloc 等不同机制共同管理的一大片运行时 RAM。
