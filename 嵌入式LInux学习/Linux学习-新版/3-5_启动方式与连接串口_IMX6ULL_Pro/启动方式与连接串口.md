## 5. 三种启动方式是什么意思？

<span style="color:#FF0000; background:#00FF80;">开发板右下角有一个4位红色拨码开关，用于告诉IMX6ULL：</span>

> 上电以后，应该<span style="background:#00FF80; color:#FF0000;">从哪个存储介质读取最初的启动程序</span>。

视频表格中的设置是：

| 启动方式 | SW1  | SW2  | SW3  | SW4  |
| -------- | ---- | ---- | ---- | ---- |
| eMMC启动 | OFF  | OFF  | ON   | OFF  |
| SD卡启动 | ON   | ON   | ON   | OFF  |
| USB烧写  | X    | X    | OFF  | ON   |

其中：

```text
ON  = 开关拨到ON方向
OFF = 开关拨离ON方向
X   = 无关，ON或OFF均可
```

------

## 5.1 eMMC启动

eMMC是<span style="color:#FF0000; background:#00FF80;">焊接在开发板上的存储器</span>，可以<span style="color:#FF0000; background:#00FF80;">理解成开发板内部的“硬盘”</span>。

流程：

```text
上电
 ↓
IMX6ULL读取eMMC
 ↓
运行Boot ROM找到的启动程序
 ↓
启动U-Boot
 ↓
启动Linux内核和根文件系统
```

<span style="color:#FF0000; background:#00FF80;">刚出厂的板子通常已经在eMMC中烧写了系统，因此正常使用时经常选择eMMC启动。</span>

------

## 5.2 SD卡启动

将制作好的系统镜像写入SD/TF卡，然后设置为SD卡启动。

流程：

```text
上电
 ↓
从SD卡读取U-Boot
 ↓
从SD卡读取Linux内核、设备树、根文件系统
```

<span style="color:#FF0000; background:#00FF80;">常见用途</span>：

- 测试另一套系统；
- eMMC系统损坏时救援；
- 不覆盖板载系统的情况下进行实验。

------

## 5.3 USB烧写模式

<span style="color:#FF0000; background:#00FF80;">USB模式不是普通意义上的“从U盘启动”。</span>

它通常表示：

> <span style="background:#00FF80;">让芯片进入USB下载模式，由电脑上的烧写工具把系统镜像写入开发板。</span>

视频特别提醒：

```text
设置为USB启动时，上电前不要插SD/TF卡；
开发板上电后，再按课程要求插卡或执行烧写。
```

这是为了避免启动介质干扰USB下载流程。

## 6. USB串口到底是什么？

开发板上的处理器通常提供UART串口：

```text
TX：发送
RX：接收
GND：地
```

但<span style="color:#FF0000; background:#00FF80;">普通电脑现在通常没有原生UART接口</span>，因此<span style="color:#FF0000; background:#00FF80;">开发板增加了USB转串口芯片</span>，例如<span style="color:#FF0000; background:#00FF80;">视频中出现的：</span>

```text
CP2104
CP210x系列
CH9102
```

转换关系是：

```text
IMX6ULL UART信号
        ↓
CP2104 / CH9102
        ↓
USB数据
        ↓
Windows电脑
        ↓
COM17、COM19等虚拟串口
```

所以<span style="color:#FF0000; background:#00FF80;">Windows设备管理器里看到的COM口</span>，代表的<span style="color:#FF0000; background:#00FF80;">不是网络连接</span>，而是：

> <span style="background:#00FF80;">**通过USB连接的一条串行通信通道。**</span>

## 7. 串口和SSH有什么本质区别？

这是<span style="color:#FF0000; background:#00FF80;">这节最重要的区别。</span>

### 串口连接

```text
Windows MobaXterm
      ↓ USB线
USB转串口芯片
      ↓ UART
开发板
```

<span style="color:#FF0000; background:#00FF80;">串口的特点：</span>

- 不需要IP地址；
- 不需要开发板网卡工作；
- 能看到开发板刚上电时的启动日志；
- 即使Linux没有启动成功，仍可能看到U-Boot或错误信息；
- 常用于系统烧写、启动调试和救援。

<span style="color:#FF0000; background:#00FF80;">MobaXterm中选择：</span>

```text
Serial
COM端口
115200 bps
```

------

### SSH连接

```text
Windows MobaXterm
      ↓ 以太网
开发板IP地址
      ↓
开发板SSH服务
```

<span style="color:#FF0000; background:#00FF80;">SSH的特点：</span>

- 必须配置网络；
- 开发板<span style="color:#FF0000; background:#00FF80;">需要有IP地址</span>；
- Linux通常需要已经正常启动；
- SSH服务必须运行；
- 适合系统启动后的日常操作、传文件和<span style="color:#FF0000; background:#00FF80;">远程开发</span>。

<span style="color:#FF0000; background:#00FF80;">可以记成：</span>

```text
串口：不靠网络，主要解决“板子能不能启动”。

SSH：依赖网络，主要解决“系统启动后怎么远程使用”。
```

------

## 8. VMware弹出的USB设备归属是什么意思？

视频约在 **00:38-01:08** 出现提示：

```text
检测到新的USB设备
Silicon CP2104 USB to UART Bridge Controller
连接到主机
连接到虚拟机
```

因为你的电脑同时运行：

```text
Windows宿主机
Ubuntu虚拟机
```

<span style="color:#FF0000; background:#00FF80;">一台USB设备通常在某一时刻只能由其中一方直接占用。</span>

### 连接到主机

表示<span style="color:#FF0000; background:#00FF80;">CP2104交给Windows使用。</span>

之后：

- <span style="color:#FF0000;">Windows设备管理器能看到COM口；</span>
- <span style="background:#00FF80;">Windows版MobaXterm能打开这个COM口；</span>
- <span style="color:#FF0000;">Ubuntu虚拟机通常看不到它。</span>

本视频使用Windows版MobaXterm，所以应让它：

```text
连接到主机Windows
```

------

### 连接到虚拟机

表示把USB串口设备交给Ubuntu虚拟机。

此时<span style="color:#FF0000; background:#00FF80;">Ubuntu中可能出现：</span>

```text
/dev/ttyUSB0
```

或：

```text
/dev/ttyACM0
```

可以在Ubuntu中使用串口工具打开，但Windows的MobaXterm就不能同时使用它。

所以判断原则是：

```text
用Windows串口软件 → USB设备留给Windows宿主机
用Ubuntu串口软件 → USB设备连接给Ubuntu虚拟机
```

## 9. 如何检查串口驱动？

连接USB串口后，在Windows打开：

```text
设备管理器
→ 端口（COM和LPT）
```

正常情况下会看到类似：

```text
Silicon Labs CP210x USB to UART Bridge (COM17)
```

或者：

```text
USB-Enhanced-SERIAL CH9102 (COM19)
```

<span style="color:#FF0000; background:#00FF80;">这里要记下的是：</span>

```text
COM17
COM19
```

你的电脑显示的数字不一定和视频相同。

------

### 9.1 没有显示“端口（COM和LPT）”

可能原因：

- USB数据线没有连接好；
- 使用的是只能充电、不能传数据的线；
- 开发板USB串口接错接口；
- USB设备被VMware虚拟机占用；
- <span style="color:#FF0000; border:1px solid #330000; background:#00FF80;">驱动未安装；</span>
- <span style="color:#FF0000; background:#00FF80; border:1px solid #330000;">USB转串口芯片故障。</span>

------

### 9.2 出现黄色感叹号

通常说明：

> Windows已经检测到硬件，但没有正确驱动。

<span style="color:#FF0000; background:#00FF80;">根据设备名称选择对应驱动：</span>

```text
名称中有CP210x
→ 安装CP210x Windows驱动

名称中有CH9102或类似CH34x
→ 安装对应WCH串口驱动
```

## 10. MobaXterm串口设置

视频中操作：

```text
Session
→ Serial
```

主要配置两个参数。

### Serial port

<span style="color:#FF0000; background:#00FF80;">选择设备管理器中看到的COM端口</span>，例如：

```text
COM17
COM19
```

也可以设置为启动会话时再选择。

------

### Speed

视频设置：

```text
115200 bps
```

这表示每秒传输约115200个比特。

开发板串口常见配置可以写成：

```text
115200 8N1
```

意思是：

```text
波特率：115200
数据位：8
校验位：None，无校验
停止位：1
```

通信双方参数必须一致，否则可能出现：

- 屏幕全是乱码；
- 能看到输出但输入无效；
- 输出字符不完整。

## 11. 为什么打开串口后可能只有空白屏幕？

串口工具打开后，不一定马上有内容。

可能需要：

1. 给开发板重新上电；
2. 按一下开发板复位键；
3. 在终端中按一次回车；
4. 确认选择了正确COM口；
5. 确认波特率是115200。

原因是：

> 串口只显示它打开以后接收到的数据；如果开发板已经启动完毕且没有继续输出，窗口可能暂时空白。

## 12. 登录开发板时发生了什么？

视频中出现：

```text
100ask login:
```

这说明开发板已经：

```text
完成Boot ROM阶段
→ 完成U-Boot阶段
→ 启动Linux内核
→ 启动用户空间
→ 运行登录程序
```

讲师一开始输入了大写：

```text
ROOT
```

系统提示：

```text
Login incorrect
```

Linux用户名区分大小写：

```text
ROOT ≠ root
```

随后输入小写：

```text
root
```

成功进入：

```text
[root@100ask:~]#
```

从视频表现看，这套开发板系统的root账号可能没有设置密码，所以出现 `Password:` 时直接回车即可。不同镜像可能设置不同，不能把“无密码”当作所有Linux系统的通用规则。

## 13. 如何证明当前操作的是开发板，而不是Ubuntu？

视频串口窗口的提示符是：

```text
[root@100ask:~]#
```

而之前Ubuntu虚拟机的提示符通常是：

```text
book@100ask:~$
```

它们虽然主机名都可能包含 `100ask`，但可以通过多个特征区分。

| 项目         | Ubuntu虚拟机      | Linux开发板       |
| ------------ | ----------------- | ----------------- |
| 常见连接方式 | SSH到Ubuntu IP    | Serial/COM串口    |
| 常见用户     | `book`            | `root`            |
| 提示符       | `$`               | `#`               |
| `pwd`结果    | `/home/book`      | `/root`           |
| CPU架构      | x86-64            | ARM               |
| 当前系统     | Ubuntu桌面/服务器 | 开发板嵌入式Linux |

最可靠的检查命令是：

```bash
uname -m
```

Ubuntu虚拟机可能显示：

```text
x86_64
```

IMX6ULL开发板通常显示类似：

```text
armv7l
```

## 14. 结尾命令的含义

登录后，视频演示了几个Linux基础命令。

### `ls`

```bash
ls
```

显示当前目录内容。

在 `/root` 下可能没有太多文件，所以第一次执行后画面几乎没有变化。

------

### `pwd`

```bash
pwd
```

显示当前工作目录：

```text
/root
```

说明当前登录的是root用户，并位于root的主目录。

------

### `cd /`

```bash
cd /
```

进入Linux根目录。

这里的 `/` 是整个文件系统的最顶层。

------

```text
dev
etc
home
lib
linuxrc
media
mnt
proc
```

这些目录属于开发板的根文件系统。

> MobaXterm窗口中的命令现在由IMX6ULL开发板执行，而不是Windows或Ubuntu虚拟机执行。

## 15. 启动和串口的关系

<span style="color:#FF0000; background:#00FF80;">拨码开关与串口负责两件不同的事：</span>

```text
拨码开关：
决定开发板从哪里读取系统。

串口：
让电脑看到开发板启动过程，并向开发板输入命令。
```

例如<span style="color:#FF0000; border:1px solid #330000; background:#00FF80;">设置为eMMC启动：</span>

```text
拨码开关选择eMMC
        ↓
开发板从eMMC启动
        ↓
启动日志通过UART发出
        ↓
CP2104转换成USB
        ↓
MobaXterm显示日志
```

<span style="color:#FF0000; background:#00FF80;">串口本身不会提供系统，也不会决定系统从哪里启动。</span>

## 16. 常见故障判断

| 现象                     | 可能原因                                      |
| ------------------------ | --------------------------------------------- |
| 设备管理器没有COM口      | 数据线、驱动、USB设备归属或接口错误           |
| MobaXterm中找不到COM口   | 被其他软件占用，或USB设备连接给了Ubuntu虚拟机 |
| 串口全是乱码             | 波特率或串口参数不一致                        |
| 打开后完全空白           | 板子未上电、COM口错误、尚未复位或串口线错误   |
| 能看到启动日志但不能输入 | 串口流控、接收链路、终端设置或硬件问题        |
| `Login incorrect`        | 用户名或密码错误，Linux区分大小写             |
| 一直停在U-Boot或启动失败 | 拨码模式、启动介质或系统镜像有问题            |
| eMMC启动没有反应         | eMMC中没有有效系统，或拨码设置错误            |

# 问题1

视频里面所说的串口驱动程序指的是com口还是那个USB转UART呢，为什么连接上了之后主机会自动安装驱动程序呢，这个驱动程序是个什么东西呢。



视频里说的“<span style="color:#FF0000; background:#00FF80;">串口驱动程序</span>”，**主要指 <span style="background:#00FF80;">Windows 为 USB 转 UART 芯片安装的驱动</span>**，<span style="color:#FF0000;">不是指 `COM17` 这个号码本身。</span>

最关键的关系是：

```text
USB转UART芯片：真实硬件
驱动程序：让Windows认识并控制这个硬件的软件
COM17：驱动安装成功后，Windows提供给应用程序的逻辑接口名称
```

------

## 1. COM口和USB转UART不是同一个东西

<span style="color:#FF0000; background:#00FF80;">开发板上通常有一颗芯片</span>，例如：

```text
CP2104
CH9102
CH340
FT232
```

它的作用是转换：

```text
USB数据 ↔ UART串口数据
```

整个链路是：

```text
Windows电脑
    │ USB
    ▼
CP2104 / CH9102 USB转UART芯片
    │ TX、RX
    ▼
IMX6ULL处理器的UART串口
```

这颗<span style="color:#FF0000; background:#00FF80;">USB转UART芯片</span>是一个<span style="background:#00FF80;">**真实硬件设备**。</span>

而<span style="color:#FF0000; background:#00FF80;">Windows设备管理器中显示</span>的：

```text
Silicon Labs CP210x USB to UART Bridge (COM17)
```

可以<span style="color:#FF0000; background:#00FF80;">拆成两部分：</span>

```text
Silicon Labs CP210x USB to UART Bridge
→ Windows识别出的硬件类型

COM17
→ Windows为它分配的逻辑串口编号
```

所以：

> <span style="color:#FF0000; background:#00FF80;">驱动主要服务于CP2104、CH9102等USB转UART芯片；COM17是驱动加载后呈现给MobaXterm使用的接口。</span>

------

## 2. 驱动程序到底是什么？

<span style="color:#FF0000;">驱动程序</span>是<span style="color:#FF0000; background:#00FF80;">一段运行在操作系统底层的软件。</span>

它<span style="color:#FF0000;">负责在两边之间“翻译”：</span>

```text
上层软件的串口操作
        ↕
USB转UART芯片能理解的USB命令
```

例如你在MobaXterm中设置：

```text
波特率：115200
数据位：8
停止位：1
无校验
```

MobaXterm本身通常不会直接控制CP2104芯片。

它<span style="color:#FF0000; background:#00FF80;">只是告诉Windows：</span>

```text
请把COM17设置为115200
请把这些字符发送出去
```

然后驱动程序负责：

1. 找到对应的USB设备；
2. 将115200等设置转换成芯片命令；
3. 通过USB把数据发送给CP2104；
4. 接收CP2104传回来的数据；
5. 把数据交给MobaXterm显示。

可以理解为：

```text
MobaXterm
   │ “向COM17发送root”
   ▼
Windows串口接口
   ▼
CP2104驱动
   │ 转换成USB数据包
   ▼
USB转UART芯片
   │ 转换成UART电信号
   ▼
IMX6ULL开发板
```

------

## 3. 为什么不安装驱动就不能直接使用？

因为Windows刚看到一个USB设备时，只知道：

```text
有一个USB设备接进来了
```

但<span style="color:#FF0000; background:#00FF80;">Windows不一定知道：</span>

- 这个设备是鼠标、键盘还是串口芯片；
- 应该怎样设置波特率；
- 怎样发送和接收数据；
- 怎样把它呈现成COM口；
- 芯片厂商有哪些特殊控制命令。

<span style="color:#FF0000; background:#00FF80;">驱动程序就是设备的“使用说明和控制翻译器”。</span>

没有合适驱动时，设备管理器可能显示：

```text
未知设备
```

或者带黄色感叹号，且不会正常出现：

```text
COM17
```

------

## 4. 为什么连接以后Windows会自动安装驱动？

这是<span style="color:#FF0000; background:#00FF80;">USB的“即插即用”机制。</span>

<span style="color:#FF0000;">当你插入USB串口后，CP2104或CH9102会向Windows报告自己的身份信息，例如：</span>

```text
设备类型
厂商编号 VID
产品编号 PID
设备类别
版本信息
```

其中：

```text
VID = Vendor ID，厂商编号
PID = Product ID，产品编号
```

<span style="color:#FF0000; background:#00FF80;">Windows根据这些信息寻找匹配的驱动</span>。

过程大致是：

```text
插入USB设备
   ↓
Windows检测到新硬件
   ↓
读取设备的VID和PID
   ↓
在本地驱动库中寻找匹配驱动
   ↓
如果本地没有，可能通过Windows Update查找
   ↓
安装并启动驱动
   ↓
创建虚拟COM端口
   ↓
设备管理器显示COM17
```

因此<span style="color:#FF0000; background:#00FF80;">“自动安装”不代表不需要驱动</span>，而是：

> <span style="color:#FF0000; background:#00FF80;">Windows自动找到了驱动并替你完成了安装。</span>

------

## 5. Windows从哪里找到驱动？

通常有三种来源。

### 情况一：Windows系统自带

有些USB串口设备使用标准USB CDC协议，Windows自带通用驱动，例如：

```text
usbser.sys
```

插上后可以直接识别。

------

### 情况二：以前已经安装过

<span style="color:#FF0000;">可能课程虚拟机、开发工具包或其他软件已经把驱动放入Windows驱动仓库。</span>

<span style="color:#FF0000; background:#00FF80;">再次连接同类芯片时，Windows会自动匹配，不再询问。</span>

------

### 情况三：Windows Update自动下载

<span style="color:#FF0000; background:#00FF80;">电脑联网时，Windows可能根据VID、PID自动从微软的驱动库中下载厂商驱动。</span>

例如CP210x驱动可能<span style="color:#FF0000; background:#00FF80;">来自Silicon Labs。</span>

------

### 自动安装失败时

<span style="color:#FF0000; background:#00FF80;">需要手动安装厂商提供的驱动，例如：</span>

```text
CP210x → Silicon Labs驱动
CH9102、CH340 → WCH驱动
FT232 → FTDI驱动
```

<span style="color:#FF0000;">安装成功后，再重新插拔USB设备。</span>

------

## 6. “虚拟COM口”是什么意思？

传统电脑曾经有真实的串口接口，例如：

```text
COM1
COM2
```

对应主板上的物理RS-232串口。

<span style="color:#FF0000; background:#00FF80;">现在很多电脑没有物理串口，所以USB转UART驱动会创建一个：</span>

> 虚拟串口 Virtual COM Port，简称VCP。

它<span style="color:#FF0000;">在软件看来像普通串口：</span>

```text
COM17
```

但<span style="color:#FF0000;">物理传输实际上走的是：</span>

```text
USB线
```

所以<span style="color:#FF0000; background:#00FF80;">“虚拟”的含义不是它不存在，而是：</span>

```text
软件接口表现为串口
实际硬件连接使用USB
```

MobaXterm只需要打开：

```text
COM17
```

不需要关心背后是CP2104还是CH9102。

------

## 7. 为什么COM编号可能是17、19，而不是COM1？

<span style="color:#FF0000; background:#00FF80;">Windows会为每个识别过的串口设备分配编号。</span>

例如：

```text
曾经连接的蓝牙串口：COM3、COM4
其他开发板：COM5
调试器：COM8
当前CP2104：COM17
```

<span style="color:#FF0000; background:#00FF80;">即使以前的设备已经拔掉，部分编号仍可能被保留。</span>

因此<span style="color:#FF0000;">COM17并不表示有17个设备正在连接，只表示：</span>

> <span style="color:#FF0000; background:#00FF80;">Windows为当前设备分配的逻辑编号是17。</span>

不同电脑上可能显示：

```text
COM3
COM7
COM17
COM19
```

都很正常。

------

## 8. 驱动安装成功后具体创建了什么？

驱动正常加载后，会向Windows注册一个串口设备。

应用程序可以通过类似下面的设备路径访问它：

```text
\\.\COM17
```

<span style="color:#FF0000; background:#00FF80;">MobaXterm、串口助手等软件从Windows获得可用端口列表</span>，然后显示：

```text
COM17
```

因此层次是：

```text
真实硬件：CP2104
    ↓
硬件驱动：CP2104驱动程序
    ↓
操作系统接口：COM17
    ↓
用户软件：MobaXterm
```

------

## 9. 开发板内部是否也有串口驱动？

有，这里其实可能涉及两侧的驱动。

### <span style="background:#00FF80;">Windows端驱动</span>

负责控制：

```text
USB转UART芯片
```

例如：

```text
CP2104驱动
CH9102驱动
```

它让Windows产生COM口。

------

### 开发板Linux端驱动

<span style="color:#FF0000; background:#00FF80;">IMX6ULL处理器内部有UART控制器，Linux内核也需要UART驱动来控制它。</span>

例如负责：

- 初始化IMX6ULL UART；
- 设置波特率；
- 接收和发送字符；
- 把UART作为Linux控制台；
- 显示启动日志和登录界面。

完整路径是：

```text
MobaXterm
  ↓
Windows USB转串口驱动
  ↓
CP2104芯片
  ↓
UART线路
  ↓
IMX6ULL UART控制器
  ↓
开发板Linux UART驱动
  ↓
Linux控制台和Shell
```

不过<span style="color:#FF0000; background:#00FF80;">视频中说“安装串口驱动”</span>，通常特指：

> <span style="background:#00FF80;">**Windows端的USB转串口驱动。**</span>

因为<span style="color:#FF0000; background:#00FF80;">开发板Linux中的UART驱动已经包含在系统镜像和内核里了。</span>

------

## 10. 为什么驱动与芯片型号必须匹配？

<span style="color:#FF0000; background:#00FF80;">不同芯片的控制协议可能不同。</span>

例如：

```text
CP2104使用Silicon Labs的协议
CH9102使用WCH的协议
FT232使用FTDI的协议
```

虽然<span style="color:#FF0000;">最终都显示成COM口，但Windows底层控制它们的方法可能不一样。</span>

就像<span style="color:#FF0000; background:#00FF80;">三台打印机都能打印文档，但具体通信方式不同，需要相应驱动。</span>

因此：

```text
装了CH340驱动
```

不一定能正确驱动：

```text
CP2104
```

应该先查看设备管理器中的名称或硬件ID，再安装对应驱动。

## 12. 你可以这样区分三个概念


## 13. 最准确的一句话

> 视频里的“串口驱动程序”通常指Windows端用于控制CP2104、CH9102等USB转UART芯片的驱动。COM口不是驱动，而是驱动成功加载后创建的逻辑串口接口。Windows插入设备后读取其VID/PID，通过即插即用机制从本地驱动库或Windows Update匹配驱动，因此经常能够自动安装并显示为COM端口。

记忆版：

```text

再加载对应驱动，
驱动成功后才出现COM口，
MobaXterm最后通过COM口访问开发板。
```





# 启动过程详解

 完成Boot ROM阶段 → 完成U-Boot阶段 → 启动Linux内核 → 启动用户空间 → 运行登录程序



eMMC是焊接在开发板上的存储器，可以理解成开发版上的 “硬盘” 

流程： 

上电 

IMX6ULL读取eMMC 

运行Boot ROM找到的启动程序 

启动U-Boot 

启动Linux内核和根文件系统 

刚出厂的板子通常已经在eMMC中烧写了系统，因此正常使用时经常选择eMMC启动。





## eMMC 启动过程详解

你图片里的流程方向是对的，但它把很多中间步骤省略了。更完整的过程应该是：

```text
开发板上电/复位
        ↓
处理器内部的 Boot ROM 开始运行
        ↓
读取启动拨码、熔丝等启动配置
        ↓
确定从 eMMC 启动
        ↓
从 eMMC 找到启动镜像头信息
        ↓
根据 DCD 初始化 DDR 内存
        ↓
把 U-Boot 从 eMMC 复制到 DDR
        ↓
跳转到 U-Boot 运行
        ↓
U-Boot 初始化更多硬件、读取启动参数
        ↓
把 Linux 内核和设备树从 eMMC 加载到 DDR
        ↓
跳转到 Linux 内核
        ↓
Linux 内核初始化驱动、进程和内存管理
        ↓
挂载 eMMC 中的根文件系统
        ↓
运行 init 进程、启动服务
        ↓
出现登录提示符
```

NXP给出的i.MX6系列高层启动流程也是“复位 → 片内ROM → U-Boot → Linux及设备树 → Linux系统”；ARM Linux本身需要由启动加载程序先准备内存和必要参数，再进入内核。([NXP](https://www.nxp.com/docs/en/user-guide/IMX_PORTING_GUIDE.pdf?utm_source=chatgpt.com))

------

## 一、先认识启动过程中涉及的四个部分

| 部分       | 存放位置                            | 主要任务                            |
| ---------- | ----------------------------------- | ----------------------------------- |
| Boot ROM   | IMX6ULL芯片内部                     | 找到并加载第一阶段启动程序          |
| U-Boot     | 一般烧写在eMMC中，运行时进入DDR     | 加载Linux内核、设备树并传递启动参数 |
| Linux内核  | 一般保存在eMMC分区中，运行时进入DDR | 管理CPU、内存、驱动和进程           |
| 根文件系统 | 一般保存在eMMC的ext4等分区中        | 提供命令、库、配置文件和应用程序    |

可以先把它们类比成电脑：

```text
Boot ROM ≈ 主板中固化的最初启动代码
U-Boot  ≈ 类似BIOS/UEFI承担的启动加载功能
Linux内核 ≈ 操作系统核心
根文件系统 ≈ 系统盘中的程序、库和配置文件
```

这个类比只能帮助理解，U-Boot和PC上的BIOS/UEFI并不完全相同。

------

## 二、第一阶段：开发板上电

当你给开发板接通电源时，首先发生的是：

1. 电源芯片提供各路电压；
2. IMX6ULL退出复位状态；
3. CPU从规定的复位地址开始取指；
4. 执行芯片内部固化的Boot ROM代码。

这里<span style="color:#FF0000;">有一个很重要的点：</span>

> 此时<span style="color:#FF0000; background:#00FF80;">还没有运行eMMC中的U-Boot，也没有运行Linux。</span>

<span style="color:#FF0000; background:#00FF80;">首先执行的是IMX6ULL芯片内部自带的Boot ROM。</span>

------

### Boot ROM存放在哪里？

Boot ROM存在于<span style="color:#FF0000; background:#00FF80;">IMX6ULL芯片内部的只读存储区域。</span>

它具有这些特点：

```text
芯片出厂时已经写好
普通用户无法修改
开发板断电后不会消失
每次复位后最先执行
```

因此，即使：

- eMMC是空的；
- Linux内核损坏；
- U-Boot损坏；

芯片内部的Boot ROM仍然存在。

<span style="color:#FF0000;">只是Boot ROM可能找不到有效的下一阶段程序，于是开发板无法正常启动，或者进入USB下载模式。</span>

------

## 三、第二阶段：Boot ROM判断从哪里启动

IMX6ULL<span style="color:#FF0000;">并不知道你一定要从eMMC启动。</span>

它<span style="color:#FF0000; background:#00FF80;">需要检查启动配置</span>，例如：

- 启动拨码开关；
- BOOT_MODE引脚；
- 启动配置引脚；
- 芯片内部熔丝配置。

<span style="color:#FF0000; background:#00FF80;">假设你把拨码设置为eMMC启动，Boot ROM就会得到类似的信息：</span>

```text
启动模式：内部启动
启动设备：eMMC/MMC接口
```

随后<span style="color:#FF0000; background:#00FF80;">Boot ROM初始化访问eMMC所需的最基本控制器，尝试从eMMC的规定位置读取启动镜像。</span>

所以图片中的：

```text
IMX6ULL读取eMMC
```

更准确地说应该是：

> **IMX6ULL内部的Boot ROM，根据启动配置，通过USDHC/MMC控制器访问eMMC，并搜索有效启动镜像。**

NXP说明eMMC是永久焊接在开发板上的存储芯片，并通过处理器的SD/MMC接口连接；IMX6ULL本身支持eMMC等多种外部非易失性存储接口。([NXP](https://www.nxp.com/docs/en/user-guide/IMX_LINUX_USERS_GUIDE.pdf?utm_source=chatgpt.com))

------

## 四、第三阶段：Boot ROM在eMMC里找什么？

Boot ROM不是随便看到一个文件名叫作：

```text
u-boot
```

就能够启动。

它通常会从eMMC规定的偏移位置，读取具有特殊格式的启动镜像。对于i.MX6系列，常见的U-Boot启动镜像叫：

```text
u-boot.imx
```

这个镜像不只是普通的U-Boot二进制代码，前面通常还有一些启动数据结构：

```text
┌─────────────────────────┐
│ IVT：镜像向量表          │
├─────────────────────────┤
│ Boot Data：镜像位置和大小 │
├─────────────────────────┤
│ DCD：DDR初始化数据        │
├─────────────────────────┤
│ CSF：安全启动信息，可选    │
├─────────────────────────┤
│ U-Boot程序代码            │
└─────────────────────────┘
```

<span style="color:#FF0000; background:#00FF80;">Boot ROM会读取IVT、DCD等结构，获得U-Boot的加载地址、入口地址、镜像大小和DDR配置，然后再加载并跳转到U-Boot</span>。([NXP Community](https://community.nxp.com/t5/i-MX-Processors/Can-any-body-explain-the-booting-sequence-of-i-MX6-based-board/m-p/503337?utm_source=chatgpt.com))

------

### 1. IVT是什么？

IVT全称：

```text
Image Vector Table
镜像向量表
```

它类似一张“启动镜像说明表”，告诉Boot ROM：

```text
程序入口地址在哪里
DCD在哪里
Boot Data在哪里
安全启动信息在哪里
当前IVT自身在哪里
```

可以把它理解成快递包裹上的标签：

```text
包裹里面是什么
应该搬到哪里
搬多少内容
最终从哪里开始执行
```

------

### 2. Boot Data是什么？

Boot Data通常会告诉Boot ROM：

```text
镜像要放到内存的什么位置
镜像一共有多大
是否属于特殊插件镜像
```

因此Boot ROM知道：

> 应该从eMMC读取多少字节，并把它们放到哪一段内存。

------

### 3. DCD是什么？

DCD全称：

```text
Device Configuration Data
设备配置数据
```

它在IMX6ULL启动时非常重要，尤其与DDR初始化有关。

<span style="color:#FF0000; background:#00FF80;">上电初期，外部DDR还不能直接正常使用。因为DDR控制器需要配置很多参数，例如：</span>

- DDR类型；
- 时序；
- 行列地址；
- 数据宽度；
- 驱动强度；
- 延迟参数；
- 校准参数。

这些配置值会以DCD形式放在启动镜像中。

Boot ROM读取DCD后，根据里面的指令写入IMX6ULL相关寄存器，从而初始化DDR。NXP对i.MX6启动流程的说明明确指出，片内ROM会解析并执行DCD，借此完成DDR和部分必要I/O的早期配置。([NXP Community](https://community.nxp.com/t5/i-MX-Processors/Can-any-body-explain-the-booting-sequence-of-i-MX6-based-board/m-p/503337?utm_source=chatgpt.com))

------

## 五、为什么要先初始化DDR？

因为U-Boot和Linux内核都比较大。

IMX6ULL芯片内部只有容量有限的内部RAM，无法长期容纳完整的：

- U-Boot；
- Linux内核；
- 大量运行数据。

所以启动过程大致是：

```text
先使用芯片内部的小容量RAM
        ↓
读取IVT和DCD
        ↓
初始化外部DDR
        ↓
把完整U-Boot搬到大容量DDR
```

可以类比成：

```text
片内RAM：门口的小桌子
DDR：正式的大仓库
```

刚开始仓库还没开门，所以Boot ROM只能先在小桌子上处理启动信息。DCD把仓库配置好以后，才能把U-Boot等大型程序搬进去。

------

## 六、第四阶段：把U-Boot加载到DDR

DDR初始化成功以后，Boot ROM根据IVT和Boot Data提供的信息：

1. 从eMMC继续读取U-Boot镜像；
2. 把U-Boot复制到DDR指定地址；
3. 可选地进行安全启动校验；
4. 将CPU的执行位置跳转到U-Boot入口。

流程可以写成：

```text
eMMC中的u-boot.imx
        ↓ Boot ROM读取
DDR中的U-Boot代码
        ↓ 跳转入口地址
CPU开始执行U-Boot
```

注意：

> U-Boot长期存放在eMMC，但实际运行时通常是在DDR中执行。

因为DDR速度通常远高于eMMC，而且程序运行过程中需要可读写内存、栈和各种数据结构。

------

## 七、第五阶段：U-Boot开始运行

CPU跳到U-Boot后，你通常会开始在串口中看到输出，例如：

```text
U-Boot 2016.03 ...
CPU:   Freescale i.MX6ULL
DRAM:  512 MiB
MMC:   ...
Loading Environment from MMC...
```

Boot ROM阶段通常不会像U-Boot一样输出大量串口日志，所以你在串口里看到的第一批明显信息往往来自U-Boot。

------

### U-Boot具体做什么？

U-Boot主要负责：

#### 1. 进一步初始化硬件

例如：

- 串口；
- 网卡；
- eMMC/SD；
- USB；
- 时钟；
- GPIO；
- DDR；
- 显示设备等。

Boot ROM只完成最低限度的启动工作，U-Boot则完成更完整、更灵活的板级初始化。

------

#### 2. 读取环境变量

U-Boot会读取启动环境变量，例如：

```text
bootcmd
bootargs
kernel_addr_r
fdt_addr_r
rootfs位置
```

其中<span style="color:#FF0000; background:#00FF80;">最重要的两个概念是：</span>

```text
bootcmd：U-Boot接下来执行哪些加载和启动命令
bootargs：传给Linux内核的启动参数
```

例如bootargs可能类似：

```text
console=ttymxc0,115200
root=/dev/mmcblk1p2
rootwait
rw
```

含义大致为：

```text
console=ttymxc0,115200
内核日志和终端使用指定串口，波特率115200

root=/dev/mmcblk1p2
根文件系统位于某个eMMC分区

rootwait
等待eMMC设备初始化完成

rw
以可读写方式挂载根文件系统
```

实际设备编号由开发板镜像配置决定，不一定就是上面的示例。

------

#### 3. 从eMMC加载Linux内核

U-Boot在eMMC中寻找内核镜像，例如：

```text
zImage
uImage
Image
```

IMX6ULL这种32位ARM平台常见：

```text
zImage
```

随后将它复制到DDR：

```text
eMMC中的zImage
        ↓
DDR中的内核加载地址
```

------

#### 4. 加载设备树

<span style="color:#FF0000; background:#00FF80;">U-Boot还会加载设备树文件：</span>

```text
imx6ull-xxx.dtb
```

<span style="color:#FF0000; background:#00FF80;">设备树向Linux内核描述开发板硬件，例如：</span>

```text
有多少内存
串口地址是什么
网卡使用哪些引脚
eMMC连接到哪个控制器
LED连接到哪个GPIO
I²C、SPI设备有哪些
```

可以把设备树理解成：

> **开发板的硬件说明书，以二进制数据形式交给Linux内核。**

ARM Linux启动规范要求启动加载程序准备RAM和必要的机器信息；现代ARM系统通常通过设备树将硬件描述传给内核。([Linux Kernel Documentation](https://docs.kernel.org/arch/arm/booting.html?utm_source=chatgpt.com))

------

#### 5. <span style="color:#FF0000;">告诉Linux内核根文件系统在哪里</span>

根文件系统可能位于：

- eMMC分区；
- SD卡分区；
- NAND；
- initramfs；
- 网络NFS服务器。

eMMC启动时经常类似：

```text
U-Boot从eMMC加载内核和DTB
Linux内核再挂载eMMC中的根文件系统分区
```

------

## 八、一个示意性的U-Boot启动命令

下面只是帮助理解，不是要求你在开发板上照抄：

```bash
load mmc 1:1 ${loadaddr} zImage
load mmc 1:1 ${fdt_addr} imx6ull-board.dtb
setenv bootargs console=ttymxc0,115200 root=/dev/mmcblk1p2 rootwait rw
bootz ${loadaddr} - ${fdt_addr}
```

可以逐条理解：

```text
第一条：
从MMC/eMMC分区加载zImage到DDR

第二条：
从MMC/eMMC加载设备树到DDR

第三条：
设置Linux启动参数

第四条：
启动zImage，并把设备树地址传给内核
```

------

## 九、第六阶段：Linux内核开始运行

执行类似：

```text
bootz
```

后，<span style="color:#FF0000; background:#00FF80;">U-Boot把控制权交给Linux内核。</span>

此时U-Boot的任务基本结束，不再继续控制系统。

<span style="color:#FF0000; background:#00FF80;">Linux内核接下来会完成：</span>

1. 解压内核；
2. 设置CPU运行环境；
3. 初始化MMU和页表；
4. 初始化中断；
5. 初始化内存管理；
6. 启动调度器；
7. 初始化各类驱动；
8. 根据设备树识别硬件；
9. 初始化eMMC控制器；
10. 准备挂载根文件系统。

串口中会开始出现类似：

```text
Booting Linux on physical CPU...
Linux version 4.9.88...
CPU: ARMv7 Processor...
Memory: ...
mmc0: new high speed MMC card...
```

------

### Linux内核是直接在eMMC中执行的吗？

通常不是。

常见过程是：

```text
eMMC保存压缩的内核镜像
        ↓
U-Boot复制到DDR
        ↓
内核在DDR中解压和运行
```

所以：

```text
eMMC：长期存储
DDR：程序运行空间
```

------

## 十、第七阶段：挂载根文件系统

图片写的是：

```text
启动Linux内核和根文件系统
```

这句话<span style="color:#FF0000; background:#00FF80;">容易让人误以为“内核和根文件系统是一起启动的”。</span>

更准确地说是：

> U-Boot启动Linux内核；Linux内核初始化完成后，再根据bootargs指定的位置挂载根文件系统。

------

### <span style="background:#00FF80;">根文件系统是什么？</span>

根文件系统就是你在开发板上执行：

```bash
ls /
```

看到的这些目录：

```text
/bin
/dev
/etc
/home
/lib
/proc
/root
/sbin
/sys
/tmp
/usr
/var
```

其中包括：

- Shell；
- `ls`、`cd`等命令；
- 动态链接库；
- 配置文件；
- 启动脚本；
- 用户程序；
- 系统服务。

Linux内核本身只负责核心资源管理，不自带完整的命令环境。

所以只有内核而没有根文件系统时，你不会获得正常的：

```text
[root@100ask:~]#
```

------

### 根文件系统会全部复制到DDR吗？

通常不会。

如果根文件系统位于eMMC的ext4分区，它一般是：

```text
Linux内核通过eMMC驱动访问根文件系统
按需读取文件
```

而不是启动时把整个根文件系统全部复制进DDR。

只有使用initramfs等方案时，根文件系统内容才可能作为压缩包进入内存并展开。Linux内核文档说明，内核可以解压initramfs到rootfs，并执行其中的`/init`作为PID 1；如果使用真实磁盘根文件系统，则后续会定位并挂载实际根设备。([Linux Kernel Documentation](https://docs.kernel.org/filesystems/ramfs-rootfs-initramfs.html?utm_source=chatgpt.com))

------

## 十一、第八阶段：运行第一个用户进程

根文件系统挂载成功以后，Linux内核会尝试运行第一个用户空间进程，例如：

```text
/sbin/init
/init
```

这个进程的PID通常是：

```text
1
```

它<span style="color:#FF0000; background:#00FF80;">负责继续启动用户空间</span>，例如：

- 挂载`/proc`和`/sys`；
- 创建设备节点；
- 配置网络；
- 启动后台服务；
- 执行启动脚本；
- 启动串口登录程序；
- 启动用户应用。

流程变成：

```text
Linux内核
   ↓
执行init，PID 1
   ↓
执行启动脚本
   ↓
启动各种服务
   ↓
启动串口getty/login
   ↓
显示登录界面
```

------

## 十二、最后出现登录提示

当你在串口中看到：

```text
100ask login:
```

说明以下步骤基本都成功了：

```text
Boot ROM成功
U-Boot成功
Linux内核成功
设备树基本可用
eMMC驱动成功
根文件系统挂载成功
init进程成功
串口登录服务成功
```

输入：

```text
root
```

登录以后看到：

```text
[root@100ask:~]#
```

这说明已经进入开发板Linux用户空间。

------

## 十三、eMMC中通常怎样存放这些东西？

一个简化的eMMC布局可能是：

```text
eMMC
├── 前部保留区域或裸扇区
│     └── U-Boot启动镜像
│
├── 分区1：FAT
│     ├── zImage
│     └── imx6ull-board.dtb
│
└── 分区2：ext4
      ├── bin/
      ├── etc/
      ├── lib/
      ├── root/
      ├── sbin/
      └── usr/
```

也可能把内核和设备树放在ext4、专用分区或其他位置，取决于厂商的镜像布局。

要特别注意：

> U-Boot不一定是一个能在文件系统中用`ls`看到的普通文件。

它经常直接烧写在eMMC开头的特定扇区或eMMC专用启动区域中，Boot ROM根据固定规则找到它。

------

## 十四、为什么不能上电后直接运行Linux？

<span style="color:#FF0000; background:#00FF80;">因为刚上电时：</span>

- DDR还没有配置；
- Linux内核还没有被加载到内存；
- 设备树还没有准备好；
- 内核不知道根文件系统在哪里；
- 各种时钟和外设未准备；
- Linux内核镜像太大，Boot ROM功能又非常有限。

所以需要分层：

```text
Boot ROM：
能力最小，但芯片内部永远存在
负责找到并启动U-Boot

U-Boot：
能力更强，可以识别存储、网络和文件系统
负责准备并启动Linux

Linux内核：
负责整个操作系统核心

根文件系统：
提供用户空间程序和服务
```

这是一种“一级启动下一级”的接力过程。

------

## 十五、哪里出错，对应什么现象？

| 停止位置           | 可能现象                                      | 常见原因                            |
| ------------------ | --------------------------------------------- | ----------------------------------- |
| Boot ROM之前       | 串口完全无输出                                | 电源、复位、硬件问题                |
| Boot ROM找不到镜像 | 无正常U-Boot输出，可能进入USB模式             | 拨码错误、eMMC无有效U-Boot          |
| DDR初始化失败      | U-Boot无法运行或很早崩溃                      | DCD、DDR参数、硬件问题              |
| U-Boot阶段         | 能看到U-Boot提示符，但Linux不启动             | 找不到zImage/DTB、bootcmd错误       |
| 内核早期           | 能看到Linux日志但中途停止                     | 设备树、驱动、内核配置问题          |
| 挂载根文件系统     | 出现`Kernel panic`、`Unable to mount root fs` | `root=`参数、分区、文件系统驱动错误 |
| 用户空间阶段       | 内核正常但无登录界面                          | init、启动脚本、getty配置问题       |
| 登录提示出现       | 基本启动完成                                  | 可以登录并使用系统                  |

## 十七、最适合记忆的版本

```text
第一棒：Boot ROM
芯片内部自带，负责从eMMC找到U-Boot。

第二棒：U-Boot
从eMMC加载到DDR，负责加载内核和设备树。

第三棒：Linux内核
在DDR中运行，负责初始化硬件、驱动和系统核心。

第四棒：根文件系统
保存在eMMC，提供命令、库、配置和应用。

最后：
内核运行init，启动服务，显示登录界面。
```

一句话概括：

> **上电以后，片内Boot ROM<span style="background:#00FF80;">先把U-Boot从eMMC搬到DDR</span>；U-Boot再<span style="background:#00FF80;">把Linux内核和设备树搬到DDR</span>；Linux内核启动后<span style="background:#00FF80;">挂载eMMC中的根文件系统</span>，运行init，最终进入可登录、可执行命令的完整Linux系统。**
