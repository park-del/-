# 视频分析：P72《在 STM32MP157 上做串口实验的准备工作》

这一节特别适合接着你前面“STM32 经验 → Linux 抽象”的思路来学。它本质上在告诉你：

> <span style="background:#00FF80;">**STM32 裸机里，你会直接把 UART8、PE0/PE1、复用功能这些东西写进初始化代码；Linux 则把这些“板级硬件信息”抽到 Device Tree 里，让已有 UART Driver 根据设备树去管理硬件。**</span>

视频时长约 **7 分 29 秒**。

## 1. 视频类型判断

主要类型：**Linux 设备树 + UART 实验准备教程**。次要类型：**驱动配置 / 板级资源分析**。

<span style="color:#FF0000; background:#00FF80;">这一节不是正式编写串口 APP，而是在解决：</span>

```text
开发板上明明有 UART8
        ↓
为什么 Linux 没有 /dev/ttySTM* 对应节点？
        ↓
怎样通过修改设备树让 Linux 把 UART8 用起来？
```

------

## 2. 一句话总结

> <span style="color:#FF0000; background:#00FF80;">**STM32MP157 板子上物理存在 UART8，但出厂设备树没有把扩展板 UART8 完整启用；因此需要确认 PE1/PE0 引脚 → enable UART8 节点 → 配置 pinctrl → 设置 serial alias → 重新编译 DTB → 替换设备树并重启，最终生成 `/dev/ttySTM3`。**</span>

## 4. 这一节真正解决了什么问题？

先建立一个<span style="color:#FF0000; background:#00FF80;">很关键的概念：</span>

<span style="background:#00FF80;">**硬件存在 ≠ Linux 一定会使用它。**</span>

STM32MP157 芯片内部本来就有：

```text
UART8 Controller
```

<span style="color:#FF0000;">开发板扩展接口也已经把：</span>

```text
UART8_TX
UART8_RX
```

<span style="color:#FF0000;">引出来了。</span>

<span style="color:#FF0000; background:#00FF80;">但是 Linux 启动以后，一开始只能看到类似：</span>

```text
/dev/ttySTM0
/dev/ttySTM1
```

<span style="color:#FF0000; background:#00FF80;">却看不到：</span>

```text
/dev/ttySTM3
```

<span style="color:#FF0000;">为什么？</span>

<span style="color:#FF0000; background:#00FF80;">不是因为：</span>

```text
芯片没有UART8
```

<span style="color:#FF0000; background:#00FF80;">也不一定是：</span>

```text
Linux没有UART8驱动
```

<span style="color:#FF0000; background:#00FF80;">而是：</span>

> <span style="color:#FF0000; background:#00FF80;">**当前 DTB 没有把板子上的 UART8 配置成一个可用设备。**</span>

整个关系：

```text
硬件已经存在
UART8
   │
   ▼
但是Device Tree：
status = "disabled"
   │
   ▼
Linux启动时不启用它
   │
   ▼
不会得到对应可用串口
```

## 5. 这个思想和 STM32 裸机特别好类比

<span style="color:#FF0000;">你以前写 STM32 UART，很可能会：</span>

```c
GPIO_Init(...);
USART_Init(...);
```

<span style="color:#FF0000;">或者 HAL：</span>

```c
HAL_UART_Init(&huart8);
```

其中<span style="color:#FF0000; background:#00FF80;">你必须自己告诉 MCU：</span>

```text
我要使用UART8

TX = PE1
RX = PE0

PE1切换成UART复用功能
PE0切换成UART复用功能

使能UART8时钟
设置波特率
……
```

<span style="color:#FF0000; background:#00FF80;">Linux 不希望每块开发板都去修改通用 UART Driver。</span>

<span style="color:#FF0000; background:#00FF80;">所以拆成：</span>

```text
         通用UART Driver
               │
               │
       “UART怎么操作？”
               │
               ▼
         STM32 UART硬件


        Device Tree
               │
               │
    “这块板子UART在哪里？
     用哪两个引脚？
     是否启用？”
```

这就是<span style="color:#FF0000; background:#00FF80;">特别典型的 Linux 分层。</span>

你<span style="background:#00FF80; color:#FF0000;">可以把 Device Tree 粗略类比成</span>：

> <span style="background:#00FF80; color:#FF0000;">**以前 STM32 BSP/HAL 初始化代码中那些“跟具体板子相关的配置”。**</span>

## 6. 第一步：确定硬件资源

视频大约 **02:30以后**开始查扩展板。

扩展板明确标出来：

```text
UART8_TX
UART8_RX
```

然后查底板原理图，发现：

```text
UART8_TX → PE1
UART8_RX → PE0
```

所以<span style="color:#FF0000; background:#00FF80;">从硬件角度：</span>

```text
STM32MP157

GPIOE Pin1
   │
   └── 可以复用为 UART8_TX

GPIOE Pin0
   │
   └── 可以复用为 UART8_RX
```

这一步特别像 STM32。

<span style="color:#FF0000; background:#00FF80;">如果你以前写：</span>

```c
GPIO_InitStruct.Pin = GPIO_PIN_1;
GPIO_InitStruct.Alternate = GPIO_AF8_UART8;
```

<span style="color:#FF0000; background:#00FF80;">Linux 这里做的事情本质上一样。</span>

<span style="color:#FF0000; background:#00FF80;">只是写法从 C 初始化代码变成了：</span>

```text
Device Tree + pinctrl
```

## 7. 第二步：为什么 `status = "disabled"` 很关键？

视频<span style="color:#FF0000; background:#00FF80;">展示 UART8 的基础节点：</span>

```dts
uart8: serial@40019000 {
    compatible = "st,stm32h7-uart";
    reg = <0x40019000 0x400>;
    ...
    clocks = <&rcc UART8_K>;
    resets = <&rcc UART8_R>;
    ...
    status = "disabled";
};
```

你暂时不用把所有字段都背下来。

<span style="color:#FF0000; background:#00FF80;">可以这样理解：</span>

```text
uart8
│
├── reg
│    UART8寄存器在哪
│
├── interrupts
│    UART8用哪个中断
│
├── clocks
│    UART8使用什么时钟
│
├── resets
│    UART8复位控制
│
├── dma
│    DMA资源
│
└── status = "disabled"
     默认不使用
```

这里<span style="color:#FF0000; background:#00FF80;">其实已经把很多你在 STM32 中熟悉的东西写出来了。</span>

比如：

### STM32：

```text
USART8寄存器基地址
IRQn
RCC时钟
DMA通道
```

### Linux Device Tree：

```text
reg
interrupts
clocks
dmas
```

是不是一下就熟悉很多了？

## 8. `compatible = "st,stm32h7-uart"` 又是什么意思？

这个很值得你提前理解。

它<span style="color:#FF0000; background:#00FF80;">大概是在告诉 Linux：</span>

> <span style="color:#FF0000; background:#00FF80;">**“我是 ST 这一类 UART 硬件，找能够支持 `st,stm32h7-uart` 的驱动来管理我。”**</span>

所以：

```text
Device Tree UART8节点
       │
       │ compatible
       ▼
Linux寻找匹配的UART Driver
       │
       ▼
驱动接管UART8
```

这也是<span style="color:#FF0000; background:#00FF80;">为什么前面说：</span>

> <span style="color:#FF0000; background:#00FF80;">当前问题并不是“从头写一个 UART8 Driver”。</span>

<span style="background:#00FF80; color:#FF0000;">STM32MP157 内核本来就已经有支持这类 UART 控制器的驱动</span>。

现在缺的是：

> <span style="background:#00FF80; color:#FF0000;">**告诉现有驱动：这块板子还要使用 UART8。**</span>

## 9. 第三步：`&uart8 { status = "okay"; }`

基础 `.dtsi` 里面：

```text
UART8存在
但是
disabled
```

板级 DTS 可以覆盖：

```dts
&uart8 {
    ...
    status = "okay";
};
```

<span style="color:#FF0000; background:#00FF80;">含义非常直白：</span>

```text
&uart8
 ↓
引用之前定义好的UART8节点

status = "okay"
 ↓
这块板子要启用它
```

可以<span style="color:#FF0000; background:#00FF80;">把它类比 STM32：</span>

```c
__HAL_RCC_UART8_CLK_ENABLE();

HAL_UART_Init(&huart8);
```

当然底层实现不是完全等价，但学习上可以这么建立直觉：

> <span style="color:#FF0000; background:#00FF80;">**`status = "okay"` 就相当于板级配置明确告诉 Linux：“这个硬件在本板上是存在且需要工作的。”**</span>

------

## 10. 但是只写 `status = "okay"` 为什么还不够？

因为：

> <span style="background:#00FF80; color:#FF0000;">**UART8 控制器可以工作，不代表 PE0、PE1 已经连接到 UART8。**</span>

<span style="color:#FF0000;">STM32 的引脚往往是复用的</span>。

<span style="color:#FF0000; background:#00FF80;">PE1 可能可以干：</span>

```text
GPIO
UART
SPI
定时器
……
```

所以<span style="color:#FF0000; background:#00FF80;">还必须告诉芯片：</span>

```text
PE1 → UART8_TX
PE0 → UART8_RX
```

<span style="color:#FF0000; background:#00FF80;">于是就有：</span>

### `pinctrl`

## 11. `pinctrl` 可以直接类比 STM32 GPIO Alternate Function

视频中：

```dts
&uart8 {
    pinctrl-names = "default", "sleep";
    pinctrl-0 = <&uart8_pins_mx>;
    pinctrl-1 = <&uart8_sleep_pins_mx>;
    status = "okay";
};
```

然后 <span style="color:#FF0000; background:#00FF80;">pinctrl 节点里：</span>

```dts
pinmux = <STM32_PINMUX('E', 1, AF8)>; /* UART8_TX */
```

<span style="color:#FF0000; background:#00FF80;">以及：</span>

```dts
pinmux = <STM32_PINMUX('E', 0, AF8)>; /* UART8_RX */
```

这里<span style="color:#FF0000; background:#00FF80;">你用 STM32 经验理解最好：</span>

```text
STM32裸机：

PE1
 ↓
GPIO Alternate Function
 ↓
AF8
 ↓
UART8_TX


Linux：

PE1
 ↓
pinctrl
 ↓
AF8
 ↓
UART8_TX
```

<span style="color:#FF0000; background:#00FF80;">基本就是同一件硬件事情。</span>

# 12. 为什么有 `default` 和 `sleep` 两套 pinctrl？

视频里还能看到：

```text
default
sleep
```

正常工作：

```text
default
 ↓
PE1 → UART8_TX
PE0 → UART8_RX
```

进入低功耗状态时：

```text
sleep
 ↓
把引脚调整为适合低功耗的状态
例如 Analog 等
```

所以：

```text
pinctrl-0
= 正常运行怎么配置引脚

pinctrl-1
= sleep状态怎么配置引脚
```

这个也是 Linux 比普通 STM32 小实验做得更完整的地方。

因为操作系统还考虑：

```text
Suspend
Resume
Power Management
```

# 13. 第四步：`aliases` 为什么会影响 `/dev/ttySTM3`？

视频大约 **06:00** 展示：

```dts
aliases {
    ethernet0 = &ethernet0;

    serial0 = &uart4;   // debug
    serial1 = &usart6;  // rs485
    serial2 = &usart1;  // bluetooth
    serial3 = &uart8;   // extend board uart, /dev/ttySTM3
};
```

这里最值得注意：

```text
serial3 = &uart8
```

它是在告诉系统：

> **UART8 在这套板级串口编号关系里作为 serial3。**

因此最终对应：

```text
/dev/ttySTM3
```

所以注意：

```text
UART8
```

不意味着一定叫：

```text
ttySTM8
```

这是很多初学者特别容易误会的地方。

硬件编号：

```text
UART8
```

和 Linux 设备节点编号：

```text
ttySTM3
```

是两个概念。

可以类比：

```text
硬件身份：
UART8

Linux逻辑编号：
serial3

设备节点：
/dev/ttySTM3
```

现在你终于可以看到：

```text
/dev/ttySTM3
```

到底是怎么来的。

不是开发人员随便：

```bash

```

创建的普通文件。

而大致经过：

```text
Device Tree：
serial3 = &uart8
status = "okay"

        ↓
Kernel启动
        ↓
Device Tree解析
        ↓
匹配STM32 UART Driver
        ↓
驱动probe
        ↓
UART8注册进TTY/Serial Core
        ↓

        ↓
/dev/ttySTM3
```

这一下就把前面几节串起来了：

```text
Device Tree
    ↓
UART Driver
    ↓
TTY subsystem
    ↓
/dev/ttySTM3
    ↓
APP
```

# 15. 为什么 `/dev/ttySTM3` 属于 TTY，而不是直接“UART文件”？

因为你上一节刚学：

```text
APP
 ↓
TTY Core
 ↓
Line Discipline
 ↓
UART Driver
 ↓
UART Hardware
```

所以：

```text
/dev/ttySTM3
```

其实是：

> **UART8 这个物理串口经过 Linux TTY/Serial 子系统后暴露给用户空间的设备接口。**

例如未来：

```c
fd = open("/dev/ttySTM3", O_RDWR);
```

真正链路：

```text
APP
 ↓
/dev/ttySTM3
 ↓
fd
 ↓
TTY Core
 ↓
Line Discipline
 ↓
STM32 UART Driver
 ↓
UART8
 ↓
PE1 / PE0
 ↓
外部模块
```

这一节其实正好补上了以前链条里的：

> “`/dev/ttySTM3` 是怎么被创造出来的？”

# 17. DTB 是什么？

这里顺便帮你区分：

你编辑的是：

```text
.dts
.dtsi
```

它们是人可以看的设备树源码。

例如：

```dts
&uart8 {
    status = "okay";
};
```

经过编译以后：

```text
DTS/DTSI
   ↓
Device Tree Compiler
   ↓
DTB
```

得到：

```text
stm32mp157c-100ask-512d-lcd-v1.dtb
```

这个：

```text
.dtb
```

才是启动时真正交给 Linux Kernel 使用的二进制设备树。

你可以类比：

```text
C源码
 ↓
gcc
 ↓
ELF
```

和：

```text
DTS源码
 ↓
dtc / kernel build
 ↓
DTB
```

# 18. `make dtbs` 是干什么？

视频最后：

```bash
make dtbs
```

不是重新完整编译整个 Linux 内核。

它的主要目的：

> **重新编译设备树。**

所以：

```text
修改 .dts/.dtsi
      ↓
make dtbs
      ↓
生成新的 .dtb
```

然后把新 DTB 替换到：

```text
/boot
```

重启时：

```text
Bootloader
 ↓
加载Kernel
+
加载新的DTB
 ↓
Linux按照新硬件配置启动
```

# 19. 视频里的 NFS 在这里是什么作用？

这里不要把 NFS 跟 UART 混起来。

NFS 只是：

> **为了方便把 Ubuntu 上刚编译出来的 DTB 文件传给开发板。**

例如：

```text
Ubuntu
新的DTB
   ↓
NFS共享目录
   ↓
开发板 mount
   ↓
/mnt
   ↓
复制到 /boot
```

相当于一个开发阶段的“文件传输桥梁”。

真正 UART 是否工作跟 NFS 本身没有关系。

# 20. 用 STM32 思维把整节课翻译一遍

这是我觉得你最值得记住的部分。

假如这是 STM32 裸机，你可能会写：

```text
① 看原理图
   ↓
UART8 TX = PE1
UART8 RX = PE0

② 使能UART8
   ↓
RCC

③ 配置GPIO
   ↓
PE1 AF8
PE0 AF8

④ 初始化UART
   ↓
HAL_UART_Init()

⑤ 开始发送接收
```

而 Linux：

```text
① 看原理图
   ↓
UART8 TX = PE1
UART8 RX = PE0

② Device Tree
   ↓
&uart8
status = "okay"

③ pinctrl
   ↓
PE1 AF8
PE0 AF8

④ aliases
   ↓
serial3 = &uart8

⑤ make dtbs + 重启
   ↓
驱动匹配、注册

⑥ /dev/ttySTM3
   ↓
APP open/read/write
```

你会发现：

> **硬件层面的事情根本没变，只是“谁负责描述和执行”变了。**

# 21. Linux 比 STM32 多出来的抽象在哪？

STM32：

```text
你的代码
 ↓
HAL / 寄存器
 ↓
UART8
```

Linux：

```text
用户APP
 ↓
TTY
 ↓
UART Driver
 ↓
UART8


Device Tree
 ↓
告诉Driver：
UART8在哪
用哪些Pins
IRQ是什么
Clock是什么
是否启用
```

所以 Linux 最大的不同是把：

```text
“硬件是什么”
```

和：

```text
“硬件怎么操作”
```

拆开了。

Device Tree：

```text
描述硬件
```

Driver：

```text
操作这一类硬件
```

这个思想你以后学：

```text
GPIO
I2C
SPI
LCD
网卡
USB
```

都会反复遇到。

如果你以前写：

```text
    ↓
切换成 Alternate Function 8

 ↓
```

```text
 ↓
AF8
 ↓
UART8_TX
```

## 那 Device Tree 到底是什么？

你可以先把它理解成：

> <span style="color:#FF0000; background:#00FF80;">**Linux 的“硬件说明书”。**</span>

它<span style="color:#FF0000; background:#00FF80;">主要告诉 Linux：</span>

```text
这块板子上有什么硬件？
硬件的寄存器地址是多少？
IRQ是多少？
使用什么时钟？
用了哪些GPIO？
引脚怎么复用？
DMA是什么？
这个设备要不要启用？
```

比如 <span style="color:#FF0000; background:#00FF80;">UART8 设备树节点：</span>

```dts
uart8: serial@40019000 {
    compatible = "st,stm32h7-uart";
    reg = <0x40019000 0x400>;
    interrupts = <...>;
    clocks = <&rcc UART8_K>;
    status = "disabled";
};
```

你<span style="color:#FF0000; background:#00FF80;">可以把它翻译成人话：</span>

```text
serial@40019000
=
这里有一个串口控制器

reg
=
它的寄存器在 0x40019000

interrupts
=
它用哪个中断

clocks
=
它依赖哪个时钟

compatible
=
应该找哪一类驱动来管理它

status
=
这块板子现在要不要启用它
```

------

## 为什么 <span style="background:#00FF80; color:#FF0000;">Linux 要专门搞 Device Tree？</span>

<span style="color:#FF0000;">因为 Linux 内核代码要尽量做到：</span>

> <span style="color:#FF0000; background:#00FF80;">**同一个驱动，可以支持很多块板子。**</span>

假设<span style="color:#FF0000;">有两块 STM32MP157 板子。</span>

A 板：

```text
UART8_TX = PE1
UART8_RX = PE0
```

B 板可能：

```text
UART8_TX = PJ8
UART8_RX = PJ9
```

<span style="color:#FF0000; background:#00FF80;">如果不用设备树，你可能只能在 UART 驱动里写：</span>

```c
if (board_A) {
    configure_PE1_PE0();
}

if (board_B) {
    configure_PJ8_PJ9();
}
```

<span style="color:#FF0000; background:#00FF80;">板子越来越多以后：</span>

```text
UART Driver
里面塞满
各种板子的GPIO
各种板子的地址
各种板子的IRQ
各种特殊配置
```

<span style="color:#FF0000; background:#00FF80;">会非常乱。</span>

于是 <span style="color:#FF0000; background:#00FF80;">Linux 把它拆成：</span>

```text
Driver
=
“这种UART怎么操作”

Device Tree
=
“这块板子具体怎么连接”
```

这就是<span style="color:#FF0000; background:#00FF80;">非常重要的分离。</span>

这就是 <span style="color:#FF0000; background:#00FF80;">Device Tree 最核心的价值。</span>

## Device Tree 在 Linux 里对应什么文件？

主要有三种你会看到的东西：

```text
.dts
.dtsi
.dtb
```

它们关系是：

```text
.dts / .dtsi
      ↓
设备树源码
      ↓
编译
      ↓
.dtb
      ↓
Device Tree Blob
二进制设备树
```

很像：

```text
.c
 ↓
gcc
 ↓
.o / ELF
```

------

### `.dts` 是什么？

DTS：

**Device Tree Source**

通常描述：

> <span style="color:#FF0000; background:#00FF80;">**某一块具体开发板。**</span>

例如可能看到：

```text
stm32mp157c-100ask-512d-lcd-v1.dts
```

<span style="color:#FF0000; background:#00FF80;">这种文件。</span>

<span style="color:#FF0000; background:#00FF80;">里面会写：</span>

```dts
&uart8 {
    pinctrl-names = "default";
    pinctrl-0 = <&uart8_pins_mx>;
    status = "okay";
};
```

意思就是：

> <span style="color:#FF0000; background:#00FF80;">这块具体开发板要启用 UART8，并使用这些引脚。</span>

------

## `.dtsi` 是什么？

DTSI：

可以理解成：

<span style="background:#00FF80;">**被多个 `.dts` 共用的设备树公共文件。**</span>

例如 STM32MP157 这个 SoC 天生就有：

```text
UART1
UART2
UART4
UART8
I2C
SPI
GPIO
Timer
……
```

<span style="color:#FF0000; background:#00FF80;">这些跟“具体哪块开发板”无关。</span>

所以<span style="color:#FF0000; background:#00FF80;">可以放在：</span>

```text
stm32mp157.dtsi
```

<span style="background:#00FF80;">类似的公共文件里。</span>

<span style="background:#00FF80;">比如：</span>

```dts
uart8: serial@40019000 {
    reg = <0x40019000 0x400>;
    clocks = <&rcc UART8_K>;
    status = "disabled";
};
```

意思是：

> <span style="background:#00FF80;">STM32MP157 芯片本身确实有 UART8。</span>

至于<span style="color:#FF0000; background:#00FF80;">某块板子到底用不用：</span>

再<span style="background:#00FF80;">由 `.dts` 决定。</span>

------

所以<span style="color:#FF0000; background:#00FF80;">可以理解成：</span>

```text
SoC公共描述
stm32mp157.dtsi
       │
       │ “芯片有什么”
       ▼

板级描述
xxx-board.dts
       │
       │ “这块板子用了哪些”
       ▼

最终DTB
```

------

## `.dtb` 又是什么？

`.dtb` 是：

**Device Tree Blob**

也就是<span style="color:#FF0000; background:#00FF80;">编译后的二进制设备树。</span>

<span style="color:#FF0000; background:#00FF80;">人主要编辑：</span>

```text
.dts
.dtsi
```

<span style="background:#00FF80;">Linux 启动时真正读取：</span>

```text
.dtb
```

<span style="color:#FF0000; background:#00FF80;">流程：</span>

```text
修改 .dts/.dtsi
       ↓
make dtbs
       ↓
生成 .dtb
       ↓
放进 /boot
       ↓
Bootloader加载
       ↓
交给Linux Kernel
```

------

## <span style="color:#FF0000; background:#00FF80;">Linux 启动时设备树是怎么被使用的？</span>

<span style="color:#FF0000; background:#00FF80;">这条链非常重要：</span>

```text
开发板上电
   ↓
U-Boot
   ↓
加载 Kernel
   +
加载 DTB
   ↓
启动 Linux
   ↓
Kernel解析 DTB
   ↓
发现：
“这里有一个UART8”
   ↓
compatible匹配驱动
   ↓
调用对应UART Driver
   ↓
驱动读取：
寄存器地址
IRQ
clock
pinctrl
……
   ↓
初始化UART
```

<span style="color:#FF0000; background:#00FF80;">最后可能：</span>

```text
UART8
 ↓
注册到 Serial Core / TTY
 ↓
生成
/dev/ttySTM3
```

所以<span style="background:#00FF80;">设备树不是“程序执行逻辑”。</span>

它更像：

> <span style="background:#00FF80; color:#FF0000;">**一份数据结构化硬件配置表。**</span>

<span style="background:#00FF80;">真正执行：</span>

```text
写寄存器
申请IRQ
开时钟
设置引脚
```

的是<span style="color:#FF0000; background:#00FF80;"> Linux 内核里的各种驱动。</span>

------

## pinctrl 又是什么？

`pinctrl` 可以理解成 Linux 的：

> <span style="background:#00FF80;">**引脚复用和引脚电气属性管理子系统。**</span>

你 <span style="color:#FF0000; background:#00FF80;">STM32 非常熟悉：</span>

```text
某一个引脚
可能是：
GPIO
UART_TX
SPI_MOSI
TIM_CH
I2C_SCL
……
```

<span style="color:#FF0000; background:#00FF80;">所以必须选：</span>

```text
Alternate Function
```

<span style="color:#FF0000; background:#00FF80;">Linux 中：</span>

```text
Device Tree
 ↓
pinctrl配置
 ↓
Pinctrl Driver
 ↓
真正修改SoC寄存器
```

<span style="color:#FF0000; background:#00FF80;">例如：</span>

```dts
pinmux = <STM32_PINMUX('E', 1, AF8)>;
```

<span style="color:#FF0000; background:#00FF80;">实际最终效果仍然是：</span>

```text
修改某个 pinmux 寄存器
 ↓
把 PE1 连接到 UART8_TX
```

跟 STM32：

```c
GPIO_InitStruct.Alternate = GPIO_AF8_UART8;
```

<span style="background:#00FF80; color:#FF0000;">最终做的是同一件硬件操作。</span>

## 但是注意：<span style="background:#00FF80;">并不是 STM32 所有 UART 初始化代码都搬进 Device Tree</span>

这个特别重要。

比如 STM32：

```c
BaudRate = 115200;
WordLength = 8;
StopBits = 1;
Parity = None;
```

这些属于：

> <span style="background:#00FF80;">**UART运行时通信参数。**</span>

<span style="color:#FF0000; background:#00FF80;">Linux 通常不是都固定写进设备树。</span>

用户程序以后可以：

```text
termios
 ↓
配置：
115200
8N1
```

然后：

```text
APP
 ↓
TTY
 ↓
UART Driver
 ↓
修改UART寄存器
```

所以<span style="color:#FF0000; background:#00FF80;">可以分成：</span>

### Device Tree 负责

```text
UART硬件在哪里
IRQ是多少
Clock是谁
TX/RX用哪些Pin
这个设备是否存在/启用
```

### Driver 负责

```text
如何操作UART寄存器
如何处理中断
如何发数据
如何收数据
```

### APP / TTY配置负责

```text
波特率
数据位
停止位
校验
Raw/Canonical
```

<span style="background:#00FF80; color:#FF0000;">这三个层次一定要分开。</span>

## 一、设备树中的“节点”到底是什么？

这个最重要。

<span style="color:#FF0000;">看到这种结构：</span>

```dts
uart8: serial@40019000 {
    ...
};
```

<span style="background:#00FF80; color:#FF0000;">整个：</span>

```dts
serial@40019000 {
    ...
};
```

就是<span style="background:#00FF80;">一个**节点 Node**。</span>

最基本语法：

```dts
节点名字 {
    属性1;
    属性2;
    属性3;

    子节点1 {
        ...
    };

    子节点2 {
        ...
    };
};
```

<span style="color:#FF0000; background:#00FF80;">所以设备树真的就是：</span>

```text
根节点
│
├── CPU节点
│
├── memory节点
│
├── GPIO节点
│
├── UART节点
│
│    ├── 属性
│
│    └── 子节点
│
├── I2C节点
│    ├── I2C设备A
│    └── I2C设备B
│
└── SPI节点
```

<span style="color:#FF0000; background:#00FF80;">比如非常简化地：</span>

```dts
/ {
    cpus {
        cpu@0 {
        };
    };

    memory@c0000000 {
    };

    soc {
        serial@40019000 {
        };

        i2c@40012000 {
        };
    };
};
```

这就真的是一棵：

```text
/
├── cpus
│   └── cpu@0
├── memory@c0000000
└── soc
    ├── serial@40019000
    └── i2c@40012000
```

所以<span style="background:#00FF80;">“树”不是比喻，它的数据组织方式真的就是**父节点 → 子节点 → 子节点**。</span>

------

## 二、逐句拆你的 UART8 节点

你贴的是：

```dts
uart8: serial@40019000 {
    compatible = "st,stm32h7-uart";
    reg = <0x40019000 0x400>;
    interrupts = <...>;
    clocks = <&rcc UART8_K>;
    status = "disabled";
};
```

我们一句一句来。

------

### 1. `uart8:`

```dts
uart8:
```

这个叫：

**label，标签。**

你可以把它理解成：

> <span style="color:#FF0000; background:#00FF80;">给这个节点起了一个方便其他地方引用的“变量名”。</span>

例如<span style="color:#FF0000; background:#00FF80;">完整节点：</span>

```dts
uart8: serial@40019000 {
};
```

<span style="color:#FF0000; background:#00FF80;">其中：</span>

```text
uart8
↓
label
```

以后<span style="color:#FF0000; background:#00FF80;">别的地方就能写：</span>

```dts
&uart8 {
    status = "okay";
};
```

<span style="color:#FF0000; background:#00FF80;">其中：</span>

```text
&uart8
```

就是：

> <span style="background:#00FF80;">找到 label 叫 `uart8` 的那个节点。</span>

很像 C：

```c
UART_Config uart8;
```

后面：

```c
uart8.xxx = ...
```

当然不是完全相同，但这个类比很好理解。

------

### 2.`serial@40019000`

<span style="background:#00FF80;">这一部分才是：</span>

**节点名称 node name。**

```dts
serial@40019000
```

<span style="color:#FF0000; background:#00FF80;">拆成：</span>

```text
serial
   +
@40019000
```

<span style="background:#00FF80; border:1px solid #330000;">其中：</span>

```text
serial
```

<span style="color:#FF0000; background:#00FF80;">说明这是一个：</span>

<span style="background:#00FF80;">**serial 串行控制器类型节点。**</span>

而：

```text
40019000
```

<span style="color:#FF0000; background:#00FF80;">是：</span>

**unit-address，单元地址。**

<span style="color:#FF0000; background:#00FF80;">通常跟这个设备的寄存器起始地址有关。</span>

所以：

```dts
serial@40019000
```

<span style="background:#00FF80; color:#FF0000;">可以粗略理解：</span>

> <span style="background:#00FF80;">一个寄存器基地址在 `0x40019000` 附近的串口控制器。</span>

这<span style="background:#00FF80; color:#FF0000;">和 STM32 特别像。</span>

<span style="color:#FF0000; background:#00FF80;">例如裸机里：</span>

```c
#define UART8_BASE 0x40019000
```

<span style="border:1px solid #330000; color:#FF0000; background:#00FF80;">设备树里则：</span>

```dts
serial@40019000
```

------

### 3. `{ ... }`

```dts
{
    ...
};
```

<span style="background:#00FF80; color:#FF0000;">大括号里面</span>就是：

> <span style="background:#00FF80; color:#FF0000;">**这个节点具有的属性和子节点。**</span>

所以：

```dts
serial@40019000 {
    compatible = ...;
    reg = ...;
    clocks = ...;
};
```

<span style="color:#FF0000; background:#00FF80;">意思就是：</span>

```text
UART8节点
│
├── compatible
├── reg
├── interrupts
├── clocks
└── status
```

<span style="color:#FF0000; background:#00FF80;">这些都叫：</span>

**property 属性。**

------

## 三、<span style="background:#00FF80;">`compatible`</span>

```dts
compatible = "st,stm32h7-uart";
```

这个特别重要。

可以翻译成：

> <span style="color:#FF0000; background:#00FF80;">“我是一个 ST 的 STM32H7 类型 UART 控制器。”</span>

主要作用：

> **让 Linux 找到能够管理这个硬件的驱动。**

<span style="color:#FF0000; background:#00FF80;">驱动代码里可能会有类似：</span>

```c
static const struct of_device_id stm32_uart_match[] = {
    { .compatible = "st,stm32h7-uart" },
    ...
};
```

<span style="color:#FF0000; background:#00FF80;">然后 Linux：</span>

```text
Device Tree

compatible =
"st,stm32h7-uart"
       │
       ▼
寻找支持这个compatible的Driver
       │
       ▼
STM32 UART Driver
```

所以：

```dts
compatible
```

你可以理解为：

> **<span style="color:#FF0000; background:#00FF80;">设备树节点和驱动程序之间的“匹配身份证”</span>。**

------

## 四、`reg = <0x40019000 0x400>;`

这句特别值得你用 STM32 思维理解。

```dts
reg = <0x40019000 0x400>;
```

<span style="color:#FF0000; background:#00FF80;">粗略可以理解为：</span>

```text
寄存器物理起始地址：
0x40019000

寄存器区域大小：
0x400 Byte
```

也就是：

```text
0x40019000
      ↓
┌─────────────────────┐
│ UART8 registers     │
│                     │
│ 大小 0x400          │
└─────────────────────┘
```

<span style="color:#FF0000; background:#00FF80;">STM32 裸机里你以前可能直接有：</span>

```c
UART8->CR1
UART8->BRR
UART8->ISR
UART8->RDR
UART8->TDR
```

<span style="color:#FF0000; background:#00FF80;">而 `UART8` 其实背后就是从：</span>

```text
0x40019000
```

<span style="color:#FF0000; background:#00FF80;">这个寄存器基地址开始。</span>

<span style="color:#FF0000;">Linux 设备树则告诉驱动：</span>

> “UART8 的 MMIO 寄存器就在这里。”

<span style="color:#FF0000; background:#00FF80;">驱动后面会做映射，然后访问寄存器。</span>

------

### `< >` 是什么？

设备树里的：

```dts
< ... >
```

通常表示：

<span style="background:#00FF80;">**一个或多个 32-bit cell 数值。**</span>

所以：

```dts
reg = <0x40019000 0x400>;
```

里面<span style="color:#FF0000; background:#00FF80;">有两个 cell：</span>

```text
cell 1 = 0x40019000
cell 2 = 0x400
```

但<span style="color:#FF0000; background:#00FF80;">这里有个进阶点：</span>

> <span style="background:#00FF80; color:#FF0000;">`reg` 里到底几个数代表地址、几个代表长度，由父节点的 `#address-cells` 和 `#size-cells` 决定。</span>

你<span style="color:#FF0000; background:#00FF80;">现阶段先把这条记成：</span>

```text
reg ≈ 地址 + 大小
```

完全够用了。

------

## 五、`interrupts = <...>;`

```dts
interrupts = <...>;
```

表示：

> <span style="background:#00FF80; color:#FF0000;">**这个硬件使用哪个中断。**</span>

比如<span style="color:#FF0000; background:#00FF80;"> STM32 裸机你以前会：</span>

```c
HAL_NVIC_SetPriority(UART8_IRQn, ...);
HAL_NVIC_EnableIRQ(UART8_IRQn);
```

<span style="color:#FF0000; background:#00FF80;">里面有：</span>

```text
UART8_IRQn
```

<span style="color:#FF0000; background:#00FF80;">Linux 设备树里就是类似：</span>

```dts
interrupts = <...>;
```

<span style="color:#FF0000; background:#00FF80;">去描述：</span>

```text
UART8
 ↓
对应哪个硬件IRQ
```

然后 <span style="color:#FF0000; background:#00FF80;">UART Driver 在 `probe()` 时会读取这个中断资源并注册：</span>

```text
request_irq(...)
```

<span style="color:#FF0000; background:#00FF80;">所以：</span>

```text
STM32：
UART8_IRQn 写在代码/头文件里

Linux：
interrupts 写在 Device Tree
Driver读取
```

------

## 六、`clocks = <&rcc UART8_K>;`

这句比前面复杂一点：

```dts
clocks = <&rcc UART8_K>;
```

<span style="color:#FF0000; background:#00FF80;">可以拆成：</span>

```text
&rcc
+
UART8_K
```

<span style="background:#00FF80;">`&rcc`：</span>

> <span style="background:#00FF80; color:#FF0000;">引用 label 为 `rcc` 的 Clock Controller 节点。</span>

<span style="color:#FF0000; background:#00FF80;">可能有：</span>

```dts
rcc: rcc@50000000 {
    ...
};
```

<span style="color:#FF0000; background:#00FF80;">那么：</span>

```dts
&rcc
```

就是指向它。

<span style="color:#FF0000; background:#00FF80;">而：</span>

```text
UART8_K
```

表示：

> <span style="background:#00FF80; color:#FF0000;">RCC 里面 UART8 对应的某个时钟标识。</span>

所以整句话：

```dts
clocks = <&rcc UART8_K>;
```

<span style="color:#FF0000; background:#00FF80;">大概意思：</span>

> UART8 的工作时钟由 RCC 提供，具体使用 RCC 中编号/标识为 `UART8_K` 的时钟。

你<span style="color:#FF0000; background:#00FF80;">用 STM32 裸机类比：</span>

```c
__HAL_RCC_UART8_CLK_ENABLE();
```

非常合适。

但是<span style="color:#FF0000; background:#00FF80;">要注意：</span>

<span style="background:#00FF80;">设备树只是告诉 Linux：</span>

```text
UART8的clock是谁
```

<span style="background:#00FF80;">真正：</span>

```text
使能clock
配置clock
```

<span style="color:#FF0000; background:#00FF80;">还是 Clock Driver + UART Driver 去做。</span>

------

## 七、`status = "disabled";`

这个最好理解：

```dts
status = "disabled";
```

意思：

> 这个节点虽然描述出来了，但是当前默认不启用。

所以：

```text
STM32MP157 SoC
确实有 UART8
       ↓
Device Tree也描述了 UART8
       ↓
但是
status = disabled
       ↓
具体板子默认不用它
```

<span style="color:#FF0000; background:#00FF80;">具体开发板需要它：</span>

```dts
&uart8 {
    status = "okay";
};
```

这样<span style="background:#00FF80;">就覆盖为：</span>

```text
enabled
```

所以 <span style="color:#FF0000; background:#00FF80;">`.dtsi` 可以写：</span>

```dts
uart8: serial@40019000 {
    ...
    status = "disabled";
};
```

意思：

> <span style="color:#FF0000; background:#00FF80;">芯片里有它，但是具体开发板用不用，我不知道。</span>

而<span style="background:#00FF80;">具体 `.dts`：</span>

```dts
&uart8 {
    status = "okay";
};
```

意思：

> 100ASK 这块板子我要用 UART8。

这<span style="color:#FF0000; background:#00FF80;">就是 SoC 公共描述和板级描述拆开的好处。</span>

## 九、第一层节点


拆开：

```text
↓

node name
```

## 十、`pins1 { ... };`


这是：

## 十一、`pinmux = <STM32_PINMUX('E', 1, AF8)>;`

这个就是你 STM32 最熟悉的部分。

拆开：

```text
'E'
↓
GPIOE

1
↓
Pin 1

AF8
↓
Alternate Function 8
```

<span style="color:#FF0000; background:#00FF80;">所以：</span>

```dts
STM32_PINMUX('E', 1, AF8)
```

<span style="color:#FF0000; background:#00FF80;">表示：</span>

> <span style="background:#00FF80;">PE1 配成 AF8。</span>

如果<span style="background:#00FF80; color:#FF0000;"> STM32 datasheet 规定：</span>

```text
PE1 + AF8
=
UART8_TX
```

<span style="color:#FF0000; background:#00FF80;">那么最终：</span>

```text
PE1
 ↓
AF8
 ↓
UART8_TX
```

<span style="background:#00FF80;">这和 STM32：</span>

```c
GPIO_InitStruct.Pin = GPIO_PIN_1;
GPIO_InitStruct.Alternate = GPIO_AF8_UART8;
```

几乎就是<span style="color:#FF0000; background:#00FF80;">同一个硬件意图。</span>

## 十二、`STM32_PINMUX(...)` 是什么？

它<span style="background:#00FF80;">看起来很像 C 宏</span>，是因为<span style="background:#00FF80; color:#FF0000;">它确实通常由设备树头文件里类似宏定义辅助编码。</span>

最终：

```dts
STM32_PINMUX('E', 1, AF8)
```

<span style="color:#FF0000; background:#00FF80;">会被预处理/编译成一个整数值。</span>

<span style="color:#FF0000; background:#00FF80;">这个整数里面编码：</span>

```text
Port E
Pin 1
AF8
```

<span style="color:#FF0000; background:#00FF80;">然后 STM32 pinctrl 驱动解析它。</span>

所以：

```text
DTS
 ↓
STM32_PINMUX(...)
 ↓
编码值
 ↓
Pinctrl Driver
 ↓
修改 STM32 PinMux 寄存器
```

## 十三、那<span style="background:#00FF80; color:#FF0000;"> UART8 节点怎么引用 pinctrl？</span>

<span style="color:#FF0000; background:#00FF80;">通常还会看到：</span>


也就是：

```text
       ↓

       ↓

```

### `pinctrl-names`

### `pinctrl-1`

## 十四、这整棵树可以怎么想？

<span style="color:#FF0000; background:#00FF80;">把相关部分抽出来：</span>

```text
Device Tree
│
├── RCC
│     label = rcc
│
├── UART8
│     label = uart8
│     reg = 0x40019000
│     interrupt = ...
│     clock = RCC/UART8_K
│     status = okay
│     pinctrl-0 ───────────────┐
│                              │
└── pinctrl                    │
      │                        │
      └── uart8-pins ◀─────────┘
            │
            └── pins1
                 │
                 └── PE1 AF8
```

你<span style="color:#FF0000; background:#00FF80;">会发现 Device Tree 很像一张：</span>

> <span style="background:#00FF80; color:#FF0000;">**硬件对象 + 硬件资源 + 对象之间引用关系的图/树。**</span>

------

## 十五、你最后的 STM32 类比：方向对，但不能直接等号

你说：

> <span style="color:#FF0000; background:#00FF80;">“是不是可以认为设备树做的就是 STM32 中各种 Init 初始化的工作？”</span>

这个<span style="background:#00FF80; color:#FF0000;">理解**有帮助</span>，<span style="background:#00FF80;">但要改成：设备树描述 Init 所需要的信息，而不是设备树自己执行 Init。</span>**

这是最重要的区别。

STM32 裸机：

```c
MX_USART8_UART_Init();
```

<span style="color:#FF0000; background:#00FF80;">这个 Init 函数里面可能真正执行：</span>

```text
使能Clock
↓
配置PinMux
↓
写UART寄存器
↓
设置115200
↓
开中断
```

<span style="color:#FF0000; background:#00FF80;">所以：</span>

```text
STM32 Init函数
=
描述 + 执行
往往混在C代码里
```

<span style="color:#FF0000; background:#00FF80;">Linux Device Tree：</span>

```text
Device Tree
=
只描述：

UART在哪里
IRQ是谁
Clock是谁
Pin是谁
是否启用
```

<span style="color:#FF0000; background:#00FF80;">然后：</span>

```text
Linux Driver
=
真正执行初始化
```

<span style="color:#FF0000; background:#00FF80;">完整：</span>

```text
Device Tree
“UART8在这里，
用PE1/PE0，
IRQ是xxx，
clock是xxx”
       │
       ▼
UART Driver probe()
       │
       ├── 获取reg
       ├── ioremap
       ├── 获取IRQ
       ├── request_irq
       ├── 获取clock
       ├── enable clock
       ├── 应用pinctrl
       └── 注册UART
```

<span style="border:1px solid #330000; background:#00FF80; color:#FF0000;">所以你的 STM32 `Init()`，到了 Linux 后其实被**拆散**了：</span>

| STM32 `UART_Init()` 里干的事 | Linux 中由谁负责              |
| ---------------------------- | ----------------------------- |
| UART 硬件地址                | Device Tree `reg` 描述        |
| UART IRQ                     | Device Tree `interrupts` 描述 |
| UART Clock 来源              | Device Tree `clocks` 描述     |
| PE1/PE0 AF8                  | Device Tree + pinctrl 描述    |
| 是否使用 UART8               | `status = "okay"`             |
| 真正使能时钟                 | Clock Driver / UART Driver    |
| 真正修改 PinMux 寄存器       | pinctrl Driver                |
| 真正配置 UART 寄存器         | UART Driver                   |
| 波特率 115200                | TTY/termios + UART Driver     |
| 注册成 `/dev/ttySTM3`        | Serial Core / TTY             |

所以最准确的一句话是：

> <span style="background:#00FF80; color:#FF0000;">**STM32 裸机中的一个 `Init()` 往往把“硬件配置数据”和“执行初始化动作”写在一起；Linux 把前者主要放进 Device Tree，把后者分给 pinctrl、clock、UART 等驱动和内核子系统执行。**</span>

你<span style="color:#FF0000;">可以把 Device Tree 想成：</span>

```text
STM32：
“我自己拿着图纸，同时自己施工”

Linux：

Device Tree
= 图纸

Driver
= 施工队

Kernel Framework
= 工程管理体系

Hardware
= 真正的房子/设备
```

这个类比以后学 I2C、SPI、GPIO、LCD、网卡时也一直成立。





# 问题3

你可以先想 CPU 看到的：

<span style="color:#FF0000; background:#00FF80;">SoC 给 CPU 设计了一整套地址：</span>

```text
CPU Physical Address Space

0x00000000
    │
    ├── ROM / Flash
    │
    ├── SRAM
    │
    ├── DDR
    │
    ├── UART
    │
    ├── GPIO
    │
    ├── I2C
    │
    ├── SPI
    │
    └── ...
```

```text
     ↓

```

这里并不是说：

> UART 寄存器存在 DDR RAM 的某个位置。

<span style="color:#FF0000; background:#00FF80;">而是 SoC 总线做地址译码：</span>

```text
CPU访问 0x40019000
       ↓
SoC Bus
       ↓
发现属于 UART8
       ↓
访问 UART8 硬件寄存器
```

这就是：

<span style="background:#00FF80;">**Memory-Mapped I/O，MMIO。**</span>

```text
.data
.bss
heap
mmap
stack
...
```

这些地址：

```text
0x55xxxx...
```

是：

**虚拟地址。**

经过页表：

```text
虚拟地址
 ↓
MMU
 ↓
页表
 ↓
物理地址
```

不要理解成：


三个完全平级的 Linux 虚拟空间。

<span style="color:#FF0000; background:#00FF80;">更准确是两层概念。</span>

<span style="color:#FF0000;">第一层是：</span>

```text
虚拟地址空间

├── 用户虚拟地址空间
└── 内核虚拟地址空间
```

<span style="color:#FF0000;">第二层是 CPU 的：</span>

```text

├── DDR RAM
├── SRAM
├── ROM
├── UART MMIO
├── GPIO MMIO
├── SPI MMIO
└── 其他外设 MMIO
```

<span style="color:#FF0000;">然后通过 MMU/页表建立映射。</span>

<span style="color:#FF0000; background:#00FF80;">完整一些：</span>

```text
                    虚拟地址空间

用户进程
Virtual Address
      │
      │ 页表
      ▼
────────────────────────────
          物理地址空间
────────────────────────────
        │              │
        ▼              ▼
      DDR RAM        设备MMIO
                     UART/GPIO
        ▲              ▲
        │              │
        │              │
内核虚拟地址          ioremap
        │              │
        └──────────────┘
```

所以：

> **设备寄存器属于 CPU 物理地址空间的一部分，而不是 Linux 单独划出来的第三个虚拟地址空间。**

## 那为什么用户程序不能直接访问 UART 寄存器？

这又是另一个问题。

不是：

> 内核不能访问。

而是：

> <span style="background:#00FF80; color:#FF0000;">**普通用户程序通常没有映射这个物理 MMIO 区域的权限。**</span>

比如应用：

```c
*(volatile int *)0x40019000 = xxx;
```

通常是不行的。

因为：

```text
用户进程虚拟地址
```

里面根本没有：

```text
0x40019000
→ UART8
```

这样的合法页表映射。

正确路径一般是：

```text
APP
 ↓
write(fd)
 ↓
系统调用
 ↓
TTY / UART Driver
 ↓
writel()
 ↓
UART寄存器
```

这正是驱动存在的意义之一：

> **把硬件访问权限留在内核里，由用户通过受控接口使用硬件。**

## 那你说的“内核缓冲区”又是什么？

这里又要注意：

<span style="background:#00FF80;">**并不是所有设备访问都必须经过一个软件缓冲区。**</span>

这点很重要。

比如<span style="color:#FF0000; background:#00FF80;">驱动配置 UART 波特率：</span>

```text
APP ioctl/termios
 ↓
UART Driver
 ↓
直接写 UART BRR/控制寄存器
```

<span style="background:#00FF80;">中间根本没必要搞一个“内核数据缓冲区”。</span>

------

但是数据收发的时候，经常会有缓冲：

```text
UART RX
 ↓
UART硬件 FIFO
 ↓
UART Driver
 ↓
TTY 软件缓冲
 ↓
APP read()
```

这里<span style="color:#FF0000; background:#00FF80;">有两个完全不同的缓冲：</span>

```text
UART RX FIFO
= 硬件缓冲

TTY buffer
= 内核 RAM 中的软件缓冲
```

<span style="color:#FF0000; background:#00FF80;">内核缓冲的目的主要是：</span>

```text
解耦硬件速度和进程速度
处理中断
阻塞/唤醒
避免丢数据
批量传输
```

它不是：

> “因为内核不能访问设备，所以必须先拷贝到缓冲区。”

这一点一定要纠正。

------

## 比如 UART 接收，完整路径可以这样看

外部发来：

```text
A B C
```

硬件：

```text
RX引脚
 ↓
Receive Shift Register
 ↓
UART RX FIFO
```

驱动：

```text
UART IRQ
 ↓
UART Driver
 ↓
readl(UART_RDR)
```

这里 Driver 已经是**直接访问 UART MMIO 寄存器**了。

然后：

```text
UART Driver
 ↓
把字符交给 TTY buffer
 ↓
Line Discipline
 ↓
用户进程 read()
```

所以：

```text
设备MMIO
         ↓
      Driver
         ↓
内核软件Buffer
         ↓
       APP
```

而不是：

```text
设备
 ↓
某神秘设备空间
 ↓
内核不能访问
 ↓
必须靠buffer中转
```

------

## 再拿 STM32 来类比一下，你应该会一下子更清楚

STM32 裸机：

```text
CPU
 ↓
UART8->RDR
 ↓
直接读 UART硬件寄存器
 ↓
把数据存进
uint8_t rx_buffer[128]
```

这里：

```text
UART8->RDR
```

是：

**设备寄存器。**

而：

```c
uint8_t rx_buffer[128];
```

是：

**RAM 软件缓冲区。**

二者是完全不同的东西。

<span style="color:#FF0000; background:#00FF80;">Linux其实一样：</span>

```text
UART MMIO Register
      ↓
Linux UART Driver
      ↓
TTY kernel buffer
      ↓
APP
```

所以<span style="color:#FF0000; background:#00FF80;">你在 STM32 里已经做过这个模式了：</span>

```text
硬件寄存器
 ↓
软件buffer
```

<span style="color:#FF0000; background:#00FF80;">Linux只是把：</span>

```text
软件buffer
中断
进程阻塞
并发
用户/内核隔离
```

<span style="color:#FF0000; background:#00FF80;">做成统一框架。</span>

------

## 还有一种“设备自己的内存”，又是另一个概念

<span style="background:#00FF80; color:#FF0000;">有些设备除了几个控制寄存器，还真有一大块自己的存储区域。</span>

比如<span style="color:#FF0000; background:#00FF80;">显卡：</span>

```text
GPU
├── MMIO控制寄存器
└── VRAM
```

<span style="color:#FF0000; background:#00FF80;">或者 Framebuffer：</span>

```text
LCD Controller
 ↓
Framebuffer
 ↓
DDR中的一片物理内存
```

这种时候设备驱动可能把某片物理内存：

```text
mmap()
```

映射给用户进程。

例如：

```text
用户虚拟地址
      │
      │ mmap
      ▼
Framebuffer物理页
```

于是用户程序可以直接修改像素。

所以<span style="color:#FF0000; background:#00FF80;">你以后要区分三个概念：</span>

```text
① Device Registers
   UART CR1/RDR/TDR
   → MMIO控制寄存器

② Kernel Buffer
   驱动/TTY申请的RAM
   → 软件数据缓冲

③ Device Memory
   VRAM / Framebuffer等
   → 设备使用的大块存储区
```

它们不是同一个东西。

------

## 最后把整个模型收起来

你现在最适合记这一张：

```text
                 用户程序
                    │
             User Virtual Addr
                    │
              system call
                    ▼
────────────────────────────────
               Linux Kernel
                    │
           Kernel Virtual Addr
                    │
        ┌───────────┴───────────┐
        │                       │
   Kernel Buffer             ioremap
   TTY buffer                  │
        │                      ▼
        │                Device MMIO
        │                UART Registers
        │                      │
        └──────── Driver ──────┘
────────────────────────────────
             CPU Physical Address
        │                        │
       DDR                    UART/GPIO
```

所以你这一轮的几个结论可以修正成：

**`compatible`**：设备树节点和驱动之间的匹配标识，通常采用 `"vendor,device"` 形式，并由对应设备树 binding/驱动约定。

**UART 寄存器**：<span style="background:#00FF80; color:#FF0000;">属于 CPU 物理地址空间中的 MMIO 区域，不属于 DDR</span>，也不是第三种 Linux 虚拟地址空间。

**Linux 内核**：可以通过 `ioremap + readl/writel` 等方式直接访问设备寄存器。

**内核缓冲区**：是为了数据缓存、异步处理、阻塞/唤醒等目的存在，不是因为“Linux 内核无法访问设备”。

**地址空间最好理解为**：<span style="color:#FF0000; background:#00FF80;">用户虚拟地址空间 + 内核虚拟地址空间，背后映射到统一的 CPU 物理地址空间；而物理地址空间里面既可能是 RAM，也可能是 UART、GPIO 等 MMIO 外设。</span>



# 问题5

我记得Linux用户空间和内核空间不是有分为什么.data、.bss、.text、.heap、.stack、.rodata这些区域吗，这里应该又可以加上一些外设的地址空间吧，还有我有点忘记了线程栈里面也是有一个用户程序的.data、.bss、.text、.heap、.stack、.rodata吗，用户空间初始的时候应该不分什么堆和栈的吧。该怎么将这些给串联起来呢。



对，这里你现在其实把 **“ELF 文件里的段/节”**、**“进程运行时的虚拟地址空间”**、**“线程自己的栈”**、**“内核虚拟地址空间”**、**“外设 MMIO 物理地址”** 几套东西混在了一起。把它们分层以后就特别清楚。

最先纠正一个很关键的点：

> <span style="background:#00FF80;">`.text、.rodata、.data、.bss` 和 `heap、stack` 不是完全同一类概念。</span>
> <span style="background:#00FF80;">前四个主要来源于可执行文件/ELF；heap 和 stack 是程序运行起来以后建立的运行时内存区域。</span>

------

## 一、先从一个普通 Linux 程序开始

比如：

```c
int g = 10;
int x;

int main()
{
    int a = 1;
    char *p = malloc(100);
}
```

编译以后，可执行文件里会有类似：

```text
ELF文件

.text
.rodata
.data
.bss
...
```

例如：

```text
main()代码
   ↓
.text

字符串常量
   ↓
.rodata

int g = 10
   ↓
.data

int x
   ↓
.bss
```

注意这里通常没有所谓：

```text
.heap section
.stack section
```

因为：

> <span style="color:#FF0000; background:#00FF80;">**Heap 和 Stack 主要是程序运行起来以后由操作系统建立的，不是像 `.text/.data` 那样直接作为程序内容存进 ELF。**</span>

------

## 二、程序真正运行以后，才形成“进程虚拟地址空间”

比如一个 64 位 Linux 进程，可以非常粗略地画成：

```text
低地址
┌────────────────────────┐
│ .text                  │ 程序机器指令
├────────────────────────┤
│ .rodata                │ 只读数据
├────────────────────────┤
│ .data                  │ 已初始化全局变量
├────────────────────────┤
│ .bss                   │ 未初始化全局变量
├────────────────────────┤
│ Heap                   │ malloc等
│        ↓增长           │
│                        │
│      空闲虚拟地址       │
│                        │
│ mmap区域               │ 动态库、文件映射等
│                        │
│        ↑               │
├────────────────────────┤
│ Stack                  │
│        ↓/↑具体实现     │
└────────────────────────┘
高地址
```

实际 64 位 Linux 布局会复杂很多，而且 ASLR 会随机化地址，但这个模型足够帮助理解。

所以<span style="color:#FF0000; background:#00FF80;">你可以先记：</span>

```text
进程虚拟地址空间
=
代码
+
静态数据
+
堆
+
mmap
+
栈
+ 其他映射
```

------

## 三、那“用户空间一开始是不是没有堆和栈”？

这里要分开。

### Stack：<span style="background:#00FF80;">程序刚启动时就已经有</span>

<span style="color:#FF0000; background:#00FF80;">Linux 启动一个进程时，会给它建立用户栈。</span>

<span style="color:#FF0000; background:#00FF80;">甚至在 `main()` 运行之前，栈就已经存在了，因为：</span>

```text
程序启动
 ↓
Kernel建立用户栈
 ↓
放入 argc
argv
envp
辅助信息
 ↓
进入用户程序入口
 ↓
C运行库初始化
 ↓
main()
```

所以：

> **Stack 从程序刚开始执行时基本就已经存在。**

------

### Heap：概念上也有对应的起始位置，但一开始可能很小

比如：

```text
.data/.bss结束
      ↓
program break
      ↓
Heap起点
```

以后：

```c
malloc(...)
```

可能通过：

```text
brk/sbrk
```

或者：

```text
mmap
```

获得更多内存。

所以更准确应该说：

> **堆不是程序启动之后凭空才“出现”，但最开始可能没有实际分配很多页；随着 malloc 等操作逐渐扩展或通过 mmap 获得内存。**

------

## 四、线程这里是你最容易混淆的地方

你问：

> “线程栈里面是不是也有 `.text/.data/.bss/.heap/.stack/.rodata`？”

**不是。**

<span style="color:#FF0000; background:#00FF80;">线程栈里面只有这个线程自己的：</span>

> **Stack 内容。**

例如：

```c
void *thread_func(void *arg)
{
    int a;
    int b;
}
```

`a、b` 这些局部变量可能就在：

```text
Thread Stack
```

里。

但是 `.text/.data/.bss/heap` 不在“线程栈里面”。

------

## 五、多个线程共享什么，独立什么？

假设一个进程有三个线程：

```text
Process
│
├── Thread A
├── Thread B
└── Thread C
```

它们共享：

```text
.text
.rodata
.data
.bss
heap
mmap区域
打开的文件等很多进程资源
```

但每个线程有自己独立的：

```text
User Stack
CPU寄存器上下文
线程ID
内核栈
task_struct/调度状态等
```

所以更准确是：

```text
              一个进程虚拟地址空间

┌─────────────────────────────┐
│ .text                       │ ← A/B/C共享
├─────────────────────────────┤
│ .rodata                     │ ← 共享
├─────────────────────────────┤
│ .data                       │ ← 共享
├─────────────────────────────┤
│ .bss                        │ ← 共享
├─────────────────────────────┤
│ Heap                        │ ← 共享
├─────────────────────────────┤
│ mmap                        │ ← 共享
├─────────────────────────────┤
│ Thread A User Stack         │ ← A独有
├─────────────────────────────┤
│ Thread B User Stack         │ ← B独有
├─────────────────────────────┤
│ Thread C User Stack         │ ← C独有
└─────────────────────────────┘
```

这张图特别重要。

所以不是：

```text
Thread A
├── .text
├── .data
├── heap
└── stack

Thread B
├── .text
├── .data
├── heap
└── stack
```

而是：

```text
Process拥有一套：
.text/.data/.bss/heap/mmap

每个Thread只有自己额外的一块User Stack
```

这和你之前理解 pthread/thread 的共享地址空间是完全连起来的。

------

## 六、那 Linux 内核空间里面是不是也有 `.text/.data/.bss`？

对。

Linux Kernel 本身也是一个程序。

内核映像里同样有：

```text
Kernel .text
Kernel .rodata
Kernel .data
Kernel .bss
```

比如：

```text
Kernel Virtual Address Space

┌─────────────────────────┐
│ Kernel .text            │
├─────────────────────────┤
│ Kernel .rodata          │
├─────────────────────────┤
│ Kernel .data            │
├─────────────────────────┤
│ Kernel .bss             │
├─────────────────────────┤
│ Direct Mapping          │
├─────────────────────────┤
│ vmalloc area            │
├─────────────────────────┤
│ module area             │
├─────────────────────────┤
│ ioremap area            │
└─────────────────────────┘
```

而且 Linux 内核还有动态内存，例如：

```text
kmalloc
slab/slub
vmalloc
page allocator
```

所以也不能简单把 Kernel Space 理解成：

```text
.text
.data
.bss
heap
stack
```

因为内核的运行时内存组织比普通进程复杂很多。

------

## 七、线程还有“内核栈”

这个也要和用户栈分开。

一个 Linux 线程通常有：

```text
User Stack
+
Kernel Stack
```

比如 Thread A 在用户态执行：

```text
Thread A
User Mode
 ↓
User Stack A
```

然后：

```c
read(fd,...)
```

触发系统调用：

```text
User Mode
 ↓
syscall
 ↓
Kernel Mode
 ↓
Kernel Stack A
```

所以：

```text
Thread A
├── User Stack A
└── Kernel Stack A

Thread B
├── User Stack B
└── Kernel Stack B
```

而：

```text
.text/.data/.heap
```

仍然不是存在这些栈里面。

------

## 八、<span style="background:#00FF80; color:#FF0000;">那外设地址空间放在哪里？</span>

<span style="color:#FF0000; background:#00FF80;">这个地方不要把它硬塞到：</span>

```text
.text
.data
.bss
heap
stack
```

旁边。

因为<span style="color:#FF0000;">那些主要是在讲：</span>

> <span style="background:#00FF80; color:#FF0000;">**虚拟地址空间中的程序内存布局。**</span>

而 <span style="color:#FF0000;">UART、GPIO 等外设首先存在于：</span>

> **CPU 的物理地址空间。**

<span style="color:#FF0000; background:#00FF80;">比如：</span>

```text
CPU Physical Address Space

┌──────────────────────┐
│ ROM / Flash          │
├──────────────────────┤
│ SRAM                 │
├──────────────────────┤
│ DDR                  │
├──────────────────────┤
│ UART8 MMIO           │
│ 0x40019000...        │
├──────────────────────┤
│ GPIO MMIO            │
├──────────────────────┤
│ I2C MMIO             │
├──────────────────────┤
│ SPI MMIO             │
└──────────────────────┘
```

<span style="color:#FF0000; background:#00FF80;">所以 UART：</span>

```text
0x40019000
```

<span style="color:#FF0000; background:#00FF80;">不是：</span>

```text
Kernel heap里面的一块区域
```

<span style="color:#FF0000; background:#00FF80;">也不是：</span>

```text
User Space里面的一块区域
```

而是<span style="background:#00FF80;"> CPU 物理地址空间中被 SoC 总线分配给 UART 的地址。</span>

------

## 九、那<span style="background:#00FF80; color:#FF0000;">为什么 Linux 内核能访问 UART？</span>

因为 <span style="color:#FF0000; background:#00FF80;">Linux 驱动可以建立映射：</span>

```text
UART物理地址
0x40019000
      │
      │ ioremap
      ▼
Kernel Virtual Address
0xffff....
      │
      ▼
UART Driver
readl/writel
```

所以这时：

```text
Kernel Virtual Address Space
```

里面确实会有一小段虚拟地址映射到：

```text
UART MMIO Physical Address
```

<span style="color:#FF0000; background:#00FF80;">可以想：</span>

```text
Kernel Virtual Space
┌──────────────────────┐
│ Kernel text/data     │
│                      │
│ vmalloc              │
│                      │
│ ioremap region       │──────┐
└──────────────────────┘      │
                              ▼
Physical Address Space
                       0x40019000
                              ↓
                           UART8
```

<span style="color:#FF0000; background:#00FF80;">所以：</span>

> <span style="background:#00FF80; color:#FF0000;">**外设地址不是 Kernel Space 的一种“普通内存段”，但 Kernel Space 可以建立虚拟地址映射去访问它。**</span>

------

## 十、用户空间也可以映射外设吗？

一般普通 APP 不直接这样干。

正常：

```text
APP
 ↓
read/write/ioctl
 ↓
Kernel Driver
 ↓
Device MMIO
```

但<span style="color:#FF0000; background:#00FF80;">某些驱动也可以通过：</span>

```c
mmap()
```

<span style="color:#FF0000; background:#00FF80;">把设备内存映射给用户空间。</span>

例如<span style="color:#FF0000; background:#00FF80;">你之前学的 Framebuffer：</span>

```text
Framebuffer Physical Memory
      ↑
      │ mmap
      │
User Virtual Address
```

这时用户程序：

```c
pixel[100] = ...
```

<span style="color:#FF0000; background:#00FF80;">就能通过页表映射直接修改对应物理页。</span>

所以不是：

> 用户地址空间绝对不能映射设备。

而是：

> <span style="background:#00FF80;">**必须由内核控制和授权建立这种映射。**</span>

------

## 十一、这里最重要的是区分“三张图”

你现在脑子里最好同时保存三张不同的图，不要混。

### 第一张：ELF 文件

```text
ELF
├── .text
├── .rodata
├── .data
└── .bss
```

这是：

> **编译链接结果。**

------

### 第二张：进程虚拟地址空间

```text
Process Virtual Address Space

.text
.rodata
.data
.bss
heap
mmap
Thread A stack
Thread B stack
...
```

这是：

> <span style="background:#00FF80; color:#FF0000;">**程序运行以后进程看到的虚拟地址布局。**</span>

------

### 第三张：CPU 物理地址空间

```text
Physical Address Space

DDR
SRAM
ROM
UART
GPIO
SPI
I2C
...
```

这是：

> <span style="color:#FF0000; background:#00FF80;">**SoC 硬件地址地图。**</span>

然后<span style="color:#FF0000; background:#00FF80;">页表负责把前两者中的虚拟地址连接到第三张：</span>

```text
Virtual Address
      ↓
Page Table/MMU
      ↓
Physical Address
```

------

## 十二、把所有知识最终串成一张总图

这是你现在<span style="color:#FF0000; background:#00FF80;">最适合建立的完整模型：</span>

```text
                       一个Linux进程
                  User Virtual Address

          ┌─────────────────────────┐
          │ .text                   │
          │ .rodata                 │
          │ .data                   │
          │ .bss                    │
          │ Heap                    │
          │ mmap                    │
          │ Thread A User Stack     │
          │ Thread B User Stack     │
          └────────────┬────────────┘
                       │
                   syscall
                       ▼
══════════════════════════════════════════
                  Kernel Space

          ┌─────────────────────────┐
          │ Kernel .text            │
          │ Kernel .rodata          │
          │ Kernel .data/.bss       │
          │ slab/kmalloc            │
          │ vmalloc                 │
          │ Kernel Stacks           │
          │ ioremap region          │───────┐
          └─────────────────────────┘       │
                                            │
                        MMU / Page Table     │
                              │             │
══════════════════════════════╪═════════════╪════
                       Physical Address Space
                              │             │
               ┌──────────────┼─────────────┘
               │              │
              DDR          UART/GPIO
                              │
                         MMIO Registers
```

<span style="color:#FF0000; background:#00FF80;">这样以后你再看到：</span>

```text
.text
heap
stack
page table
kmalloc
ioremap
UART reg
Framebuffer
```

<span style="color:#FF0000; background:#00FF80;">就能立刻知道它属于哪一层。</span>

最后给你一句特别适合记忆的：

```text
│    └── PE1 AF8 → TX
```

思想非常像。

## 最后再用 STM32 HAL 类比一次

STM32 裸机你可能写：

```c
void MX_UART8_Init(void)
{
    GPIO_InitStruct.Pin = GPIO_PIN_1;
    GPIO_InitStruct.Alternate = GPIO_AF8_UART8;

    HAL_GPIO_Init(GPIOE, &GPIO_InitStruct);

    huart8.Instance = UART8;

    HAL_UART_Init(&huart8);
}
```

Linux 把里面的事情拆开：

```text
STM32裸机
─────────────────────────

UART8硬件是谁？
→ huart8.Instance

Pin是谁？
→ PE1/PE0

复用是什么？
→ AF8

启不启用？
→ Init函数是否调用
```

Linux：

```text
Device Tree
─────────────────────────

UART8硬件是谁？
→ serial@40019000

Pin是谁？
→ uart8_pins_mx

复用是什么？
→ STM32_PINMUX('E',1,AF8)

UART8引用哪套Pin？
→ pinctrl-0 = <&uart8_pins_mx>

启不启用？
→ status = "okay"
```

所以你现在可以这样理解整个设计：

> <span style="background:#00FF80; color:#FF0000;">`.dtsi` 先定义“STM32MP157 芯片本身有哪些硬件节点”；`.dts` 再通过 `&label {}` 找到这些节点，根据具体开发板情况进行启用、覆盖和补充；`uart8_pins_mx` 则是另一棵 pinctrl 配置节点，UART8 通过 `pinctrl-0 = <&uart8_pins_mx>` 引用它。</span>

而最值得你记住的三个符号就是：

```text
:
→ 给节点起label

&label
→ 引用已有节点

property = <&label ...>
→ 一个节点引用另一个节点
```

掌握这三个以后，你再看设备树，大部分结构就不会那么陌生了。



# 问题7

这个SoC公共文件是个什么东西，还有一个开发板是可以有多个.dtsi和.dts文件吗，一个设备数文件.dts对应着一组.dtsi和.dts吗，应该怎么理解呢。



对，这里最容易混的是：**`.dts` 和 `.dtsi` 不是“一一对应”的关系**。更准确地说，它们像“主配置文件 + 若干被包含的公共配置片段”，最终一起组成一棵完整设备树。

你先把 **SoC 公共文件** 理解清楚。

所谓<span style="color:#FF0000; background:#00FF80;"> SoC 公共文件</span>，就是：

> <span style="color:#FF0000; background:#00FF80;">**描述“这个芯片本身有什么硬件资源”的公共设备树文件。**</span>

比如 <span style="color:#FF0000; background:#00FF80;">STM32MP157 这个 SoC，不管它被焊在哪一块开发板上，它芯片内部本来就有这些东西：</span>

```text

UART1
UART2
UART8
I2C
SPI
GPIO
Timer
RCC
DMA
USB
...
```

<span style="color:#FF0000; background:#00FF80;">这些资源是 **芯片级固定的**，和具体开发板怎么接线没关系。</span>

所以可以放在类似：

```text
stm32mp157.dtsi
stm32mp15.dtsi
```

这样的公共文件里。

里面可能写：

```dts
uart8: serial@40019000 {
    compatible = "st,stm32h7-uart";
    reg = <0x40019000 0x400>;
    interrupts = <...>;
    clocks = <&rcc UART8_K>;
    status = "disabled";
};
```

意思是：

> <span style="color:#FF0000; background:#00FF80;">STM32MP157 这个芯片里确实有 UART8，而且它的寄存器、中断、时钟资源是这些。</span>

但是<span style="color:#FF0000; background:#00FF80;">它**不知道具体某块板子到底有没有把 UART8 引脚接出来**，所以先：</span>

```dts
status = "disabled";
```

------

然后才轮到具体开发板 `.dts`。

比如：

```text
stm32mp157c-100ask-512d-lcd-v1.dts
```

<span style="color:#FF0000; background:#00FF80;">这个文件描述的是：</span>

> <span style="background:#00FF80;">“100ASK 这块具体开发板，怎么使用 STM32MP157 这颗芯片。”</span>

它<span style="color:#FF0000; background:#00FF80;">可能会说：</span>

```dts
&uart8 {
    pinctrl-0 = <&uart8_pins_mx>;
    status = "okay";
};
```

<span style="color:#FF0000; background:#00FF80;">也就是：</span>

```text
芯片本身有UART8
      ↓
这块板子真的把它接出来了
      ↓
那就在这块板子上启用
```

<span style="color:#FF0000; background:#00FF80;">所以可以记：</span>

```text
SoC .dtsi
=
“芯片有什么”

Board .dts
=
“这块板子用了什么”
```

------

## 一个开发板可以有多个 `.dtsi` 吗？

**当然可以，而且非常常见。**

比如<span style="color:#FF0000; background:#00FF80;">最终某个板子的 `.dts` 可能包含：</span>

```dts
#include "stm32mp15.dtsi"
#include "stm32mp157.dtsi"
#include "stm32mp15-pinctrl.dtsi"
#include "stm32mp15xx-100ask-common.dtsi"
```

你可以理解：

```text
最终板级.dts
│
├── SoC公共.dtsi
├── pinctrl公共.dtsi
├── 电源公共.dtsi
├── 板卡公共.dtsi
└── 自己再补充一些具体配置
```

就像 C 代码：

```c
#include "stm32.h"
#include "gpio.h"
#include "uart.h"
#include "board.h"
```

不是只允许 include 一个头文件。

------

## 那一个开发板可以有多个 `.dts` 吗？

也可以。

<span style="color:#FF0000; background:#00FF80;">比如同一块基础开发板可能有不同硬件版本：</span>

```text
board-v1.dts
board-v2.dts
board-lcd.dts
board-hdmi.dts
board-512m.dts
board-1g.dts
```

它们<span style="color:#FF0000; background:#00FF80;">可能共用很多 `.dtsi`。</span>

例如：

```text
                stm32mp157.dtsi
                      │
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
      board-v1.dts board-v2.dts board-lcd.dts
```

<span style="color:#FF0000; background:#00FF80;">每一个 `.dts` 最终都可以编译出一个独立：</span>

```text
.dtb
```

例如：

```text
board-v1.dts
   ↓
board-v1.dtb

board-v2.dts
   ↓
board-v2.dtb
```

<span style="color:#FF0000; background:#00FF80;">启动时通常只加载其中一个适合当前板子的 DTB。</span>

------

## 最重要：不是“一个 `.dts` 对应一组 `.dts + .dtsi`”

更准确的结构是：

> <span style="color:#FF0000; background:#00FF80;">**一个最终 `.dts` 可以通过 include 引入多个 `.dtsi`，这些内容合并后形成一棵完整设备树，再编译成一个 `.dtb`。**</span>

可以画成：

```text
stm32mp15.dtsi
        │
stm32mp157.dtsi
        │
pinctrl.dtsi
        │
100ask-common.dtsi
        │
        ▼
stm32mp157c-100ask.dts
        │
        ▼
   合并成完整设备树
        │
        ▼
      dtc编译
        │
        ▼
stm32mp157c-100ask.dtb
```

<span style="color:#FF0000; background:#00FF80;">所以：</span>

```text
多个 .dtsi
+
一个顶层 .dts
=
一棵最终设备树
```

这个理解最稳。

------

## `.dtsi` 自己也是设备树代码吗？

对。

它不是完全不同的语言。

`.dtsi` 本质上也是 Device Tree Source 的一部分。

区别主要是“用途”：

```text
.dts
→ 通常作为最终入口
→ 描述一个具体机器/开发板

.dtsi
→ 通常被别的文件include
→ 放公共、可复用部分
```

有点像：

```text
.c
和
.h
```

但也不能完全等同。

更像：

```text
.dts
= 主配置文件

.dtsi
= 可复用配置片段
```

------

## 用 STM32 工程来类比最好理解

假设你以前 STM32 工程：

```text
stm32f4xx.h
↓
描述芯片寄存器、外设

board.h
↓
描述这块板子的LED、UART引脚

main.c
↓
最终决定启用哪些东西
```

设备树：

```text
stm32mp157.dtsi
↓
描述SoC有什么

100ask-common.dtsi
↓
描述这系列板子公共连接

100ask-board.dts
↓
描述具体板子最终配置
```

很像：

```text
芯片层
   ↓
板级公共层
   ↓
具体产品层
```

------

## 你还可以把它理解成“继承 + 覆盖”

假设 `.dtsi`：

```dts
uart8: serial@40019000 {
    status = "disabled";
};
```

板级 `.dts`：

```dts
&uart8 {
    status = "okay";
};
```

最终逻辑上：

```dts
uart8: serial@40019000 {
    status = "okay";

```

所以很像：

```text
公共模板：
UART8默认关闭

具体板子：
我要用UART8
→ 覆盖为okay
```

这也是为什么设备树工程里会有很多层 `.dtsi`。

最后给你一个特别好记的模型：

```text
SoC .dtsi

芯片说明书

Board-common .dtsi
=
某一系列开发板的公共接线图

Board .dts
=
这块具体板子的最终配置

.dtb

Linux启动真正读取的二进制结果
```

而且通常是：

> <span style="background:#00FF80; color:#FF0000;">**很多 `.dtsi` + 一个顶层 `.dts` → 一个最终 `.dtb`。**</span>

这句话你记住，后面再看设备树目录结构就会清楚很多。



# 问题8

CPU

UART1

UART2

UART8

I2C

SPI

GPIO

Timer

RCC

DMA

USB

...



芯片层

   ↓

板级公共层

   ↓

具体产品层



我有个疑惑点，就是这些资源都是芯片级固定，芯片和板子有什么区别呢，帮我从.dtsi和.dts的角度理解下。一个板子上面应该有一个芯片吧，另外uart、spi、timer等等这些外设都是位于芯片里面的吗，我怎么记得芯片不是只包含CPU什么的吗，这里有点搞不太清楚。



对，<span style="background:#00FF80;">你这里真正混淆的是 **CPU、SoC/MCU 芯片、开发板** 这三个层级。这个一旦分开，`.dtsi` 和 `.dts` 就会一下子变得特别直观。</span>

最关键的一句话先记住：

> <span style="background:#00FF80; color:#FF0000;">**CPU 只是“计算核心”；SoC/MCU 是一整颗芯片，里面除了 CPU，还集成 UART、SPI、I2C、Timer、GPIO、DMA、RCC 等大量外设控制器；开发板则是把这颗主芯片和 DDR、Flash、电源芯片、网口 PHY、接口座等许多器件焊在 PCB 上形成的完整硬件。**</span>

------

## 1. CPU ≠ 芯片 ≠ 开发板

你以前可能脑子里是：

```text
芯片
≈
CPU
```

<span style="background:#00FF80; color:#FF0000;">实际上对于 STM32、STM32MP157 这种嵌入式芯片，更准确是：</span>

```text
一颗 SoC / MCU 芯片
┌──────────────────────────────┐
│                              │
│      CPU Core                │
│      Cortex-A / Cortex-M     │
│                              │
│  UART   SPI   I2C   Timer    │
│                              │
│  GPIO   DMA   RCC   USB      │
│                              │
│  Ethernet Controller         │
│                              │
│  Interrupt Controller        │
│                              │
│  内部总线                    │
│                              │
└──────────────────────────────┘
```

所以 CPU 只是里面的一部分。

你可以把它想成：

```text
SoC
=
CPU
+
很多外设控制器
+
总线
+
时钟系统
+
中断系统
+
其他硬件模块
```

这就是<span style="background:#00FF80;"> **System on Chip** 这个名字的含义：</span>

> <span style="background:#00FF80; color:#FF0000;">尽可能把原来很多独立芯片的功能集成到一颗芯片里。</span>

------

## 2. STM32 其实你以前早就接触过这种结构

比如 STM32F103。

你不会认为：

```text
STM32F103里面只有Cortex-M3
```

它其实是：

```text
STM32F103
│
├── Cortex-M3 CPU
│
├── USART1
├── USART2
├── SPI1
├── SPI2
├── I2C
├── GPIOA
├── GPIOB
├── TIM1
├── TIM2
├── ADC
├── DMA
├── RCC
└── ...
```

所以<span style="background:#00FF80;">你以前写：</span>

```c
USART1->CR1
TIM2->CNT
GPIOA->ODR
RCC->APB2ENR
```

<span style="color:#FF0000;">这些寄存器对应的：</span>

```text
USART
Timer
GPIO
RCC
```

<span style="background:#00FF80;">本来就是**这颗 STM32 芯片内部的硬件模块**。</span>

只是你以前没把：

```text
CPU
```

和：

```text
整个STM32芯片
```

严格区分开。

------

## 3. STM32MP157 也是一样，只不过规模更大

STM32MP157 可以粗略想成：

```text
STM32MP157 SoC
┌────────────────────────────────┐
│                                │
│ Cortex-A7 CPU Core             │
│ Cortex-A7 CPU Core             │
│ Cortex-M4                      │
│                                │
│ UART / USART                   │
│ SPI                            │
│ I2C                            │
│ GPIO                           │
│ Timer                          │
│ DMA                            │
│ RCC                            │
│ USB Controller                 │
│ Ethernet MAC                   │
│ SD/MMC Controller              │
│ Display Controller             │
│ ...                            │
│                                │
└────────────────────────────────┘
```

所以你前面看到：

```text
UART1
UART2
UART8
I2C
SPI
GPIO
Timer
RCC
DMA
USB
```

这些很多确实都是：

> <span style="background:#00FF80;">**STM32MP157 这颗 SoC 内部已经集成好的硬件控制器。**</span>

------

## 4. 那“板子”是什么？

板子就是：

> <span style="background:#00FF80; color:#FF0000;">PCB + 主 SoC + 各种外围芯片 + 接口 + 电源 + 元器件。</span>

例如你的开发板可以粗略画成：

```text
                  开发板 PCB
┌─────────────────────────────────────┐
│                                     │
│        STM32MP157 SoC               │
│       ┌───────────────┐             │
│       │ CPU           │             │
│       │ UART          │             │
│       │ SPI           │             │
│       │ I2C           │             │
│       │ Ethernet MAC  │             │
│       └───────┬───────┘             │
│               │                     │
│        ┌──────┼────────┐            │
│        ▼      ▼        ▼            │
│      DDR    eMMC     PMIC           │
│                                     │
│      Ethernet PHY                   │
│                                     │
│      USB Connector                  │
│                                     │
│      LCD Connector                  │
│                                     │
│      LEDs / Buttons                 │
│                                     │
│      USB-UART Chip                  │
│                                     │
└─────────────────────────────────────┘
```

所以：

> <span style="background:#00FF80; color:#FF0000;">**一块板子绝对不是只有一个芯片。**</span>

<span style="background:#00FF80;">一般可能有：</span>

```text
主SoC
DDR芯片
eMMC/NAND/NOR Flash
PMIC电源管理芯片
Ethernet PHY
USB Hub
USB-UART
Audio Codec
Wi-Fi/BT芯片
EEPROM
传感器
...
```

<span style="color:#FF0000; background:#00FF80;">几十颗芯片都很正常。</span>

------

## 5. 那为什么我们经常感觉“板子上就是一个 STM32”？

因为在简单 STM32 最小系统板里：

```text
STM32 MCU
```

承担了最主要功能。

<span style="color:#FF0000; background:#00FF80;">外围可能只有：</span>

```text
晶振
电源
Flash（有时内部已经有）
LED
按键
USB-UART
```

所以视觉上容易觉得：

> <span style="background:#00FF80;">“这块板就是这颗 STM32。”</span>

但<span style="color:#FF0000; background:#00FF80;">严格来说：</span>

```text
STM32
=
一颗芯片

STM32开发板
=
PCB + STM32芯片 + 外围器件
```

完全不是同一个层级。

------

## 6. 现在 `.dtsi` 就特别容易理解了

因为<span style="background:#00FF80;"> `.dtsi` 经常负责描述：</span>

> <span style="color:#FF0000; background:#00FF80;">**主 SoC 芯片内部本来就有什么。**</span>

<span style="background:#00FF80;">例如：</span>

```text
stm32mp157.dtsi
```

<span style="color:#FF0000; background:#00FF80;">描述：</span>

```text
STM32MP157 SoC

CPU
UART8
SPI
I2C
GPIO
Timer
RCC
DMA
...
```

<span style="color:#FF0000; background:#00FF80;">比如：</span>

```dts
uart8: serial@40019000 {
    reg = <0x40019000 0x400>;
    interrupts = <...>;
    clocks = <&rcc UART8_K>;
    status = "disabled";
};
```

这在说：

> <span style="background:#00FF80; color:#FF0000;">STM32MP157 这颗芯片内部存在 UART8 控制器。</span>

<span style="color:#FF0000; border:1px solid #330000; background:#00FF80;">这个事实不管你把 STM32MP157 焊在哪块板子上，都不会变。</span>

所以<span style="color:#FF0000; background:#00FF80;">非常适合放：</span>

```text
SoC公共 .dtsi
```

------

## 7. `.dts` 描述的是<span style="background:#00FF80; color:#FF0000;">“这块板子怎么用了这些东西”</span>

假设 SoC 里面有：

```text
UART8
```

但是<span style="color:#FF0000; background:#00FF80;">芯片的 UART8 是否真正能拿来用，还要看开发板怎么接。</span>

例如：

```text
STM32MP157
UART8_TX
     │
     │ PE1
     ▼
开发板扩展接口
```

如果<span style="color:#FF0000; background:#00FF80;">开发板把 PE1/PE0 接出来：</span>

```text
UART8
↓
PE1 / PE0
↓
扩展接口
```

那 <span style="background:#00FF80; color:#FF0000;">`.dts` 就可以写：</span>

```dts
&uart8 {
    pinctrl-0 = <&uart8_pins_mx>;
    status = "okay";
};
```

意思：

> <span style="background:#00FF80;">这块具体开发板确实使用 UART8，所以启用。</span>

------

<span style="color:#FF0000;">如果另一块板子根本没有用 UART8：</span>

```text
STM32MP157
UART8
↓
引脚可能拿去做SPI了
```

<span style="color:#FF0000; background:#00FF80;">那么它的 `.dts` 就不会启用 UART8。</span>

所以：

```text
.dtsi
回答：
“芯片有什么？”

.dts
回答：
“板子怎么使用芯片里的这些东西？”
```

这个区分特别重要。

------

## 8. 一个具体 UART 例子最好理解

SoC 内部：

```text
STM32MP157
┌───────────────────┐
│ UART8 Controller  │
│                   │
│ TX                 │──── PE1
│ RX                 │──── PE0
└───────────────────┘
```

这部分属于：

```text
芯片层
```

所以 `.dtsi` 描述：

```dts
uart8: serial@40019000 {
    reg = <0x40019000 0x400>;
    interrupts = <...>;
    clocks = <&rcc UART8_K>;
    status = "disabled";
};
```

而 <span style="color:#FF0000; background:#00FF80;">PCB 设计决定：</span>

```text
PE1
↓
到底接到哪里？

PE0
↓
到底接到哪里？
```

比如<span style="color:#FF0000; background:#00FF80;"> 100ASK 板：</span>

```text
PE1 → 扩展接口 UART_TX
PE0 → 扩展接口 UART_RX
```

<span style="background:#00FF80;">所以 `.dts`：</span>

```dts
&uart8 {
    pinctrl-0 = <&uart8_pins_mx>;
    status = "okay";
};
```

------

## 9. SPI 更能体现 SoC 和板子的区别

假设 STM32MP157 内部：

```text
SPI1 Controller
```

这个是 SoC 固有的。

所以 `.dtsi`：

```text
SPI1存在
寄存器在哪里
IRQ是什么
Clock是什么
```

<span style="color:#FF0000; background:#00FF80;">但是 SPI 总线上挂什么东西？</span>

<span style="color:#FF0000; background:#00FF80;">完全由开发板决定。</span>

板 A：

```text
SPI1
 ↓
LCD Controller
```

板 B：

```text
SPI1
 ↓
SPI Flash
```

板 C：

```text
SPI1
 ↓
ADC芯片
```

所以：

```text
SoC .dtsi

SPI1 Controller
```

<span style="color:#FF0000;">而：</span>

```text
Board .dts

SPI1下面挂了什么设备
```

<span style="color:#FF0000; background:#00FF80;">甚至设备树里会真的形成父子关系：</span>

```text
SPI Controller
│
├── SPI Flash
└── Sensor
```

这个就是设备树“树”特别经典的地方。

------

## 10. I2C 也是一样

SoC 内部有：

```text
I2C1 Controller
```

但是板子上可能接：

```text
I2C1
├── EEPROM
├── Temperature Sensor
└── Touch Controller
```

<span style="color:#FF0000; background:#00FF80;">因此：</span>

```text
.dtsi
```

<span style="color:#FF0000; background:#00FF80;">描述：</span>

```text
I2C1控制器本身
```

<span style="color:#FF0000; background:#00FF80;">而：</span>

```text
.dts
```

<span style="color:#FF0000; background:#00FF80;">可能描述：</span>

```text
I2C1总线上接了EEPROM、Touch芯片
```

<span style="background:#00FF80;">所以 `.dts` 里面很多时候会出现**外部芯片节点**。</span>

------

## 11. 一个很重要的区别：Controller 和 Device

这里<span style="color:#FF0000;">以后设备树里经常遇到。</span>

比如：

```text
SoC内部：
I2C Controller
SPI Controller
UART Controller
Ethernet MAC
USB Controller
```

这些是：

> **控制器 Controller。**

而<span style="color:#FF0000; background:#00FF80;">板子外面可能连接：</span>

```text
I2C Sensor
SPI Flash
UART GPS
Ethernet PHY
USB Device
```

这些是：

> <span style="background:#00FF80;">**外部 Device。**</span>

例如：

```text
STM32MP157 SoC
┌──────────────────┐
│ I2C Controller   │
└────────┬─────────┘
         │
         │ PCB走线
         ▼
   Temperature Sensor
```

<span style="color:#FF0000; background:#00FF80;">设备树可以体现为：</span>

```text
i2c1
│
└── sensor@48
```

所以：

> <span style="background:#00FF80; color:#FF0000;">SoC 提供“控制能力”，板子决定“连接谁”。</span>

------

## 12. Ethernet 这个例子也特别典型

<span style="background:#00FF80; color:#FF0000;">SoC 里面可能只有：</span>

```text
Ethernet MAC Controller
```

<span style="background:#00FF80; color:#FF0000;">但是 RJ45 网口不是直接接 MAC。</span>

通常：

```text
SoC内部

Ethernet MAC
      │
      │ RGMII/RMII
      ▼
板上的 PHY芯片
      │
      ▼
网络变压器
      │
      ▼
RJ45
```

所以：

```text
MAC
=
SoC内部

PHY
=
开发板上的另一个芯片
```

这也是为什么：

```text
一块开发板
```

对，你这里纠正得很关键<span style="background:#00FF80;">。**“多个 `.dtsi` + 一个 `.dts`”并不意味着多个 SoC；因为 `.dtsi` 根本不等于“一个 SoC 文件”。**</span>

更准确地说：

> `.dtsi` 只是“可复用的设备树片段”。
> <span style="background:#00FF80; color:#FF0000;">它可以描述 SoC，也可以描述 SoC 家族公共部分、pinctrl、板级公共电路、电源、DDR 等。</span>
> <span style="background:#00FF80; color:#FF0000;">而一个具体 `.dtb` 通常以一个顶层 `.dts` 作为入口，包含多个 `.dtsi` 后编译得到。</span>

### 先看<span style="background:#00FF80;">为什么一个 SoC 会对应多个 `.dtsi`</span>

<span style="color:#FF0000; background:#00FF80;">假设是一块 STM32MP157 开发板，可能有这样的文件：</span>

```text
stm32mp15.dtsi
    ↓
描述整个 STM32MP15 系列共有的东西

stm32mp157.dtsi
    ↓
在上面基础上描述 STM32MP157 特有部分

stm32mp15-pinctrl.dtsi
    ↓
描述 GPIO / PinMux 相关内容

stm32mp15xx-100ask-common.dtsi
    ↓
描述 100ASK 一系列板子的公共硬件连接

stm32mp157c-100ask-lcd.dts
    ↓
描述这一块具体开发板
```

这里虽然有四个 `.dtsi`：

```text
.dtsi
.dtsi
.dtsi
.dtsi
```

但主 SoC 仍然只有：

```text
STM32MP157
```

因为 `.dtsi` 只是为了把一个特别大的硬件描述拆成几个模块。

有点像你写 C：

```c
#include "stm32mp15.h"
#include "gpio.h"
#include "clock.h"
#include "board_common.h"
```

不能因为 include 四个 `.h` 就说有四个 CPU。

设备树也是一样。

------

### 所以 `.dtsi` 最好不要记成“Soc 文件”

更准确记成：

```text
.dtsi
=
Device Tree Source Include
=
可以被其他设备树文件复用的配置片段
```

它<span style="color:#FF0000; background:#00FF80;">里面可以放各种东西。</span>

<span style="background:#00FF80;">比如：</span>

```text
SoC公共硬件
```

<span style="background:#00FF80;">也可以放：</span>

```text
PinMux
```

<span style="background:#00FF80;">也可以放：</span>

```text
一系列开发板公共电路
```

<span style="background:#00FF80;">甚至：</span>

```text
PMIC配置
DDR配置
LCD公共配置
```

<span style="background:#00FF80; color:#FF0000;">所以：</span>

> **有多个 `.dtsi` ≠ 有多个 SoC。**

## 那你说“不是可以有多个 `.dts` 吗？”

对，**整个 Linux 内核源码目录里当然可以有很多 `.dts`。**

例如可能有：

```text

board-b.dts
board-c.dts
board-lcd.dts
board-hdmi.dts
```

<span style="color:#FF0000; background:#00FF80;">分别代表不同：</span>

```text

硬件版本
产品型号
外设组合
```

但关键是：

> <span style="background:#00FF80;">**编译一个具体 `.dtb` 时，通常有一个顶层 `.dts` 作为入口。**</span>

比如：

```text
board-a.dts
   ↓
include 多个 .dtsi
   ↓
board-a.dtb
```

另外：

```text
board-b.dts
   ↓
include 多个 .dtsi
   ↓
board-b.dtb
```

所以关系应该画成这样：

```text
                 stm32mp15.dtsi
                       │
                 stm32mp157.dtsi
                       │
               pinctrl-common.dtsi
                       │

                 │           │
                 ▼           ▼

                 │           │
                 ▼           ▼

```

<span style="color:#FF0000; background:#00FF80;">这就很清楚了：</span>

```text
很多 .dts
↓
可以生成很多 .dtb
```

<span style="color:#FF0000; background:#00FF80;">但：</span>

```text
某一个具体 .dtb
```

<span style="color:#FF0000; background:#00FF80;">通常对应：</span>

```text
某一个顶层 .dts
+
它包含的若干 .dtsi
```

```dts
&uart8 {

    pinctrl-names = "default", "sleep";

    pinctrl-0 = <&uart8_pins_mx>;

    pinctrl-1 = <&uart8_sleep_pins_mx>;

    status = "okay";
};
```

<span style="color:#FF0000; background:#00FF80;">逻辑上合并以后相当于：</span>

```dts
uart8: serial@40019000 {

    compatible = "st,stm32h7-uart";

    reg = <0x40019000 0x400>;

    clocks = <&rcc UART8_K>;


    pinctrl-names = "default", "sleep";

    pinctrl-0 = <&uart8_pins_mx>;

    pinctrl-1 = <&uart8_sleep_pins_mx>;


    status = "okay";
};
```

注意：

原来：

```dts
status = "disabled";
```

后来又：

```dts
status = "okay";
```

<span style="color:#FF0000; background:#00FF80;">后面的板级配置覆盖前面公共默认值。</span>

所以：

```text
.dtsi
=
默认模板

.dts
=
具体产品最终决定
```

<span style="color:#FF0000; background:#00FF80;">特别像：</span>

```c
默认：

uart8.enable = false;

具体板子：

uart8.enable = true;
```

## 八、`pinctrl-0 = <&uart8_pins_mx>;` 又发生什么？

前面已经定义：

```dts
uart8_pins_mx: uart8-pins {
    ...
};
```

所以：

```dts
&uart8_pins_mx
```

就是引用它。

可以用 C 指针帮助理解：

```c
struct PinConfig uart8_pins_mx;

struct UART8 uart8;

uart8.pins = &uart8_pins_mx;
```

设备树：

```dts
pinctrl-0 = <&uart8_pins_mx>;
```

就是类似：

```text
UART8
 │
 │ 引用
 ▼
uart8_pins_mx
 │
 ├── PE1 AF8
 └── PE0 AF8
```

<span style="background:#00FF80; color:#FF0000;">最终设备树不是简单一堆独立节点。</span>

<span style="background:#00FF80;">节点之间可以互相引用。</span>

## 九、最终<span style="color:#FF0000; background:#00FF80;">完整设备树</span>大概是什么样？

把<span style="color:#FF0000; background:#00FF80;">前面所有文件逻辑合并：</span>

```text
/
│
├── cpus
│   ├── cpu@0
│   └── cpu@1
│
├── model = "100ASK ..."
│
├── aliases
│   └── serial3 ────────────────┐
│                               │
└── soc                         │
    │                           │
    ├── rcc@50000000            │
    │                           │
    ├── pin-controller@50002000 │
    │   │                       │
    │   ├── uart8-pins ◀────┐   │
    │   │   ├── PE1 AF8     │   │
    │   │   └── PE0 AF8     │   │
    │   │                    │   │
    │   └── uart8-sleep      │   │
    │                        │   │
    └── serial@40019000 ◀────┴───┘

        ├── clocks

```

这<span style="color:#FF0000; background:#00FF80;">就是真正的一棵树。</span>

## 十一、`.dtb` 里面还有 `uart8` 这种 label 吗？

源码里的：


以及：

主要方便**写源码和编译时解析引用**。

# 十三、接下来轮到 U-Boot

开发板启动：

```text
上电
 ↓
BootROM
 ↓
TF-A / SPL等
 ↓
U-Boot
```

我们先不管前面的复杂启动链。



# 十四、U-Boot 把 Kernel 和 DTB 都加载到 DDR

例如概念化命令：

```bash
load mmc 0:1 ${kernel_addr_r} /zImage
```

意思：

```text
从MMC/SD/eMMC
读取 zImage
↓
放入DDR
kernel_addr_r
```

然后：

```bash
load mmc 0:1 ${fdt_addr_r} /stm32mp157c-100ask-lcd.dtb
```

意思：

```text
从存储设备读取DTB
↓
放入DDR
fdt_addr_r
```

所以 DDR 里变成：

```text
DDR

0xC2000000
┌───────────────────────┐
│ Linux zImage          │
└───────────────────────┘


0xC4000000
┌───────────────────────┐
│ board.dtb             │
└───────────────────────┘
```

地址只是举例，实际由 U-Boot 环境变量决定。

------

# 十五、然后 U-Boot 怎么启动 Kernel？

STM32MP157 是 Cortex-A7，属于 32-bit ARM，常见启动可能用：

```bash
bootz ${kernel_addr_r} - ${fdt_addr_r}
```

三个参数可以粗略理解：

```text
bootz

参数1：
Kernel地址

参数2：
initrd地址
“-”表示没有

参数3：
DTB地址
```

所以：

```bash
bootz ${kernel_addr_r} - ${fdt_addr_r}
```

可以理解：

> Linux Kernel 在这里，设备树 DTB 在那里，请启动。

------

# 十六、那 U-Boot 是怎么把 DTB“交给” Linux 的？

这里特别关键：

不是：

```text
U-Boot
把DTB复制进Kernel代码
```

而是：

> **把 DTB 放在 DDR 的某个地址，然后按照 ARM 启动约定把这个地址告诉 Kernel。**

概念：

```text
U-Boot
 │
 ├── Kernel在 0xC2000000
 │
 └── DTB在    0xC4000000
                 │
                 │ 告诉Kernel
                 ▼
              DTB地址
```

Kernel 启动后：

```text
Kernel
↓
知道：
DTB在0xC4000000
↓
解析这块内存
```

------

# 十七、Linux Kernel 启动后发生什么？

Linux 早期启动：

```text
Kernel入口
 ↓
读取Bootloader传来的FDT地址
 ↓
检查DTB头部
 ↓
解析Flattened Device Tree
 ↓
建立内核中的Device Tree结构
```

`.dtb` 也叫：

```text
FDT
=
Flattened Device Tree
```

因为：

```text
源码：
树形结构

↓ 编译

DTB：
扁平化二进制格式
```

Linux 启动后再把它解析成方便内核使用的数据结构。

# 二十一、把它和 STM32 裸机对照，你会更容易记

STM32 裸机：

```text
main.c
↓
MX_GPIO_Init()
↓
MX_UART8_Init()
↓
配置PE1/PE0
↓
开RCC
↓
配置UART寄存器
↓
UART工作
```

Linux：

```text
.dtsi/.dts
↓
描述：
UART8在哪里
PE1/PE0怎么复用
clock是谁
irq是谁

↓ dtb

Kernel
↓
Driver读取Device Tree
↓
pinctrl/clock/UART Driver
真正写寄存器
↓
UART工作
```

所以你现在可以非常准确地说：

> **Device Tree 本身不是初始化函数，它更像把 STM32 `Init()` 中“硬件配置数据”抽离了出来；真正执行初始化动作的仍然是 Linux 内核的各种 Driver。**

而这条链最核心的五个动作，就是：

```text
#include
↓
把多个公共.dtsi拼进来

&uart8
↓
找到已有节点并追加/覆盖

dtc
↓
DTS → DTB

U-Boot
↓
把Kernel和DTB加载到DDR

Kernel
↓
解析DTB并匹配Driver
```

这五步吃透以后，你再看韦东山后面真正修改设备树、驱动 probe 的代码，就不会只是“照着敲”，而是知道整个系统为什么这么走。









# 问题8

**STM32 裸机中的一个 `Init()` 往往把“硬件配置数据”和“执行初始化动作”写在一起；Linux 把前者主要放进 Device Tree，把后者分给 pinctrl、clock、UART 等驱动和内核子系统执行。**
