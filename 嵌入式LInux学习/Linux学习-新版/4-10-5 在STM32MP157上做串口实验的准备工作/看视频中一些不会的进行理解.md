# 与挂载相关的指令

可以。我把视频里这一段操作重新串了一遍。你现在最容易混淆的其实不是某一条命令，而是<span style="background:#00FF80;">**为什么先联网、再挂 NFS、再挂 `/boot`、再复制 dtb**。</span>它们其实是一条完整链路。

这段视频大致在做：

```text
开发板启动
   ↓
让 eth0 获取 IP
   ↓
开发板通过网络访问 Ubuntu
   ↓
把 Ubuntu 的 nfs_rootfs 挂载到开发板 /mnt
   ↓
开发板因此能看到 Ubuntu 中准备好的 dtb
   ↓
再把开发板自己的 boot 分区挂载到 /boot
   ↓
把新的 dtb 从 /mnt 复制到 /boot
   ↓
sync 写入存储设备
   ↓
重启开发板
   ↓
查看新的串口设备节点是否出现
```

视频里这一部分出现的主要命令，我给你逐条解释。

### 1. 查看当前的串口设备

```bash
ls /dev/tty
```

或者后面：

```bash
ls /dev/ttySTM*
```

`ls` 就是查看文件。

<span style="background:#00FF80;">Linux 里面硬件设备通常会以**设备文件**的形式出现在 `/dev` 目录</span>，所以：

```text
/dev/ttySTM0
/dev/ttySTM1
```

这些不是普通文件，而是<span style="color:#FF0000; background:#00FF80;"> STM32 UART 对应的设备节点。</span>

老师<span style="background:#00FF80;">在修改设备树之前查看一次，修改后又查看一次，本质上是在比较：</span>

> <span style="background:#00FF80; color:#FF0000;">修改设备树以后，新的 UART 驱动有没有成功创建对应的设备节点。</span>

------

### 2. 让<span style="background:#00FF80;">开发板通过 DHCP 获取 IP 地址</span>

视频中执行的是：

```bash
udhcpc -i eth0
```

拆开来看：

```text
udhcpc
│
└── 一个轻量级 DHCP 客户端

-i eth0
   │
   └── 指定使用 eth0 网卡
```

也就是：

> <span style="background:#00FF80; color:#FF0000;">让开发板的 `eth0` 网口向网络中的 DHCP 服务器申请一个 IP 地址。</span>

视频中申请到了类似：

```text
192.168.1.6
```

所以这一步之后：

```text
开发板 eth0
    ↓
192.168.1.6
```

<span style="color:#FF0000; background:#00FF80;">开发板才具备通过以太网访问 Ubuntu 主机的条件。</span>

这一点非常重要，因为<span style="background:#00FF80;">后面的 NFS 本质就是**网络访问**。</span>

------

### 3. Ubuntu 上把新的 DTB 放进 NFS 共享目录

视频文档中给出的命令：

```bash
cp stm32mp157c-100ask-512d-lcd-v1.dtb ~/nfs_rootfs/
```

`cp` 就是复制。

相当于：

```text
stm32mp157c-100ask-512d-lcd-v1.dtb

              cp
               ↓

/home/book/nfs_rootfs/
```

其中：

```bash
~
```

代表当前用户的 home 目录。

例如当前用户是 `book`：

```text
~/nfs_rootfs/

实际上就是：

/home/book/nfs_rootfs/
```

为什么要放这里？

因为这个目录已经被 Ubuntu 配置成了 **NFS 共享目录**。

------

## 4. 最关键的一条：挂载 NFS

视频实际终端里执行的是：

```bash
mount -t nfs -o nolock,vers=3 \
192.168.1.137:/home/book/nfs_rootfs /mnt
```

这条命令建议你重点理解。

它的整体含义是：

> 把 IP 为 `192.168.1.137` 的 Ubuntu 主机上的 `/home/book/nfs_rootfs`，通过 NFS 挂载到开发板自己的 `/mnt` 目录。

可以画成：

```text
Ubuntu PC
192.168.1.137

/home/book/nfs_rootfs
        │
        │ 网络 NFS
        │
        ▼
STM32MP157 开发板

/mnt
```

挂载成功以后，在开发板执行：

```bash
ls /mnt
```

看到的实际上就是：

```text
Ubuntu：
/home/book/nfs_rootfs
```

里面的内容。

### 把参数拆开

```bash
mount
```

Linux 的挂载命令。

```bash
-t nfs
```

`-t` 是 type：

```text
文件系统类型 = NFS
```

也就是说告诉 Linux：

> 我要挂的不是 ext4、FAT，而是网络文件系统 NFS。

------

```bash
-o nolock,vers=3
```

`-o` 后面是挂载选项。

其中：

```text
nolock
```

表示不使用 NFS 文件锁服务。

嵌入式开发环境中比较常见，因为开发板系统可能没有完整运行 NFS lock 服务。

而：

```text
vers=3
```

表示：

```text
使用 NFS v3 协议
```

------

接下来：

```bash
192.168.1.137:/home/book/nfs_rootfs
```

这是**远程目录**。

格式其实是：

```text
服务器IP:服务器目录
```

也就是：

```text
192.168.1.137
        │
        └── Ubuntu 主机

/home/book/nfs_rootfs
        │
        └── Ubuntu 上共享的目录
```

最后：

```bash
/mnt
```

是开发板本地的挂载点。

所以整个命令可以理解成一句很生活化的话：

> “开发板啊，你把 Ubuntu 192.168.1.137 上面的 `/home/book/nfs_rootfs` 接到你自己的 `/mnt` 上。”

------

### 视频文档里还有另一个 NFS 命令

文档中还写了 NAT 情况下的：

```bash
mount -t nfs -o nolock,vers=3,port=2049,mountport=9999 \
192.168.1.100:/home/book/nfs_rootfs /mnt
```

多出了：

```text
port=2049
mountport=9999
```

也就是人为指定 NFS 相关服务端口。

不过视频中实际操作使用的是更简单的：

```bash
mount -t nfs -o nolock,vers=3 \
192.168.1.137:/home/book/nfs_rootfs /mnt
```

这里我还注意到一个细节：视频文档截图里有一处写成了 `193.168.1.137`，但实际终端执行的是：

```text
192.168.1.137
```

而且左侧连接信息也是 `192.168.1.137`，所以你学习的时候以**实际执行的 `192.168.1.137`**为准，文档那里的 `193` 很可能只是笔误。

------

## 5. 挂载开发板自己的 boot 分区

接下来执行：

```bash
mount /dev/mmcblk2p2 /boot
```

这一步和刚才 NFS 的 `mount` 是同一个思想，但挂载对象完全不一样。

前面：

```bash
mount -t nfs ... /mnt
```

挂的是：

```text
远程 Ubuntu 文件系统
```

现在：

```bash
mount /dev/mmcblk2p2 /boot
```

挂的是：

```text
开发板本地存储设备上的一个分区
```

其中：

```text
/dev/mmcblk2p2
```

可以拆成：

```text
mmcblk2
   │
   └── 第 2 个 MMC/SD/eMMC 块设备

p2
│
└── 第 2 个分区
```

也就是：

```text
/dev/mmcblk2p2
        ↓
开发板存储设备中的第 2 分区
```

把它挂载到：

```text
/boot
```

之后：

```bash
ls /boot
```

看到的才真正是这个 boot 分区里的文件。

这就是 Linux 很重要的一个思想：

```text
设备 / 分区
      ↓
    mount
      ↓
普通目录
      ↓
程序通过目录访问
```

------

## 6. 把新的设备树复制进 boot 分区

视频中的命令：

```bash
cp /mnt/stm32mp157c-100ask-512d-lcd-v1.dtb /boot
```

现在你理解前两次 `mount` 以后，这条命令就特别清楚了。

此时：

```text
/mnt
 │
 └── 实际对应 Ubuntu 的 /home/book/nfs_rootfs

/boot
 │
 └── 实际对应开发板的 /dev/mmcblk2p2
```

于是：

```bash
cp /mnt/xxx.dtb /boot
```

本质上就是：

```text
Ubuntu PC
新的 dtb
   │
   │ NFS
   ▼
开发板 /mnt/xxx.dtb
   │
   │ cp
   ▼
开发板 /boot/xxx.dtb
   │
   ▼
eMMC / SD 中的 boot 分区
```

所以你甚至可以把这个过程理解成：

> **通过网络把 Ubuntu 上编译好的设备树更新到开发板启动分区。**

而不是非要用 U 盘或者 FileZilla 再传一次。

------

## 7. `sync`

复制完以后视频执行：

```bash
sync
```

这个也非常重要。

你以前学 Linux 文件 I/O 的时候其实已经接触过这个思想：

```text
程序写文件
   ↓
Linux 内核缓存
   ↓
真正的 eMMC / SD
```

`cp` 命令执行完成，并不一定意味着所有数据已经立刻物理写入存储芯片。

所以：

```bash
sync
```

就是要求 Linux：

> 把尚未写入磁盘/eMMC/SD 卡的数据尽快同步到底层存储设备。

所以更新 boot 文件以后执行：

```bash
sync
```

是很正常的操作。

否则如果马上断电重启，有可能数据还停留在缓存里。

这和你之前学习的 Page Cache / `fsync()` / `sync()` 是能够直接串起来的。

------

## 最后把整套命令放到一起

视频这一小段你可以先记成下面这套流程：

```bash
# 1. 查看已有串口设备
ls /dev/tty

# 2. 给开发板 eth0 获取 IP
udhcpc -i eth0

# 3. Ubuntu 上准备新的设备树
cp stm32mp157c-100ask-512d-lcd-v1.dtb ~/nfs_rootfs/

# 4. 开发板挂载 Ubuntu 的 NFS 目录
mount -t nfs -o nolock,vers=3 \
192.168.1.137:/home/book/nfs_rootfs /mnt

# 5. 开发板挂载自己的 boot 分区
mount /dev/mmcblk2p2 /boot

# 6. 把新设备树从 NFS 目录复制到 boot 分区
cp /mnt/stm32mp157c-100ask-512d-lcd-v1.dtb /boot

# 7. 强制把缓存数据写入存储设备
sync

# 8. 重启以后查看 STM32 串口节点
ls /dev/ttySTM*
```

最关键的是不要把两个 `mount` 混在一起：

```text
① mount NFS

Ubuntu目录
/home/book/nfs_rootfs
       │
       │ 网络
       ▼
开发板 /mnt


② mount 本地分区

开发板 eMMC/SD
/dev/mmcblk2p2
       │
       ▼
开发板 /boot
```

然后：

```text
/mnt/new.dtb
     │
     │ cp
     ▼
/boot/new.dtb
```

这样一看，老师这一大串操作其实就非常简单了：

> **先让开发板通过 NFS“看见”电脑里的新设备树，再把这个设备树复制到开发板真正用于启动的 boot 分区中。**

这里还有一个特别值得继续弄明白的问题：**“挂载”到底是什么意思？为什么 `/mnt` 本来只是一个空目录，执行 `mount` 以后突然就能看到另一台电脑上的文件，而且文件实际上并没有被复制到开发板？**
这个正好涉及 Linux VFS、mount point、NFS client、网络协议这几个概念。我可以接着用一张从 `ls /mnt` 一直到 Ubuntu 磁盘的调用链给你彻底拆开。





# 开发板与主机连接

这里我有一个疑问，开发板和主机不应该是通过局域网来进行访问的吗，此时直接使用数据链路层的MAC地址不就行了吗，不是用不到IP地址吗，这里为什么还要使用udhcpc -i eth0 呢，我不是太懂，你能够给我详细解释下吗。





对，你这个疑问非常关键。你现在其实是把两个概念混到一起了：

> **<span style="background:#00FF80;">“局域网通信不经过路由器转发”</span>**
> 和
> **<span style="background:#00FF80;">“局域网通信不需要 IP”</span>**

这<span style="color:#FF0000;">两句话不是一回事。</span>

<span style="background:#00FF80;">开发板和 Ubuntu 主机即使处在**同一个局域网**，最终以太网帧确实是靠 **MAC 地址**送到对方网卡的；但是像视频里的 **NFS、SSH、ping、TCP/UDP Socket** 这些程序，仍然是建立在 **IP 协议**之上的。</span>

所以 `udhcpc -i eth0` 仍然有必要。

------

### 先看你当前这个场景

比如视频里：

```text
Ubuntu 主机
IP：192.168.1.137
MAC：AA:AA:AA:AA:AA:AA
       │
       │   同一个局域网
       │
STM32MP157 开发板
IP：192.168.1.6
MAC：BB:BB:BB:BB:BB:BB
```

然后开发板执行：

```bash
mount -t nfs -o nolock,vers=3 \
192.168.1.137:/home/book/nfs_rootfs /mnt
```

你看<span style="background:#00FF80; color:#FF0000;">这个命令里指定服务器时，用的就是：</span>

```text
192.168.1.137
```

<span style="color:#FF0000;">而不是：</span>

```text
AA:AA:AA:AA:AA:AA
```

<span style="color:#FF0000; background:#00FF80;">原因就是：</span>

```text
NFS
 ↓
TCP / UDP
 ↓
IP
 ↓
Ethernet
 ↓
网卡
```

<span style="color:#FF0000; background:#00FF80;">NFS 本身不是直接建立在 MAC 地址上的。</span>

------

## 那既然最后还是 MAC 地址发过去，为什么还需要 IP？

你这个理解有一半完全是对的：

> 在同一个以太网局域网里，真正把 Ethernet Frame 发送给另一台机器时，确实需要目的 MAC 地址。

但问题是：

**应用程序通常根本不知道目的 MAC。**

例如你执行：

```bash
ping 192.168.1.137
```

程序只知道：

```text
目标 IP = 192.168.1.137
```

它不知道：

```text
目标 MAC = ?
```

于是 Linux 会经过一个很关键的过程：

```text
IP
↓
ARP
↓
MAC
```

比如开发板发现：

```text
我要访问：
192.168.1.137
```

系统先根据：

```text
自己的 IP：192.168.1.6
子网掩码：255.255.255.0
```

判断：

```text
192.168.1.137 和我在同一网段
```

所以：

```text
不需要路由器
```

接下来它会问：

```text
谁是 192.168.1.137？
请把你的 MAC 告诉我。
```

这就是 **ARP Request**。

ARP 请求大致相当于：

```text
源 MAC：
BB:BB:BB:BB:BB:BB

目的 MAC：
FF:FF:FF:FF:FF:FF
广播

内容：
Who has 192.168.1.137?
Tell 192.168.1.6
```

Ubuntu 收到之后回答：

```text
192.168.1.137 is at
AA:AA:AA:AA:AA:AA
```

开发板于是得到：

```text
192.168.1.137
        ↓ ARP
AA:AA:AA:AA:AA:AA
```

然后才真正构造以太网帧。

------

## 真正发送一个 NFS 数据包时是什么样？

假设开发板访问 Ubuntu：

```text
开发板：
192.168.1.6

Ubuntu：
192.168.1.137
```

最终在网线上发送的数据，可以粗略理解成这样：

```text
┌────────────────────────────────┐
│ Ethernet Header                │
│                                │
│ 源 MAC：BB:BB:BB:BB:BB:BB     │
│ 目的 MAC：AA:AA:AA:AA:AA:AA   │
├────────────────────────────────┤
│ IP Header                      │
│                                │
│ 源 IP：192.168.1.6             │
│ 目的 IP：192.168.1.137         │
├────────────────────────────────┤
│ TCP / UDP Header               │
│                                │
│ 源端口                         │
│ 目的端口                       │
├────────────────────────────────┤
│ NFS 数据                       │
├────────────────────────────────┤
│ Ethernet FCS                   │
└────────────────────────────────┘
```

所以注意：

> **IP 地址并没有因为两台机器处在局域网就消失。**

而是同时存在两层地址：

```text
MAC 地址
负责这一跳怎么送到网卡

IP 地址
负责这个网络数据包是谁发给谁
```

------

## 那为什么不能直接用 MAC 地址访问 NFS？

理论上当然可以自己设计一种协议：

```text
应用程序
 ↓
自己直接构造 Ethernet Frame
 ↓
目标 MAC
```

Linux 甚至提供：

```text
raw socket
AF_PACKET
```

让你直接操作二层 Ethernet Frame。

例如自己设计：

```text
MAC A
 ↓
自定义协议
 ↓
MAC B
```

那么确实可以：

```text
完全不用 IP
```

但问题是：

NFS、SSH、HTTP、FTP、TCP Socket 等主流网络程序**不是这样设计的**。

它们的协议栈是：

```text
NFS
│
TCP / UDP
│
IP
│
Ethernet
│
MAC
```

所以 NFS 服务器不是通过：

```text
AA:BB:CC:DD:EE:FF:/home/book/nfs_rootfs
```

访问的，而是：

```text
192.168.1.137:/home/book/nfs_rootfs
```

------

## `udhcpc -i eth0` 到底干了什么？

现在回到视频里这条：

```bash
udhcpc -i eth0
```

`udhcpc` 是一个 DHCP Client。

它不是“让网卡工作”。

网卡本身可能早就已经：

```text
驱动加载成功
↓
eth0 出现
↓
可以发送 Ethernet Frame
```

了。

`udhcpc` 做的是：

> 给 `eth0` 配置 TCP/IP 网络参数。

通常会获取：

```text
IP 地址
子网掩码
默认网关
DNS
租期等
```

比如：

```text
eth0

MAC:
00:11:22:33:44:55

执行 udhcpc 之前：

IP:
无


执行：

udhcpc -i eth0

之后：

IP:
192.168.1.6

Mask:
255.255.255.0

Gateway:
192.168.1.1
```

这之后 Linux 的 TCP/IP 协议栈才知道：

```text
“我是谁？”
“哪些 IP 和我在一个局域网？”
“哪些 IP 需要通过网关访问？”
```

------

## 一个特别容易混淆的地方

你可能会进一步问：

> “可是 DHCP 自己也是网络协议啊，我还没有 IP，它怎么申请 IP？”

这个问题特别好。

因为 DHCP 在最开始的时候，客户端确实：

```text
没有 IP
```

所以 DHCP 会使用**广播**。

大致：

```text
开发板

源 IP：
0.0.0.0

目的 IP：
255.255.255.255

源 MAC：
开发板自己的 MAC

目的 MAC：
FF:FF:FF:FF:FF:FF
```

也就是：

```text
DHCP Discover
      ↓
Ethernet Broadcast
      ↓
FF:FF:FF:FF:FF:FF
```

它等于是对整个局域网喊：

> “我现在还没有 IP，有 DHCP 服务器能给我分一个吗？”

DHCP Server 回复：

```text
你可以使用：

192.168.1.6
```

之后开发板才真正拥有正常 IP。

------

## 所以 `udhcpc` 不是必须的吗？

这里又要分清楚。

**DHCP 不是必须的。**

但是对于 NFS 这种 IP 网络通信来说：

**配置一个 IP 地址通常是必须的。**

你完全可以不使用：

```bash
udhcpc -i eth0
```

而自己手动给开发板设置 IP。

比如：

```bash
ip addr add 192.168.1.6/24 dev eth0
ip link set eth0 up
```

老一些的系统可能使用：

```bash
ifconfig eth0 192.168.1.6 netmask 255.255.255.0 up
```

那么：

```text
DHCP 获取 IP
```

就变成：

```text
手动静态设置 IP
```

结果都是：

```text
eth0
↓
拥有 192.168.1.6
↓
能够正常使用 TCP/IP
↓
能够访问 NFS Server
```

所以视频里执行：

```bash
udhcpc -i eth0
```

只是为了方便。

不需要老师每次手工写：

```bash
ifconfig eth0 192.168.1.xxx ...
```

## 为什么局域网通信还要同时保留 IP 和 MAC？

你可以从“职责分工”理解。

假设：

```text
程序：
mount 192.168.1.137:/xxx /mnt
```

Linux 网络协议栈逐层处理：

```text
应用层
NFS
│
│ 我要访问 192.168.1.137
▼
传输层
TCP/UDP
│
│ 加入端口号
▼
网络层
IP
│
│ 192.168.1.6 → 192.168.1.137
▼
判断路由
│
├─ 同一网段
│
│   ↓
│   ARP
│   ↓
│   查 192.168.1.137 的 MAC
│
▼
数据链路层
Ethernet
│
│ BB:BB... → AA:AA...
▼
网卡
│
▼
网线
```

所以可以把它记成一句非常重要的话：

> **IP 决定“我要和哪台网络主机通信”，MAC 决定“这一跳的以太网帧具体交给哪个网卡”。**

在你的视频场景里，由于：

```text
开发板
192.168.1.6

Ubuntu
192.168.1.137
```

处于同一子网：

```text
192.168.1.0/24
```

所以：

```text
IP 包的目标：
192.168.1.137

这一跳 Ethernet 帧的目标 MAC：
Ubuntu 自己的 MAC
```

不需要经过网关。

------

### 如果不在同一个局域网，区别会更明显

比如开发板：

```text
192.168.1.6
```

要访问：

```text
8.8.8.8
```

这时候：

```text
IP 层目标：
8.8.8.8
```

但是 Ethernet 层目的 MAC **绝对不是 8.8.8.8 那台服务器的 MAC**。

而是：

```text
默认网关的 MAC
```

于是：

```text
IP：

192.168.1.6
    ↓
8.8.8.8
```

但是第一跳：

```text
MAC：

开发板 MAC
    ↓
路由器 MAC
```

路由器收到以后：

```text
拆掉当前 Ethernet Header
        ↓
根据 IP 判断下一跳
        ↓
重新封装一个新的 Ethernet Header
        ↓
继续发送
```

所以这时候你就更容易看出来：

```text
IP 地址
和
MAC 地址

根本不是二选一
```

它们属于不同层，完成不同任务。

------

你现在可以把视频里的 `udhcpc -i eth0` 放到整个流程里理解：

```text
网卡驱动加载
        ↓
出现 eth0
        ↓
eth0 本身有 MAC 地址
        ↓
udhcpc -i eth0
        ↓
获得 IP：
192.168.1.6
        ↓
开发板有完整 TCP/IP 网络能力
        ↓
mount -t nfs
192.168.1.137:/home/book/nfs_rootfs
        ↓
判断 192.168.1.137 在同一网段
        ↓
ARP：
192.168.1.137 是哪个 MAC？
        ↓
得到 Ubuntu MAC
        ↓
Ethernet Frame
        ↓
网线
        ↓
Ubuntu
        ↓
NFS Server
        ↓
/home/book/nfs_rootfs
```

所以你原来的说法可以稍微修正成：

> **开发板和主机位于同一局域网时，不需要路由器来转发两者之间的数据包；最终二层传输确实依赖 MAC 地址。但 NFS 等上层协议运行在 TCP/IP 协议栈上，因此开发板仍然需要配置 IP 地址。`udhcpc -i eth0` 的作用就是通过 DHCP 给 `eth0` 获取 IP、子网掩码等网络参数。之后 Linux 再通过 ARP 将目标 IP 转换为目标 MAC，最终用 Ethernet 帧完成局域网内的实际传输。**

这个地方一旦弄明白，你后面学 Socket 时的 **IP + 端口、ARP、路由表、网关、交换机和路由器为什么不是一回事**，基本就会一下连起来了。
