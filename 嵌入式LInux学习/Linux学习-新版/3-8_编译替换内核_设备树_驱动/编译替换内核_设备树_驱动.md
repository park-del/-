## 5. 为什么写驱动前要先编译内核？

### 5.1 驱动需要内核头文件

普通应用程序可能包含：

```c
#include <stdio.h>
```

<span style="color:#FF0000; background:#00FF80;">驱动程序则会包含大量Linux内核头文件</span>，例如：

```c
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>
#include <asm/io.h>
```

这些<span style="color:#FF0000; background:#00FF80;">头文件提供：</span>

- 内核数据类型；
- 驱动接口；
- 模块宏；
- 文件操作结构体；
- 中断、内存、GPIO等接口；
- 与CPU架构有关的定义。

<span style="color:#FF0000; background:#00FF80;">一些文件只有在配置和准备内核源码后才能正确生成或建立</span>，例如：

```text
include/generated/
include/config/
arch/arm/include/
asm相关链接或架构头文件
```

因此，<span style="color:#FF0000; background:#00FF80;">不能随便找一份没配置过的内核源码直接编译驱动</span>。

------

### 5.2 驱动模块要和开发板上的内核匹配

假设开发板正在运行：

```text
Linux 4.9.88，配置A
```

但你编译驱动时使用：

```text
Linux 5.x，或者4.9.88的配置B
```

<span style="color:#FF0000; background:#00FF80;">即使都叫Linux，内部接口、结构体和功能配置也可能不同。</span>

加载模块时可能出现：

```text
Invalid module format
```

或者内核日志显示：

```text
version magic ... should be ...
```

模块中通常带有类似的版本匹配信息：

```text
vermagic
```

它可能包含：

- 内核版本；
- SMP配置；
- 抢占配置；
- ARM架构信息；
- 模块版本配置。

所以需要保证：

```text
编译模块所用内核源码和配置
             =
开发板实际运行的内核和配置
```

------

### 5.3 <span style="background:#00FF80;">内核配置决定哪些接口存在</span>

<span style="color:#FF0000; background:#00FF80;">Linux内核中的功能可被配置成：</span>

| 配置状态       | 含义                   |
| -------------- | ---------------------- |
| `CONFIG_XXX=y` | 编译进内核，即内置驱动 |
| `CONFIG_XXX=m` | 编译为可加载模块 `.ko` |
| 未启用         | 不编译该功能           |

<span style="color:#FF0000; background:#00FF80;">驱动所依赖的接口如果没有启用，即使代码存在，也可能无法编译或运行。</span>

------

## 6. <span style="background:#00FF80;">内核、设备树、模块分别是什么</span>？

### 6.1 `zImage`：<span style="background:#00FF80;">Linux内核镜像</span>

生成位置：

```text
arch/arm/boot/zImage
```

它包含：

- Linux内核核心；
- 进程调度；
- 内存管理；
- 文件系统框架；
- 网络协议；
- <span style="background:#00FF80; color:#FF0000;">所有配置为 `=y` 的内置驱动。</span>

U-Boot会把 `zImage`从存储介质加载到DDR，然后启动它。

------

### 6.2 `.dtb`：<span style="background:#00FF80;">设备树二进制文件</span>

视频使用的文件是：

```text
100ask_imx6ull-14x14.dtb
```

生成位置类似：

```text
arch/arm/boot/dts/100ask_imx6ull-14x14.dtb
```

<span style="color:#FF0000; background:#00FF80;">设备树告诉Linux内核开发板上有什么硬件</span>，例如：

```text
内存大小
串口地址
eMMC控制器
网卡
GPIO
LED
I²C和SPI设备
中断编号
引脚复用
```

可以记成：

```text
zImage：内核“会做什么”
DTB：这块板“有什么硬件、硬件在哪里”
```

------

## 6.3 `.ko`：可加载内核模块

执行：

```bash
make modules
```

会编译配置为：

```text
CONFIG_XXX=m
```

的功能，生成 `.ko`文件。

例如：

```text
cp210x.ko
ftdi_sio.ko
snd-usb-audio.ko
```

<span style="color:#FF0000; background:#00FF80;">这些模块不会全部放进 `zImage`，而是安装到根文件系统的：</span>

```text
/lib/modules/内核版本/
```

<span style="color:#FF0000;">系统运行后可以使用：</span>

```bash
insmod xxx.ko
modprobe xxx
```

<span style="color:#FF0000; background:#00FF80;">加载。</span>

## 7. 内核编译命令逐条解释

视频中的主要命令大致为：

```bash
cd /home/book/100ask_imx6ull-sdk
cd Linux-4.9.88
```

进入<span style="color:#FF0000; background:#00FF80;">内核源码目录。</span>

------

### 7.1 清理源码

```bash
make mrproper
```

作用是<span style="color:#FF0000; background:#00FF80;">清除之前的：</span>

- `.config`；
- 中间目标文件；
- 自动生成文件；
- 旧的构建结果。

它比普通：

```bash
make clean
```

清理得更彻底。

需要注意：

> `mrproper`也会删除原来的 `.config`，所以后面必须重新执行开发板配置命令。

------

### 7.2 选择开发板默认配置

```bash
make 100ask_imx6ull_defconfig
```

这条命令会从：

```text
arch/arm/configs/100ask_imx6ull_defconfig
```

读取默认配置，并生成：

```text
Linux-4.9.88/.config
```

<span style="color:#FF0000; background:#00FF80;">`.config`决定：</span>

- 目标CPU架构；
- <span style="color:#FF0000; background:#00FF80;">哪些驱动内置；</span>
- <span style="color:#FF0000; background:#00FF80;">哪些驱动编译为模块；</span>
- <span style="color:#FF0000; background:#00FF80;">哪些文件系统启用；</span>
- <span style="color:#FF0000; background:#00FF80;">是否支持网络、USB等功能。</span>

------

### 7.3 编译内核

```bash
make zImage -j4
```

其中：

```text
zImage：编译压缩的ARM Linux内核镜像
-j4：同时执行最多4个编译任务
```

视频完成后显示：

```text
Kernel: arch/arm/boot/zImage is ready
```

说明<span style="color:#FF0000; background:#00FF80;">内核镜像已经生成。</span>

------

### 7.4 编译设备树

```bash
make dtbs
```

其中：

```text
dtbs = device tree binaries
```

它<span style="color:#FF0000; background:#00FF80;">会把 `.dts`、`.dtsi`源文件编译成开发板可以使用的 `.dtb`文件。</span>

------

## 8. 为什么先编译 `zImage`，再编译设备树？

技术上，准备完整的情况下可以分别执行目标；视频按以下顺序演示：

```bash
make zImage -j4
make dtbs
```

这种顺序比较容易理解，也能<span style="color:#FF0000; background:#00FF80;">先确保内核构建环境和生成文件已经准备完成</span>。

更常见的一次性命令也可能是：

```bash
make -j4 zImage dtbs modules
```

但学习阶段分开执行，更容易定位哪一步出错。

## 9. 为什么还要执行 `make modules`？

```bash
make zImage
```

<span style="color:#FF0000; background:#00FF80;">只会把配置为内置的内容编入内核</span>。

<span style="color:#FF0000;">配置成模块的驱动还需要：</span>

```bash
make modules
```

它<span style="color:#FF0000; background:#00FF80;">会生成所有启用的 `.ko`模块。</span>

所以：

```text
make zImage
→ 生成内核和内置驱动

make modules
→ 生成外置的可加载驱动
```

## 10.`modules_install`是什么意思？

视频执行的命令类似：

```bash
sudo make ARCH=arm \
INSTALL_MOD_PATH=/home/book/nfs_rootfs \
modules_install
```

它<span style="color:#FF0000; background:#00FF80;">不是把模块安装到Ubuntu自己的 `/lib/modules`，而是安装到指定的临时根目录：</span>

```text
/home/book/nfs_rootfs
```

最终产生：

```text
/home/book/nfs_rootfs/
└── lib/
    └── modules/
        └── 4.9.88.../
            ├── kernel/
            │   ├── drivers/
            │   ├── fs/
            │   ├── net/
            │   └── sound/
            ├── modules.dep
            ├── modules.alias
            └── modules.symbols
```

其中：

```text
INSTALL_MOD_PATH
```

可以理解为：

> 把未来开发板的根目录临时模拟在Ubuntu的这个目录下。

<span style="color:#FF0000; background:#00FF80;">如果不指定它，可能会错误地把ARM模块安装进Ubuntu主机自身的 `/lib/modules`中。</span>

## 11. 为什么路径仍然叫 `nfs_rootfs`，却使用ADB？

这是课程历史流程留下的目录名。

早期流程是：

```text
把文件放到 ~/nfs_rootfs
→ 开发板通过NFS访问
```

2025年勘误后的流程是：

```text
仍把它作为临时整理目录
→ 再用adb push复制到开发板
```

所以现在的：

```text
/home/book/nfs_rootfs
```

主要可以理解成：

> <span style="background:#00FF80;">用来集中保存 `zImage`、DTB和模块目录的暂存区。</span>

它不代表这一次必须使用NFS。

### 12.1 <span style="background:#00FF80;">替换Linux内核</span>

```bash

```

```text
Ubuntu的zImage
      ↓ USB OTG / ADB

```

```bash
adb push 100ask_imx6ull-14x14.dtb /boot
```

```text
开发板 /boot/100ask_imx6ull-14x14.dtb
```

### 12.3 <span style="background:#00FF80;">替换模块目录</span>

```bash

```

会把Ubuntu暂存目录中的：

```text

```

```text
/lib/modules/
```

## 13. 为什么要执行 `sync`？

文件成功显示为“pushed”，数据可能仍有一部分停留在Linux缓存中。

进入开发板：

```bash
adb shell
```

执行：

```bash
sync
```

作用是：

> <span style="background:#00FF80;">强制把缓存中的修改写入eMMC等持久化存储。</span>

然后再执行：

```bash
reboot
```

可<span style="background:#00FF80;">以降低立即重启导致文件尚未完整落盘的风险</span>。

流程应记成：

```text
adb push
→ sync
→ reboot
```

------

## 14. 为什么必须重启？

<span style="color:#FF0000; background:#00FF80;">当前运行中的内核已经加载到DDR。</span>

即使你覆盖了：

```text
/boot/zImage
```

正在运行的旧内核也不会自动变成新内核。

必须重新启动：

```text
重启
  ↓
U-Boot重新读取/boot/zImage和DTB
  ↓
新内核进入DDR
  ↓
Linux使用新的/lib/modules
```

因此替换内核后，`reboot`是生效步骤。

------

## 15. 如何验证替换成功？

视频重启后再次执行：

```bash
adb shell
uname -a
```

输出中可以看到类似：

```text
Linux 100ask 4.9.88 #2 SMP PREEMPT
Sat May 10 02:13:07 EDT 2025 armv7l GNU/Linux
```

可以重点检查：

```text
4.9.88
→ 内核版本

构建日期
→ 是否是刚刚编译的时间

armv7l
→ 当前运行在32位ARM开发板
```

<span style="color:#FF0000; background:#00FF80;">如果构建日期发生变化，通常能证明启动的是新编译的内核。</span>

还可以进一步检查：

```bash
uname -r
ls /lib/modules/$(uname -r)
```

确认当前内核版本对应的模块目录存在。

## 16. “内核、设备树、驱动都必须每次一起替换吗？”

视频为了建立一致的开发基线，把三部分一起编译、一起替换。更准确地说：

| 修改内容                                                     | 一般需要替换         |
| ------------------------------------------------------------ | -------------------- |
| 修改<span style="color:#FF0000; background:#00FF80;">内核核心或内置驱动</span> | `zImage`             |
| 修改<span style="color:#FF0000; background:#00FF80;">设备树 `.dts/.dtsi`</span> | 对应 `.dtb`          |
| 修改<span style="color:#FF0000; background:#00FF80;">配置为模块的驱动</span> | 对应 `.ko`或模块目录 |
| 三者都修改                                                   | 三者全部替换         |

例如<span style="color:#FF0000; border:1px solid #330000; background:#00FF80;">只修改一个独立的</span>：

```text
hello_drv.ko
```

而<span style="color:#FF0000; background:#00FF80;">内核源码、配置和版本没变，通常可以只上传新的 `.ko`，不需要每次都重编和替换整个 `zImage`。</span>

但第一次建立驱动环境时，完整替换一次很有价值，因为可以确保：

```text
正在运行的内核
设备树
/lib/modules
编译驱动使用的源码与配置
```

全部来自同一套构建结果。

## 17. 最容易混淆的三个“驱动”

### <span style="background:#00FF80;">内置驱动</span>

配置为：

```text
CONFIG_XXX=y
```

它<span style="background:#00FF80; color:#FF0000;">直接在</span>：

```text
zImage
```

<span style="color:#FF0000; background:#00FF80;">里面，替换内核才能替换它。</span>

### <span style="background:#00FF80;">模块驱动</span>

配置为：

```text
CONFIG_XXX=m
```

它生成：

```text
xxx.ko
```

保存在：

```text
/lib/modules/
```

<span style="color:#FF0000; background:#00FF80;">可以单独加载、卸载和替换。</span>

### 设备树节点

<span style="color:#FF0000; background:#00FF80;">设备树不是驱动程序，它只是描述：</span>

```text
设备是否存在
寄存器地址
中断
GPIO
时钟
兼容字符串
```

<span style="color:#FF0000; background:#00FF80;">内核根据设备树找到设备，再匹配对应驱动。</span>

## 21. 重点片段精读

### 片段一：01:25-02:50

**表面发生了什么：**

**更深层含义：**
内核模块不是普通可执行文件，它直接进入内核地址空间，使用内核内部接口。版本或配置错误可能不仅加载失败，还可能造成系统异常。

**重要性：**
这是整节课的理论核心。

------

**重要性：**
配置选错，后面的文件即使编译成功，也可能无法适配开发板。
