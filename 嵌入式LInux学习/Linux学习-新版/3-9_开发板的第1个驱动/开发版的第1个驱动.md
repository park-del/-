## 5. 这个实验中的三个文件分别做什么？

源码目录中有：

```text
01_hello_drv/
├── hello_drv.c
├── hello_drv_test.c
└── Makefile
```

### 5.1 `hello_drv.c`

这是<span style="background:#00FF80;">**内核驱动程序**。</span>

编译结果是：

```text
hello_drv.ko
```

它<span style="color:#FF0000; background:#00FF80;">不能像普通APP一样执行：</span>

```bash

```

而<span style="color:#FF0000; background:#00FF80;">要使用：</span>

```bash

```

<span style="color:#FF0000; background:#00FF80;">把它加载进Linux内核。</span>

它<span style="color:#FF0000; background:#00FF80;">主要完成：</span>

- 注册字符设备；
- 获得主设备号；
- <span style="background:#00FF80; color:#FF0000;">创建 `/dev/hello`；</span>
- 实现 `open`；
- 实现 `read`；
- 实现 `write`；
- 实现 `release`；
- <span style="color:#FF0000; background:#00FF80;">模块卸载时删除设备并注销字符设备。</span>

------

### 5.2 `hello_drv_test.c`

这是**用户空间测试程序**。

编译结果是：

```text
hello_drv_test
```

<span style="color:#FF0000; background:#00FF80;">它会打开</span>：

```text
/dev/hello
```

然后<span style="color:#FF0000; background:#00FF80;">根据参数调用：</span>

```text

```

它<span style="color:#FF0000; background:#00FF80;">与普通Linux应用程序一样运行：</span>

```bash

```

它同时负责：

1. <span style="color:#FF0000; background:#00FF80;">调用Linux内核的Kbuild系统编译</span> `hello_drv.ko`；

## 6. 为什么<span style="background:#00FF80;">编译驱动前必须先编译内核</span>？

视频重点解释了三个原因。

### 原因一：<span style="background:#00FF80;">需要内核生成的头文件和链接</span>

驱动代码中包含：

```c
#include <linux/module.h>
#include <linux/fs.h>
#include <asm/io.h>
```

<span style="color:#FF0000; background:#00FF80;">其中一部分文件或链接只有在内核完成配置、准备或编译后才存在。</span>

例如：

```text
include/generated/
include/config/
arch/arm/include/
asm相关架构链接
```

这里的：

```c
#include <asm/io.h>
```

不是固定指向所有CPU使用的一套文件。

对于IMX6ULL，它需要对应ARM架构：

```text
asm → asm-arm相关头文件
```

<span style="color:#FF0000; background:#00FF80;">如果内核没有正确配置目标架构，驱动编译可能找不到头文件，或者使用错误架构的定义。</span>

------

### 原因二：模块必须和板上运行的内核一致

<span style="color:#FF0000; background:#00FF80;">驱动编译时使用的是：</span>

```text
Ubuntu中的Linux内核源码和.config
```

<span style="color:#FF0000; background:#00FF80;">驱动加载时依赖的是：</span>

```text
开发板当前正在运行的Linux内核
```

<span style="color:#FF0000; background:#00FF80;">二者应当来自同一套构建环境：</span>

```text
编译驱动的内核源码
        +
内核.config
        +
编译选项
        +
符号版本
        =
开发板运行的内核
```

否则可能出现：

```text
Invalid module format
```

或者：

```text
disagrees about version of symbol module_layout
```

------

### 原因三：替换内核后，原有模块也可能需要替换

<span style="color:#FF0000;">假设开发板原来运行厂商内核A，里面的模块也是用内核A编译的。</span>

后来<span style="color:#FF0000; background:#00FF80;">你把内核替换为自己编译的内核B：</span>

```text
旧内核A → 新内核B
```

那么原来 `/lib/modules` 中的模块仍然可能属于内核A。

因此上一节才同时替换：

```text
/boot/zImage
/boot/*.dtb
/lib/modules/4.9.88/
```

这样可以确保：

```text
内核镜像
设备树
内核模块
外部驱动编译环境
```

来自同一套构建结果。

视频只快速展示了源码，下面按照其实际结构拆解。

画面中出现了：

```c

#include <linux/fs.h>
#include <linux/errno.h>
#include <linux/miscdevice.h>
#include <linux/kernel.h>
#include <linux/major.h>
#include <linux/mutex.h>

#include <linux/seq_file.h>
#include <linux/stat.h>
#include <linux/init.h>
#include <linux/device.h>
#include <linux/tty.h>
#include <linux/kmod.h>
#include <linux/gfp.h>
```

最核心的几项是：

```c
linux/module.h
```

提供模块相关宏，例如：

```c
module_init()
module_exit()
MODULE_LICENSE()
linux/fs.h
```

提供：

```c
struct file_operations
register_chrdev()
linux/device.h
```

提供：

```c
class_create()
device_create()
```

<span style="color:#FF0000; background:#00FF80;">用来自动生成设备节点。</span>

------

### 7.2 主设备号

代码中有：

```c
static int major = 0;
```

这里先设为0，意味着注册设备时让内核动态分配主设备号。

后面大致执行：

```c
major = register_chrdev(0, "hello", &hello_drv);
```

内核会返回一个可用主设备号。

视频中通过：

```bash
cat /proc/devices
```

可以查看字符设备列表，确认驱动已经注册。

<span style="color:#FF0000; background:#00FF80;">主设备号的作用是：</span>

> <span style="background:#00FF80;">告诉Linux，这个设备节点应该由哪一个驱动程序处理。</span>

------

### 7.3 内核缓冲区

代码中有：

```c
static char kernel_buf[1024];
```

它是<span style="color:#FF0000; background:#00FF80;">一块位于内核空间的内存。</span>

测试程序写入：

```text
www.100ask.net
```

时，数据被保存到：

```text
kernel_buf
```

随后测试程序读取，驱动再把同一字符串返回。

<span style="color:#FF0000;">这个驱动没有真正控制LED、GPIO或硬件，它只是用内存缓冲区演示字符设备的读写流程。</span>

所以它属于：

> **<span style="background:#00FF80;">用于学习驱动框架的虚拟字符设备。</span>**

## 8.`file_operations`为什么重要？

<span style="color:#FF0000; background:#00FF80;">用户APP调用的是：</span>

```c
open()
read()
write()
close()
```

<span style="color:#FF0000; background:#00FF80;">驱动中实现的是：</span>

```c
hello_drv_open()
hello_drv_read()
hello_drv_write()
hello_drv_close()
```

<span style="color:#FF0000;">Linux需要知道它们之间如何对应，这由：</span>

```c
struct file_operations
```

<span style="color:#FF0000;">完成。</span>

其逻辑大致是：

```c
static struct file_operations hello_drv = {
    .owner   = THIS_MODULE,
    .open    = hello_drv_open,
    .read    = hello_drv_read,
    .write   = hello_drv_write,
    .release = hello_drv_close,
};
```

对应关系：

| 用户APP调用          | 驱动函数            |
| -------------------- | ------------------- |
| `open("/dev/hello")` | `hello_drv_open()`  |
| `read(fd, ...)`      | `hello_drv_read()`  |
| `write(fd, ...)`     | `hello_drv_write()` |
| `close(fd)`          | `hello_drv_close()` |

这是<span style="color:#FF0000; background:#00FF80;">字符设备驱动最核心的思想：</span>

> <span style="background:#00FF80;">用户程序看见的是普通文件接口；Linux内核把文件操作转换为驱动函数调用。</span>

## 9. 用户空间和内核空间怎样传数据？

用户程序不能直接访问：

```c
kernel_buf
```

因为用户空间和内核空间是隔离的。

### 写入过程

用户APP执行：

```c
write(fd, "www.100ask.net", length);
```

流程：

```text
用户空间字符串
        ↓ write系统调用
Linux VFS
        ↓
hello_drv_write()
        ↓ copy_from_user
kernel_buf
```

驱动中一般使用：

```c
copy_from_user(kernel_buf, buf, size);
```

含义是：

> <span style="color:#FF0000; background:#00FF80;">从用户空间地址复制数据到内核空间。</span>

------

### 读取过程

用户APP执行：

```c
read(fd, buf, size);
```

流程：

```text
kernel_buf
        ↓ copy_to_user
hello_drv_read()
        ↓ read系统调用返回
用户空间buf
```

<span style="color:#FF0000; background:#00FF80;">驱动中一般使用：</span>

```c
copy_to_user(buf, kernel_buf, size);
```

含义是：

> <span style="color:#FF0000; background:#00FF80;">从内核空间复制数据到用户空间。</span>

因此：

```text
copy_from_user：用户 → 内核
copy_to_user：内核 → 用户
```

这是非常容易记反的一组函数。

## 10. 驱动加载时发生了什么？

开发板执行：

```bash
insmod hello_drv.ko
```

<span style="color:#FF0000; background:#00FF80;">内核会调用驱动注册的初始化函数：</span>

```c
module_init(hello_init);
```

完整过程大致是：

```text
insmod hello_drv.ko
        ↓
内核加载ELF模块
        ↓
解析模块依赖和符号
        ↓
执行hello_init()
        ↓
register_chrdev()
        ↓
分配主设备号
        ↓
class_create()
        ↓
device_create()
        ↓
生成/dev/hello
```

之后执行：

```bash
ls /dev/hello
```

能看到：

```text
/dev/hello
```

说明设备节点已经生成。

------

### `/dev/hello`是不是驱动程序本身？

不是。

三个对象必须区分：

```text
hello_drv.ko
→ 驱动模块文件

驱动代码
→ 加载后存在于内核空间

/dev/hello
→ 用户程序访问该驱动的设备节点
```

<span style="background:#00FF80;">`/dev/hello`更像一个入口。</span>

<span style="color:#FF0000; background:#00FF80;">用户程序打开 `/dev/hello` 后，Linux根据设备号找到 `hello_drv`驱动。</span>

## 12. Makefile逐行解释

视频中的Makefile核心内容类似：

```makefile
KERN_DIR = /home/book/100ask_imx6ull-sdk/Linux-4.9.88

all:
	make -C $(KERN_DIR) M=`pwd` modules
	$(CROSS_COMPILE)gcc -o hello_drv_test hello_drv_test.c

clean:
	make -C $(KERN_DIR) M=`pwd` modules clean
	rm -rf modules.order
	rm -f hello_drv_test

obj-m += hello_drv.o
```

------

### 12.1 `KERN_DIR`

```makefile
KERN_DIR = /home/book/100ask_imx6ull-sdk/Linux-4.9.88
```

指定：

> 编译驱动时使用哪一套Linux内核源码。

不同开发板的路径不同，视频特别提醒需要自行修改。

不能随便填写另一个Linux源码目录。

------

### 12.2 `make -C`

```makefile
make -C $(KERN_DIR)
```

`-C`表示：

> <span style="background:#00FF80;">先进入指定的内核源码目录，再在那里执行make。</span>

相当于：

```bash
cd /home/book/100ask_imx6ull-sdk/Linux-4.9.88
make ...
```

但命令结束后仍返回驱动目录。

------

### 12.3 `M=\`pwd``

```makefile
M=`pwd`
```

告诉内核Kbuild：

> 要编译的外部模块源码位于当前目录。

假设当前目录是：

```text
/home/book/nfs_rootfs/01_hello_drv
```

那么内核会进入这个目录寻找：

```text
obj-m
hello_drv.c
```

------

### 12.4 `modules`

```makefile
make -C $(KERN_DIR) M=`pwd` modules
```

表示：

> 使用内核Kbuild系统，编译当前目录声明的外部模块。

编译输出中可以看到：

```text
CC [M] hello_drv.o
MODPOST 1 modules
CC hello_drv.mod.o
LD [M] hello_drv.ko
```

最终得到：

```text
hello_drv.ko
```

------

### 12.5 `obj-m`

```makefile
obj-m += hello_drv.o
```

它告诉Kbuild：

```text
hello_drv.o
需要最终链接成一个可加载模块
```

最终对应：

```text
hello_drv.ko
```

可以记为：

```text
obj-m中的m = module
```

------

### 12.6 编译测试APP

```makefile
$(CROSS_COMPILE)gcc -o hello_drv_test hello_drv_test.c
```

环境变量可能是：

```text
CROSS_COMPILE=arm-buildroot-linux-gnueabihf-
```

拼接后实际执行：

```bash
arm-buildroot-linux-gnueabihf-gcc \
    -o hello_drv_test hello_drv_test.c
```

这部分不是内核模块编译，而是普通ARM应用程序编译。

## 13. <span style="background:#00FF80;">为什么同一个Makefile能生成两种文件</span>？

因为两条命令走的是不同体系：

```text
hello_drv.c
    ↓ Linux Kbuild
hello_drv.ko
hello_drv_test.c
    ↓ ARM GCC
hello_drv_test
```

`hello_drv.ko`需要：

- 内核头文件；
- 内核配置；
- 内核符号；
- Kbuild规则。

`hello_drv_test`只需要：

- C库；
- 用户空间头文件；
- ARM交叉编译器。

所以<span style="color:#FF0000; background:#00FF80;">不能使用普通的：</span>

```bash
arm-gcc hello_drv.c
```

<span style="color:#FF0000; background:#00FF80;">直接编译内核模块。</span>

## 17. `loading out-of-tree module taints kernel`是不是错误？

视频加载驱动后出现：

```text
hello_drv: loading out-of-tree module taints kernel.
```

这一般不是加载失败。

它表示：

> 这个模块不是当前内核源码树内置构建体系中的正式模块，而是单独在内核树外编译的外部模块。

这种模块称为：

```text
out-of-tree module
树外模块
```

内核会标记为：

```text
tainted
```

目的是在以后出现崩溃时提醒开发者：

> 当前内核加载过外部模块，问题可能由该模块引起。

如果随后：

```bash
lsmod
ls /dev/hello
```

都能看到正确结果，通常说明模块加载成功。

## 18. 为什么有时看不到驱动的 `printk`？

视频提示，<span style="color:#FF0000; background:#00FF80;">不同系统的控制台日志级别可能不同。</span>

可以查看：

```bash
cat /proc/sys/kernel/printk
```

课程给出的设置类似：

```bash
echo "1 4 1 7" > /proc/sys/kernel/printk
```

降低控制台输出级别。

以及：

```bash
echo "7 4 1 7" > /proc/sys/kernel/printk
```

提高控制台输出级别。

这里影响的是：

> `printk`信息是否立即显示在串口控制台。

即使串口上没有显示，日志仍可能通过：

```bash
dmesg
```

查看。

所以“没有看到printk”不一定代表驱动函数没有执行。

## 19. 模块版本不匹配问题

视频最后重点展示：

```text
disagrees about version of symbol module_layout
```

含义是：

> 当前 `hello_drv.ko` 编译时依据的内核信息，与开发板正在运行的内核不一致。

------

## 为什么都是4.9.88还会不一致？

因为模块匹配信息不仅包含：

```text
4.9.88
```

还可能包含：

- `.config`配置；
- SMP设置；
- PREEMPT设置；
- ARM架构选项；
- 模块版本配置；
- 编译器信息；
- 内核符号CRC；
- 本地版本字符串；
- 生成文件状态。

所以：

```text
版本号相同
```

不等于：

```text
内核构建环境完全相同
```

------

### 正确解决办法

视频给出的核心流程是：

1. 在Ubuntu中使用当前内核源码和正确配置重新编译内核；
2. 把新内核放到开发板 `/boot`；
3. 必要时同时替换设备树和 `/lib/modules`；
4. 重启开发板；
5. 再用同一套内核源码编译驱动；
6. 重新加载驱动。

可以表示为：

```text
同一套内核源码和.config
       ├── 编译zImage → 开发板/boot
       ├── 编译modules → 开发板/lib/modules
       └── 编译hello_drv.ko
```

三者必须处于同一个“家族”。

不建议用强制加载参数绕过检查，因为不兼容模块进入内核后可能导致系统异常。

## 二、驱动加载链路详细解释

图片中的链路是：

```text
insmod hello_drv.ko
→ hello_init
→ register_chrdev
→ class_create
→ device_create
→ /dev/hello
```

下面逐步解释。

------

### 第一步：`insmod hello_drv.ko`

在开发板执行：

```bash
insmod hello_drv.ko
```

这里的 `hello_drv.ko` 是一个**内核模块文件**。

它不是普通应用程序，不能这样运行：

```bash
./hello_drv.ko
```

<span style="color:#FF0000; background:#00FF80;">因为 `.ko` 不是给用户空间执行的，而是要被加载到Linux内核中。</span>

执行 `insmod` 后，大致发生：

```text
用户执行insmod
      ↓
insmod读取hello_drv.ko
      ↓
通过系统调用把模块交给Linux内核
      ↓
内核检查模块格式、架构和版本
      ↓
解析模块依赖的内核符号
      ↓
给模块代码和数据分配内核内存
      ↓
把模块重定位到正确地址
      ↓
执行模块初始化函数
```

如果模块和当前内核不匹配，可能在这一步报错：

```text
Invalid module format
```

或者：

```text
disagrees about version of symbol module_layout
```

------

### 第二步：为什么会执行 `hello_init()`？

<span style="color:#FF0000; background:#00FF80;">驱动源码中一般有：</span>

```c
static int __init hello_init(void)
{
    /* 注册驱动 */
    return 0;
}

module_init(hello_init);
```

这里的：

```c
module_init(hello_init);
```

是<span style="color:#FF0000; background:#00FF80;">在告诉Linux内核：</span>

> <span style="color:#FF0000; background:#00FF80;">当这个模块被加载时，请调用 `hello_init()`。</span>

所以执行：

```bash
insmod hello_drv.ko
```

以后，并不是 `insmod` 根据函数名字猜测，而是<span style="color:#FF0000; background:#00FF80;">模块内部已经通过 `module_init` 声明了入口。</span>

对应<span style="color:#FF0000; background:#00FF80;">卸载时一般有：</span>

```c
static void __exit hello_exit(void)
{
    /* 注销驱动 */
}

module_exit(hello_exit);
```

<span style="color:#FF0000; background:#00FF80;">执行：</span>

```bash
rmmod hello_drv
```

时，<span style="color:#FF0000; background:#00FF80;">内核会调用：</span>

```c
hello_exit();
```

因此：

```text
module_init → 加载入口
module_exit → 卸载出口
```



## 三、`hello_init()`里面做什么？

一个简化的初始化函数可能类似：

```c
static int major;
static struct class *hello_class;

static int __init hello_init(void)
{
    major = register_chrdev(0, "hello", &hello_fops);

    hello_class = class_create(THIS_MODULE, "hello_class");

    device_create(
        hello_class,
        NULL,
        MKDEV(major, 0),
        NULL,
        "hello"
    );

    return 0;
}
```

这里主要完成三件事：

```text
1. 把驱动操作函数注册给内核
2. 创建一个设备类别
3. 创建一个具体设备并产生/dev/hello
```

------

## 四、`register_chrdev()`到底注册了什么？

典型代码：

```c
major = register_chrdev(0, "hello", &hello_fops);
```

三个重要参数是：

```text
0
→ 请求内核自动分配主设备号

"hello"
→ 注册名称

&hello_fops
→ 驱动提供的操作函数表
```

其中最重要的是：

```c
&hello_fops
```

它可能定义成：

```c
static const struct file_operations hello_fops = {
    .owner   = THIS_MODULE,
    .open    = hello_drv_open,
    .read    = hello_drv_read,
    .write   = hello_drv_write,
    .release = hello_drv_release,
};
```

这张表告诉Linux：

```text
有人打开设备
→ 调用hello_drv_open

有人读取设备
→ 调用hello_drv_read

有人写设备
→ 调用hello_drv_write

有人关闭设备
→ 调用hello_drv_release
```

所以<span style="color:#FF0000; background:#00FF80;"> `register_chrdev()` 并不只是登记一个名字。</span>

它<span style="color:#FF0000; background:#00FF80;">真正建立的是：</span>

```text
设备号
      ↓
file_operations
      ↓
驱动函数
```

------

## 五、什么是主设备号和次设备号？

<span style="color:#FF0000; background:#00FF80;">Linux设备节点</span>通常包含：

```text
主设备号 major
次设备号 minor
```

例如：

```text
/dev/hello
主设备号：240
次设备号：0
```

可以执行：

```bash
ls -l /dev/hello
```

可能看到：

```text
crw------- 1 root root 240, 0 ... /dev/hello
```

其中：

```text
c
→ character device，字符设备

240
→ 主设备号

0
→ 次设备号
```

它们的作用可以理解为：

```text
主设备号：
决定交给哪一类驱动

次设备号：
决定这个驱动下面的哪一个具体设备
```

例如一个驱动可以管理多个LED：

```text
主设备号都是240

/dev/led0 → 次设备号0
/dev/led1 → 次设备号1
/dev/led2 → 次设备号2
```

主设备号像公司编号，次设备号像公司里的部门编号。

------

## 六、`class_create()`做什么？

代码：

```c
hello_class = class_create(THIS_MODULE, "hello_class");
```

它<span style="color:#FF0000;">会在Linux设备模型中创建一个设备类别。</span>

通常能在：

```text
/sys/class/
```

<span style="color:#FF0000; background:#00FF80;">下面看到类似：</span>

```text
/sys/class/hello_class/
```

它的<span style="color:#FF0000; background:#00FF80;">作用主要是：</span>

> <span style="background:#00FF80;">把这个字符设备加入Linux统一设备模型，方便内核和用户空间设备管理系统识别。</span>

但是<span style="color:#FF0000; background:#00FF80;">它一般还不会单独产生：</span>

```text
/dev/hello
```

<span style="color:#FF0000; background:#00FF80;">还需要下一步 `device_create()`。</span>

------

## 七、`device_create()`为什么会产生 `/dev/hello`？

代码可能是：

```c
device_create(
    hello_class,
    NULL,
    MKDEV(major, 0),
    NULL,
    "hello"
);
```

其中：

```c
MKDEV(major, 0)
```

<span style="color:#FF0000; background:#00FF80;">把主设备号和次设备号组合成一个完整设备号。</span>

最后的：

```c
"hello"
```

<span style="color:#FF0000; background:#00FF80;">指定设备名称。</span>

调用完成后，内核设备模型中出现这个设备。

在常见嵌入式Linux系统中，`devtmpfs` 或用户空间设备管理程序会根据设备信息创建：

```text
/dev/hello
```

因此准确地说：

```text
device_create
→ 在Linux设备模型中注册设备
→ devtmpfs/udev等创建设备节点
→ /dev/hello出现
```

在很多简单教程中，会把它直接简化成：

```text
device_create → /dev/hello
```

------

## 八、`/dev/hello`是什么？

`/dev/hello`不是：

- 驱动源码；
- `.ko`模块文件；
- 普通文本文件；
- 真正存储数据的磁盘文件。

它是一个：

> <span style="background:#00FF80;">**字符设备节点，是用户空间进入驱动的入口。**</span>

可以理解成门牌：

```text
hello_drv.ko
→ 驱动本体

内核中的hello_drv代码
→ 已经运行的驱动

/dev/hello
→ APP找到这个驱动的入口
```

如果删除：

```bash
rm /dev/hello
```

驱动可能仍然加载在内核中，但普通APP失去了这个设备入口。

如果重新创建正确设备号的节点：

```bash
mknod /dev/hello c 240 0
```

APP又可能可以继续访问。

## 九、加载链路最终建立了什么？

驱动加载完成以后，系统中形成了下面的关系：

```text
/dev/hello
   │
   │ 保存设备类型、主设备号、次设备号
   ▼
主设备号240，次设备号0
   │
   ▼
Linux字符设备注册表
   │
   ▼
hello_fops
   │
   ├── open    → hello_drv_open
   ├── read    → hello_drv_read
   ├── write   → hello_drv_write
   └── release → hello_drv_release
```

这就是APP以后能找到驱动函数的基础。

## 十、APP调用链路详细解释

图片中的链路是：

```text
hello_drv_test
→ open/read/write
→ 系统调用
→ VFS
→ file_operations
→ hello_drv_open/read/write
```

这里最重要的是：

> <span style="background:#00FF80;">APP没有直接调用 `hello_drv_read()`，而是通过Linux的文件接口间接调用。</span>

## 十一、测试APP里通常写了什么？

简化后的测试程序可能是：

```c
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>

int main(int argc, char **argv)
{
    int fd;
    char buf[1024];

    fd = open("/dev/hello", O_RDWR);
    if (fd < 0) {
        perror("open");
        return -1;
    }

    if (strcmp(argv[1], "-w") == 0) {
        write(fd, argv[2], strlen(argv[2]) + 1);
    } else if (strcmp(argv[1], "-r") == 0) {
        read(fd, buf, sizeof(buf));
        printf("APP read: %s\n", buf);
    }

    close(fd);
    return 0;
}
```

这里调用的是标准Linux接口：

```c
open()
read()
write()
close()
```

<span style="color:#FF0000; background:#00FF80;">APP代码里并没有：</span>

```c
hello_drv_write();
```

<span style="color:#FF0000; background:#00FF80;">因为 `hello_drv_write()` 运行在内核空间，普通APP不能直接调用它。</span>

------

## 十二、`open("/dev/hello")`完整发生了什么？

假设APP执行：

```c
fd = open("/dev/hello", O_RDWR);
```

完整链路大致是：

```text
hello_drv_test
      ↓
调用C库open()
      ↓
触发open系统调用
      ↓
CPU从用户态切换到内核态
      ↓
VFS解析路径/dev/hello
      ↓
找到/dev/hello对应的inode
      ↓
发现它是字符设备
      ↓
读取主设备号和次设备号
      ↓
根据设备号查找已注册驱动
      ↓
找到hello_fops
      ↓
调用hello_fops.open
      ↓
执行hello_drv_open()
      ↓
返回文件描述符fd
```

这是<span style="color:#FF0000; background:#00FF80;">APP第一次建立与驱动之间的联系。</span>

------

## 十三、<span style="background:#00FF80;">什么是系统调用</span>？

用户APP运行在：

```text
用户空间
```

驱动运行在：

```text
内核空间
```

<span style="color:#FF0000; background:#00FF80;">用户程序不能随便跳进内核函数执行，否则会破坏系统安全。</span>

所以<span style="color:#FF0000; background:#00FF80;">必须通过Linux提供的合法入口：</span>

```text
系统调用
```

例如：

| APP函数   | 对应功能         |
| --------- | ---------------- |
| `open()`  | 打开文件或设备   |
| `read()`  | 读取数据         |
| `write()` | 写入数据         |
| `close()` | 关闭文件         |
| `ioctl()` | 发送设备控制命令 |

系统调用会让CPU从：

```text
用户态
```

安全切换到：

```text
内核态
```

内核处理完以后，再返回用户态。

可以理解为：

```text
用户程序不能直接进入内核办公室

系统调用是受检查的正式办事窗口
```

------

## 十四、VFS是什么？

VFS全称：

```text
Virtual File System
虚拟文件系统
```

它是<span style="color:#FF0000; background:#00FF80;">Linux内核提供的统一文件操作层。</span>

因为<span style="color:#FF0000; background:#00FF80;">Linux中有很多不同对象：</span>

```text
普通磁盘文件
ext4文件
NFS文件
字符设备
块设备
管道
socket
proc文件
```

但<span style="color:#FF0000; background:#00FF80;">用户程序都可以使用类似：</span>

```c
open();
read();
write();
close();
```

<span style="color:#FF0000; background:#00FF80;">VFS负责把统一操作分发给不同的具体实现。</span>

例如：

```text
read普通文件
→ ext4文件系统的读取函数

read网络文件
→ NFS读取函数

read /dev/hello
→ hello_drv_read
```

因此<span style="color:#FF0000; background:#00FF80;">VFS像一个统一前台：</span>

```text
APP只说“我要read”

VFS判断：
你读的是普通文件、网络文件，还是字符设备？
然后交给对应处理者
```

------

## 十五、`file_operations`是什么？

`file_operations`是<span style="color:#FF0000; background:#00FF80;">一张函数指针表。</span>

简化定义：

```c
struct file_operations {
    int     (*open)(...);
    ssize_t (*read)(...);
    ssize_t (*write)(...);
    int     (*release)(...);
};
```

<span style="color:#FF0000; background:#00FF80;">驱动填入自己的函数：</span>

```c
static const struct file_operations hello_fops = {
    .open    = hello_drv_open,
    .read    = hello_drv_read,
    .write   = hello_drv_write,
    .release = hello_drv_release,
};
```

所以<span style="color:#FF0000; background:#00FF80;">它相当于一个“操作翻译表”：</span>

```text
用户说open
→ 调用hello_drv_open

用户说read
→ 调用hello_drv_read

用户说write
→ 调用hello_drv_write

用户说close
→ 调用hello_drv_release
```

## 十六、`open()`与后续 `read/write()`稍有区别

这是图中没有展开、但很重要的地方。

### 第一次调用 `open()`

<span style="color:#FF0000; background:#00FF80;">内核需要根据路径和设备号找到驱动：</span>

```text
/dev/hello
→ inode
→ 主次设备号
→ 字符设备注册表
→ hello_fops
→ hello_drv_open
```

<span style="color:#FF0000; background:#00FF80;">成功后，内核会创建一个：</span>

```c
struct file
```

并让它记录：

```text
这个打开的文件使用hello_fops
```

然后APP获得一个整数：

```c
fd
```

例如：

```text
fd = 3
```

------

### 后续调用 `read(fd, ...)`

这时<span style="color:#FF0000;">不需要重新解析 `/dev/hello` 路径。</span>

内核通过：

```text
fd
→ 当前进程的文件描述符表
→ struct file
→ file_operations
→ hello_drv_read
```

<span style="color:#FF0000; background:#00FF80;">找到驱动函数。</span>

因此读取链路更准确是：

```text
APP read(fd)
      ↓
read系统调用
      ↓
根据fd查找struct file
      ↓
file->f_op->read
      ↓
hello_drv_read()
```

写入也是：

```text
APP write(fd)
      ↓
write系统调用
      ↓
根据fd查找struct file
      ↓
file->f_op->write
      ↓
hello_drv_write()
```

## 十七、文件描述符 `fd` 是什么？

APP执行：

```c
fd = open("/dev/hello", O_RDWR);
```

可能返回：

```text
3
```

这个数字不是设备号，也不是内存地址。

它是当前进程的：

> 文件描述符索引。

当前进程内部可能有：

```text
fd 0 → 标准输入
fd 1 → 标准输出
fd 2 → 标准错误
fd 3 → /dev/hello
```

所以执行：

```c
write(3, data, size);
```

内核会查当前进程的文件描述符表，发现3对应 `/dev/hello`，然后调用这个设备的驱动函数。

------

## 十八、写入链路详细解释

APP执行：

```c
write(fd, "www.100ask.net", 15);
```

完整链路：

```text
用户空间hello_drv_test
      ↓ write(fd, ...)
系统调用
      ↓
内核根据fd找到struct file
      ↓
找到file->f_op->write
      ↓
hello_drv_write()
      ↓
copy_from_user()
      ↓
数据复制到内核缓冲区kernel_buf
```

驱动函数大致可能是：

```c
static ssize_t hello_drv_write(
    struct file *file,
    const char __user *buf,
    size_t size,
    loff_t *offset)
{
    if (size > sizeof(kernel_buf))
        size = sizeof(kernel_buf);

    if (copy_from_user(kernel_buf, buf, size))
        return -EFAULT;

    return size;
}
```

这里：

```c
buf
```

是用户空间地址。

<span style="color:#FF0000; background:#00FF80;">驱动不能随意直接访问用户空间指针，所以使用：</span>

```c
copy_from_user();
```

记忆：

```text
from_user
→ 从用户空间复制到内核空间
```

------

## 十九、读取链路详细解释

APP执行：

```c
read(fd, buf, sizeof(buf));
```

完整链路：

```text
内核缓冲区kernel_buf
      ↓
hello_drv_read()
      ↓ copy_to_user()
用户空间buf
      ↓
read系统调用返回
      ↓
APP printf显示内容
```

驱动函数可能是：

```c
static ssize_t hello_drv_read(
    struct file *file,
    char __user *buf,
    size_t size,
    loff_t *offset)
{
    if (size > sizeof(kernel_buf))
        size = sizeof(kernel_buf);

    if (copy_to_user(buf, kernel_buf, size))
        return -EFAULT;

    return size;
}
```

记忆：

```text
to_user
→ 从内核空间复制到用户空间
```

## 二十、`close()`最后调用谁？

APP执行：

```c
close(fd);
```

链路是：

```text
close系统调用
      ↓
内核释放这个struct file
      ↓
调用file_operations.release
      ↓
hello_drv_release()
```

对应驱动表：

```c
.release = hello_drv_release
```

注意：

```text
用户空间调用close()
驱动中通常对应release()
```

它们名字不完全一样。

## 二十一、两个链路怎样接在一起？

<span style="color:#FF0000; background:#00FF80;">驱动加载链路先建立映射：</span>

```text
主设备号240
      ↓
hello_fops
      ↓
hello_drv_open/read/write
```

并创建：

```text

```

然后APP打开 `/dev/hello` 时：

```text
/dev/hello中的主设备号240
      ↓
找到register_chrdev注册的hello_fops
      ↓
调用hello_drv_open/read/write
```

所以两个链路的连接点是：

```text
设备号 + file_operations
```

这是<span style="color:#FF0000; background:#00FF80;">整个字符设备驱动框架的核心。</span>

## 二十三、举一个“快递柜”的类比

可以把<span style="color:#FF0000; background:#00FF80;">整个字符设备系统理解成一个快递柜。</span>

### 驱动加载

```text
register_chrdev
→ 快递公司在系统中登记营业资格

class_create
→ 建立“快递柜设备”这个类别

device_create
→ 安装具体的快递柜

/dev/hello
→ 快递柜门牌和地址
```

### APP调用

```text
open("/dev/hello")
→ 找到这台快递柜并建立一次使用会话

write()
→ 往柜子里放东西

read()
→ 从柜子里取东西

close()
→ 结束本次使用
```

### `file_operations`

它相当于这台快递柜的操作说明：

```text
开门按钮由谁处理
放入物品由谁处理
取出物品由谁处理
关闭柜门由谁处理
```

不同驱动虽然都支持 `open/read/write`，但实际执行函数完全可以不同。

## 二十四、这个Hello驱动为什么叫“虚拟字符设备”？

因为它没有真正操作外部硬件。

它只是：

```text
APP写入字符串
→ 驱动保存到kernel_buf

APP读取
→ 驱动从kernel_buf返回字符串
```

如果是LED驱动，`write()`最终可能操作GPIO寄存器：

```text
APP write("1")
      ↓
led_drv_write()
      ↓
设置GPIO高电平
      ↓
LED点亮
```

如果是按键驱动，`read()`可能读取GPIO状态：

```text
APP read()
      ↓
key_drv_read()
      ↓
读取按键GPIO
      ↓
返回按键值
```

框架仍然是：

```text
APP
→ 系统调用
→ VFS
→ file_operations
→ 具体驱动函数
```

只是驱动函数内部做的事情不同。

## 二十五、最重要的记忆版

```text
驱动加载链路：

insmod
→ 把.ko装进内核
→ hello_init
→ register_chrdev
→ 注册设备号和file_operations
→ class_create/device_create
→ 产生/dev/hello
APP调用链路：

open("/dev/hello")
→ 系统调用进入内核
→ VFS根据设备号找到驱动
→ file_operations选择具体函数
→ hello_drv_open/read/write
```

最核心的一句话是：

> **驱动加载阶段通过设备号把 `/dev/hello` 和 `file_operations` 建立联系；APP运行阶段通过 `/dev/hello` 找到这张操作表，再把 `open/read/write` 分发到驱动实现的函数。**

3. `hello_init()` 在驱动加载过程中到底做什么

先给你一张总关系图：

```text
编译驱动时
    │
    ├─ hello_fops
    │    保存 open/read/write 对应的驱动函数地址
    │
    └─ module_init(hello_init)
         告诉内核：模块加载时调用 hello_init

执行 insmod 时
    ↓
内核调用 hello_init()
    ↓
注册字符设备
    ↓
把设备号和 hello_fops 绑定
    ↓
创建 /dev/hello

APP运行时
    ↓
open/read/write
    ↓
内核查询 hello_fops
    ↓
执行 hello_drv_open/read/write
```

## 一、函数名为什么可以作为“参数”？

先看三个非常相似、但含义不同的写法：

```c
hello_init
```

表示**函数本身或函数的地址**，没有执行函数。

```c
hello_init()
```

表示**立即调用这个函数**。

```c
&hello_init
```

表示**显式取得这个函数的地址**。

在C语言的大多数表达式中，单独出现的函数名会自动转换为函数指针，所以：

```c
hello_init
```

和：

```c
&hello_init
```

在传递函数地址时，效果通常相同。

但：

```c
hello_init()
```

完全不同，它是立即执行函数。

------

### 1. 用普通C语言举例

假设有一个函数：

```c
int add(int a, int b)
{
    return a + b;
}
```

定义一个函数指针：

```c
int (*func)(int, int);
```

然后可以写：

```c
func = add;
```

也可以写：

```c
func = &add;
```

此时没有执行 `add()`，只是把 `add` 的地址保存进 `func`。

以后执行：

```c
int result = func(10, 20);
```

才相当于：

```c
int result = add(10, 20);
```

所以可以这样记：

```text
add        → 这个函数在哪里
add()      → 现在执行这个函数
&add       → 明确取得函数地址
```

------

## 二、`module_init(hello_init)` 是在传递函数名吗？

从表面看类似传参，但这里要特别注意：

```c
module_init(hello_init);
```

里面的 `module_init` 不是普通函数，而是Linux内核定义的一个**宏**。

它的作用是告诉内核：

> 这个模块被加载时，把 `hello_init` 作为初始化入口函数调用。

所以：

```c
module_init(hello_init);
```

<span style="color:#FF0000; background:#00FF80;">不是现在就执行：</span>

```c
hello_init();
```

而是<span style="color:#FF0000; background:#00FF80;">在编译、链接模块时，登记一条信息：</span>

```text
这个模块的初始化入口 = hello_init
```

<span style="color:#FF0000; background:#00FF80;">以后执行：</span>

```bash
insmod hello_drv.ko
```

<span style="color:#FF0000; background:#00FF80;">内核加载完模块后，才会间接执行：</span>

```c
hello_init();
```

------

### 为什么不能写成 `module_init(hello_init())`？

因为宏需要的是**函数的名字或地址**，不是函数的执行结果。

正确：

```c
module_init(hello_init);
```

含义：

```text
请记住 hello_init 这个函数，
以后加载模块时再调用它。
```

错误理解：

```c
module_init(hello_init());
```

这更像是：

```text
现在执行 hello_init，
然后把它返回的整数交给 module_init。
```

但 `module_init` 需要登记的是函数入口，不是返回值。

------

## 三、函数定义里的 `hello_init(void)` 怎么理解？

完整定义：

```c
static int __init hello_init(void)
{
    /* 注册驱动 */

    return 0;
}
```

可以拆成五部分：

```text
static
int
__init
hello_init
(void)
```

------

### 1. `static`

```c
static int hello_init(void)
```

这里的 `static` 表示：

> <span style="background:#00FF80;">这个函数主要只在当前 `.c` 文件内部使用，不对其他源码文件公开。</span>

假设驱动文件是：

```text
hello_drv.c
```

<span style="color:#FF0000; background:#00FF80;">那么其他 `.c` 文件通常不能直接调用这个 `hello_init()`。</span>

<span style="color:#FF0000; background:#00FF80;">驱动中的初始化函数常常写成 `static`，因为它只需要由本模块内部登记给内核。</span>

------

### 2. `int`

表示函数返回一个整数：

```c
return 0;
```

在内核初始化函数中通常约定：

```text
返回0       → 初始化成功
返回负数    → 初始化失败
```

例如：

```c
return 0;
```

表示驱动成功加载。

如果注册设备失败，可能返回：

```c
return -EINVAL;
```

或者：

```c
return -ENOMEM;
```

然后 `insmod` 会失败。

------

### 3. `__init`

```c
static int __init hello_init(void)
```

`__init` 是Linux内核定义的标记。

它表示：

> 这个函数只在初始化阶段使用。

模块加载完成后，初始化代码通常不再需要。内核可以把相应初始化区域的内存释放掉，以节省内存。

因此：

```text
hello_init()
只在加载驱动时运行一次
```

<span style="color:#FF0000; background:#00FF80;">APP每次调用 `open/read/write` 时，并不会再次执行 `hello_init()`。</span>

------

### 4. `hello_init`

这是函数名。

名称可以自己取，例如：

```c
hello_init
my_driver_init
led_init
key_driver_init
```

真正让它成为模块加载入口的不是名字本身，而是：

```c
module_init(hello_init);
```

即使函数叫：

```c
static int __init abc(void)
{
    return 0;
}
```

只要写：

```c
module_init(abc);
```

它同样会成为模块加载入口。

------

### 5. `(void)`

```c
hello_init(void)
```

表示这个函数：

> 不接收任何参数。

注意，函数定义中的：

```c
hello_init(void)
```

不是函数调用，而是在声明函数参数类型。

真正调用是：

```c
hello_init();
```

可以对比：

```c
int add(int a, int b)
```

表示 `add` 函数接收两个整数。

```c
int hello_init(void)
```

表示 `hello_init` 不接收参数。

## 四、结构体里的 `.open` 是什么意思？

你的代码是：

```c
static const struct file_operations hello_fops = {
    .owner   = THIS_MODULE,
    .open    = hello_drv_open,
    .read    = hello_drv_read,
    .write   = hello_drv_write,
    .release = hello_drv_release,
};
```

这里使用的是C语言的：

> **指定成员初始化语法，Designated Initializer。**

------

### 1. 普通结构体例子

先定义结构体：

```c
struct Student {
    int age;
    int score;
};
```

可以这样初始化：

```c
struct Student student = {
    .age = 18,
    .score = 95,
};
```

其中：

```c
.age = 18
```

表示把结构体成员 `age` 初始化为18。

```c
.score = 95
```

表示把成员 `score` 初始化为95。

所以前面的点：

```text
.age
.score
```

表示：

> <span style="color:#FF0000; background:#00FF80;">我现在指定要初始化结构体中的哪个成员。</span>

------

### 2. `file_operations`也是一个结构体

Linux内核中定义了类似：

```c
struct file_operations {
    struct module *owner;

    int (*open)(...);

    ssize_t (*read)(...);

    ssize_t (*write)(...);

    int (*release)(...);

    /* 还有很多其他成员 */
};
```

注意，其中：

```c
int (*open)(...);
```

不是普通整数，而是一个**函数指针成员**。

也就是说，`open` 这个成员可以保存一个函数的地址。

同理：

```c
ssize_t (*read)(...);
ssize_t (*write)(...);
```

也都是函数指针成员。

------

## 五、`.open = hello_drv_open` 怎样理解？

这行：

```c
.open = hello_drv_open,
```

可以拆成：

```text
.open
→ 指定初始化 file_operations 结构体中的 open 成员

hello_drv_open
→ hello_drv_open 函数的地址
```

整体含义是：

> 把 `hello_drv_open` 函数的地址，保存进 `hello_fops.open` 函数指针成员。

类似：

```c
hello_fops.open = hello_drv_open;
```

只不过由于 `hello_fops` 是在定义时初始化，所以使用：

```c
.open = hello_drv_open
```

------

### 完整映射

```c
static const struct file_operations hello_fops = {
    .owner   = THIS_MODULE,
    .open    = hello_drv_open,
    .read    = hello_drv_read,
    .write   = hello_drv_write,
    .release = hello_drv_release,
};
```

等价理解为：

```text
hello_fops.owner
→ 当前模块

hello_fops.open
→ hello_drv_open函数地址

hello_fops.read
→ hello_drv_read函数地址

hello_fops.write
→ hello_drv_write函数地址

hello_fops.release
→ hello_drv_release函数地址
```

因此这张表可以画成：

```text
hello_fops
├── owner   ──→ 当前hello_drv模块
├── open    ──→ hello_drv_open()
├── read    ──→ hello_drv_read()
├── write   ──→ hello_drv_write()
└── release ──→ hello_drv_release()
```

------

### 六、为什么右边的函数名没有括号？

正确写法：

```c
.open = hello_drv_open,
```

因为这里要保存的是：

```text
函数地址
```

不是现在调用函数。

假如写成：

```c
.open = hello_drv_open(),
```

含义就变成：

```text
立刻执行hello_drv_open，
然后把它的返回值赋给open成员。
```

但 `open` 成员需要的是函数指针，不是一个整数返回值，因此类型不匹配。

可以记住：

```text
.open = hello_drv_open
→ 保存函数地址，正确

.open = hello_drv_open()
→ 执行函数并取得返回值，错误
```

## 七、结构体里的点和普通成员访问有什么区别？

点号有两个很接近的用途。

### 1. 初始化时

```c
struct Student s = {
    .age = 18,
};
```

这里：

```c
.age
```

是“指定初始化哪个成员”。

------

### 2. 定义完成后访问成员

```c
s.age = 20;
```

这里：

```c
s.age
```

是通过结构体对象访问成员。

------

### 3. 如果拿到的是结构体指针

```c
struct Student *p = &s;
```

要使用箭头：

```c
p->age = 20;
```

它基本等价于：

```c
(*p).age = 20;
```

因此：

```text
对象访问成员    → .
指针访问成员    → ->
初始化指定成员  → .成员名 =
```

## 八、`static const struct file_operations hello_fops` 每个词是什么意思？

```c
static const struct file_operations hello_fops
```

可以拆成：

### `struct file_operations`

说明变量类型是：

```text
Linux文件操作函数表结构体
```

------

### `hello_fops`

是这个结构体变量的名字。

`fops`通常是：

```text
file operations
```

的缩写。

------

### `const`

表示初始化完成后，<span style="color:#FF0000; background:#00FF80;">这张函数表不应该被随意修改。</span>

例如不应该在运行中随便写：

```c
hello_fops.read = other_read;
```

内核驱动通常把操作表声明成 `const`，因为它在模块运行期间一般保持不变。

------

### `static`

说明<span style="color:#FF0000; background:#00FF80;">这个变量主要只在当前源码文件中使用。</span>

所以整句可以翻译为：

> 在当前源文件中定义一个只读的 `file_operations` 结构体变量，名字叫 `hello_fops`。

------

## 九、`.owner = THIS_MODULE` 有什么用？

```c
.owner = THIS_MODULE,
```

`THIS_MODULE`表示：

> 当前这个内核模块，也就是 `hello_drv.ko`。

它主要帮助内核管理模块引用计数。

例如APP已经打开：

```text
/dev/hello
```

正在调用驱动，如果这时强行卸载模块，驱动代码可能从内存消失，APP继续调用时就会发生严重错误。

设置：

```c
.owner = THIS_MODULE
```

可以帮助内核知道：

```text
这张操作表属于hello_drv模块
设备正在被使用时，需要防止模块被错误卸载
```

## 十、`hello_init()` 里面三条语句逐条解释

你的简化代码：

```c
static int major;
static struct class *hello_class;

static int __init hello_init(void)
{
    major = register_chrdev(0, "hello", &hello_fops);

    hello_class =
        class_create(THIS_MODULE, "hello_class");

    device_create(
        hello_class,
        NULL,
        MKDEV(major, 0),
        NULL,
        "hello"
    );

    return 0;
}
```

------

### 第一步：注册字符设备

```c
major = register_chrdev(0, "hello", &hello_fops);
```

这是一个真正的函数调用，因为有括号：

```c
register_chrdev(...)
```

三个参数分别是：

#### 第一个参数：`0`

```c
register_chrdev(0, ...)
```

表示：

> <span style="background:#00FF80;">请求Linux内核自动分配一个没有被占用的主设备号。</span>

假设返回：

```text
240
```

那么：

```c
major = 240;
```

------

#### 第二个参数：`"hello"`

这是<span style="color:#FF0000; background:#00FF80;">驱动注册名称。</span>

执行：

```bash
cat /proc/devices
```

可能看到：

```text
240 hello
```

------

### 第三个参数：`&hello_fops`

```c
&hello_fops
```

这里的 `&` 不是函数名，而是：

> 取得 `hello_fops` 这个结构体变量的地址。

`register_chrdev()`<span style="color:#FF0000; background:#00FF80;">需要知道操作表保存在哪里，所以传入结构体指针：</span>

```text
&hello_fops
        ↓
指向操作表
        ↓
open/read/write/release对应哪些函数
```

<span style="color:#FF0000; background:#00FF80;">注册完成后，内核建立：</span>

```text
主设备号240
     ↓
&hello_fops
     ↓
hello_drv_open/read/write
```

## 十一、这里同时出现了两种“传地址”

你当前代码里有两种容易混淆的情况。

### 情况一：传函数地址

```c
.open = hello_drv_open
```

这里 `hello_drv_open` 是函数名，在表达式中代表函数地址。

------

### 情况二：传结构体地址

```c
register_chrdev(0, "hello", &hello_fops)
```

这里 `hello_fops` 是结构体变量，必须使用：

```c
&hello_fops
```

才能取得它的地址。

区别是：

```text
函数名hello_drv_open
通常会自动转换成函数地址

普通结构体变量hello_fops
不会自动变成地址，需要显式写&
```

## 十二、第二步：创建class

```c
hello_class =
    class_create(THIS_MODULE, "hello_class");
```

它<span style="color:#FF0000; background:#00FF80;">在Linux设备模型中创建一个类别：</span>

```text
/sys/class/hello_class/
```

返回值是：

```c
struct class *
```

也就是一个结构体指针，<span style="color:#FF0000; background:#00FF80;">因此变量定义为：</span>

```c
static struct class *hello_class;
```

这里的星号：

```c
*hello_class
```

<span style="color:#FF0000; background:#00FF80;">表示 `hello_class` 保存的是一个 `struct class` 对象的地址。</span>

------

## 十三、第三步：创建设备

```c
device_create(
    hello_class,
    NULL,
    MKDEV(major, 0),
    NULL,
    "hello"
);
```

逐个参数理解。

### `hello_class`

<span style="color:#FF0000; background:#00FF80;">把设备放入刚才建立的：</span>

```text
hello_class
```

<span style="color:#FF0000; background:#00FF80;">类别中。</span>

------

### 第一个 `NULL`

通常是<span style="color:#FF0000;">父设备指针。</span>

这里<span style="color:#FF0000;">没有父设备，所以传：</span>

```c
NULL
```

------

### `MKDEV(major, 0)`

`MKDEV`<span style="color:#FF0000; background:#00FF80;">是一个宏，用来组合：</span>

```text
主设备号major
次设备号0
```

假设：

```text
major = 240
minor = 0
```

则：

```c
MKDEV(240, 0)
```

<span style="color:#FF0000; background:#00FF80;">生成完整设备编号。</span>

------

### 第二个 `NULL`

是驱动私有数据指针，这个简单例子暂时不需要，所以传空指针。

------

### `"hello"`

<span style="color:#FF0000; background:#00FF80;">设备名称。</span>

最终设备模型创建后，常见系统会生成：

```text
/dev/hello
```

## 十四、`hello_init()`和 `hello_fops`是什么关系？

`hello_fops`先在源码中准备好：

```text
hello_fops
├── open  → hello_drv_open
├── read  → hello_drv_read
└── write → hello_drv_write
```

然后 `hello_init()`执行：

```c
register_chrdev(0, "hello", &hello_fops);
```

<span style="color:#FF0000; background:#00FF80;">把这张操作表正式交给内核。</span>

所以：

```text
hello_fops
只是提前填好的一张表

hello_init()
负责把这张表注册给Linux内核
```

如果只定义：

```c
static const struct file_operations hello_fops = {...};
```

但没有执行：

```c
register_chrdev(..., &hello_fops);
```

<span style="color:#FF0000; background:#00FF80;">那么Linux并不知道应该什么时候使用这张表。</span>

## 十六、需要注意：图片里的代码省略了错误处理

图片中的代码是为了讲解流程而简化的。

真实驱动至少要检查：

```c
major = register_chrdev(...);

if (major < 0) {
    return major;
}
```

还要检查：

```c
hello_class = class_create(...);

if (IS_ERR(hello_class)) {
    unregister_chrdev(major, "hello");
    return PTR_ERR(hello_class);
}
```

以及检查 `device_create()` 是否失败。

否则如果注册失败，函数仍然：

```c
return 0;
```

会错误地告诉内核“初始化成功”。

一个更完整的思路是：

```c
static int __init hello_init(void)
{
    major = register_chrdev(0, "hello", &hello_fops);
    if (major < 0)
        return major;

    hello_class =
        class_create(THIS_MODULE, "hello_class");

    if (IS_ERR(hello_class)) {
        unregister_chrdev(major, "hello");
        return PTR_ERR(hello_class);
    }

    hello_device = device_create(
        hello_class,
        NULL,
        MKDEV(major, 0),
        NULL,
        "hello"
    );

    if (IS_ERR(hello_device)) {
        class_destroy(hello_class);
        unregister_chrdev(major, "hello");
        return PTR_ERR(hello_device);
    }

    return 0;
}
```

你现在先理解简化版即可，之后再学习错误回滚。

## 十七、最后用三句话记住

### 函数名

```text
hello_drv_open
→ 函数地址，用来登记“以后调用谁”

hello_drv_open()
→ 立即执行这个函数
```

### 结构体里的点

```text
.open = hello_drv_open
→ 把open成员初始化为hello_drv_open函数地址
```

### `hello_init`

```text
module_init(hello_init)
→ 登记模块加载入口

insmod hello_drv.ko
→ 内核调用hello_init()

hello_init()
→ 注册字符设备、登记hello_fops、创建/dev/hello
```

最核心的一句话：

> `hello_fops`是一张“APP操作与驱动函数的对应表”，`hello_init()`负责在模块加载时把这张表注册给Linux内核，并创建用户空间能够访问的 `/dev/hello` 入口。
